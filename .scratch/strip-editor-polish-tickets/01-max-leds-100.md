## Parent

#71（规格：灯组进阶编辑器打磨）

## What to build

把「一条灯组能接多少颗灯珠」的实际上限从 64 抬到 100，让每个引脚可以接不同长度的灯带。

线上字节布局**不变**：`start` / `end` 本来就是 1 字节，100 落得下；`SetLedCount` 载荷仍是 3 字节；状态存储的段记录与总长也与灯珠数无关。涨的只有固件侧的缓冲与校验常量。

固件要跟着改的静态内存：TDM 帧缓冲从 8×192 字节变成 8×300（约 +972 字节），以及渲染与推送路径上两个 192 字节的栈帧。时序代价按实测推算：8 条满 100 颗时单轮 TDM 约 26ms（实测折算约 32ms），20fps 下占用从约 42% 升到约 65%，帧率上限从约 48 降到约 31。这是接受的代价，**不为此提高帧率**。

效果计算里几处「灯珠数 ≤ 64」的溢出推导要重新核对并把注释里的界改掉（结论是仍落在 32/64 位整数内，但假设本身不能留着）。

小程序侧同步改常量与占位文案；两代测试向量重新生成，并确保固件、小程序、向量校验脚本三端对同一批向量一致。

## Acceptance criteria

- [ ] 设备接受 100 颗并把这条灯组真实点亮到 100 颗
- [ ] 101 颗被拒绝，设备保留原数量并回参数非法
- [ ] 0 颗仍被拒绝
- [ ] 同一台设备上两条灯组可以是不同长度（例如 100 与 24），互不影响
- [ ] 状态存储在 100 颗时长度不变，重启后逐组灯珠数正确恢复
- [ ] 8 条灯组各 100 颗时动画仍连续播放，无掉帧报告、无复位
- [ ] 固件 host 单测覆盖 100 接受 / 101 拒绝，并更新原先以 65 为拒绝边界的用例
- [ ] 小程序常量与界面占位文案同步到 1–100
- [ ] v3 与 v4 两代向量重新生成，三端校验一致
- [ ] 固件 host 单测、小程序单测与类型检查全部干净
