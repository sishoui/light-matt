# v3 端到端真机验收手册

对应 GitHub issue [#46](https://github.com/sishoui/light-matt/issues/46)，规格
[`spec-v3.md`](./spec-v3.md)，字节契约 [`protocol-v3.md`](./protocol-v3.md)。

本文是**执行手册 + 记录表**。#46 需要真机、8 条灯带与录像设备，**代码侧无法自证**。
自动化的部分（协议字节、两层合成、容量边界、迁移）已经在 host 测试与单测里锁死，
本手册只覆盖**必须用眼睛、手和录像判定**的项目。

> **证据规则**：每条结论必须附「现象描述」或「日志/录像片段」。
> 不接受「应该没问题」。失败条目先二分定位；设计问题记为已知限制并回写，
> 不擅自扩票。

## 0.0 已完成的机器验收（2026-11-01，COM6 / ESP32-C3）

不需要人眼的部分已经用 PC 当 central 跑过，结论如下。

**编译**（`scripts\build-firmware.cmd`，ESP-IDF v6.1）
- 零错误、零警告（我们自己的 `firmware/main/*.c`）
- app 分区余量 **87%**（`lumen.bin` 0x85430 / 分区 0x3E0000）
- NVS 分区实测 **64KB**，分区表符合 `protocol-v3.md` §10.1
- DRAM 已用 **63%**，余 **118KB**（两层结构 + 两套 16KB 剧本缓冲之后）
- 烧录哈希校验通过

**协议层 47/47**（`python scripts/probe-v3.py`）

| 组 | 结果 |
|---|---|
| State 37 字节（GATT read + 回落路径） | ✅ pmask=0xFF amask 有值，带数与灯珠数正确 |
| StripConfigReport 24B | ✅ 8 带，已分配 gpio=3/10/0/1/4/5/6/7，未分配 0xFF |
| DeviceInfoReport 15B | ✅ fw v3.0、MAC `cc:8d:a2:c2:56:62`、caps=0x01（两层有、fade 无） |
| ACK 回显 seq / 原命令字 | ✅ |
| 亮度钳位 | ✅ 写 255 读回 200 |
| 每带开关 | ✅ 关 bit1 → pmask 0xFD，开回 0xFF；strip=8 / on=2 被拒 |
| `SetPower(0)` 不改 pmask | ✅ 全局关灯后 pmask 仍 0xFF |
| SetSegment 两层 × 三种 blend | ✅ 全部 ACK，21B 单片写 |
| 非法段（单层带 blend / 空 layer0 / start>end / 呼吸 300ms） | ✅ 全部 `InvalidParam` |
| SegmentReport 21B + 真实槽位 | ✅ |
| 剧本下发全流程 | ✅ Begin→Stage(含 fade=250)→Segment→Commit→QueryScript |
| 断电重启后剧本仍在 | ✅ `剧本已恢复`，`ScriptSummary` 仍报 stages=1 |

**真机抓到并修掉的一个 P0**（host 测试无法发现）

`ScriptCommit` 一执行就 panic 重启：尺寸预检在栈上拷了两个 `lumen_script_t`
（各 ~12.3KB），而这条路径跑在 NimBLE host 任务的 **4096 字节**栈上。
PC 栈以 MB 计，所以 10993 项 host 断言全绿也没暴露。已改为
`lumen_script_blob_encode_with_override` 的覆盖视图（只传指针），
并加 `_Static_assert` 把「剧本表必须留在静态区」固定住。
**教训：凡在 BLE 回调链上新增代码，都要问一句「这会在 4KB 栈上放什么」。**

**仍需真机人眼/手机的部分**：§1 的全部功能项（颜色对不对、两层叠加好不好看）、
§2 的录像与错色率、§3.6 的日志面板、§4 的文档收尾。下面保持原清单不变。

## 0. 前置条件

| 项 | 要求 |
|---|---|
| 固件 | `integration/lumen-v3` 的 `scripts\build-firmware.cmd` 产物（**自定义分区表**，NVS 64KB） |
| 小程序 | 微信开发者工具导入 `miniprogram/`，真机预览（Android 走 `setBLEMTU(185)`；iOS 用系统协商值） |
| 硬件 | ESP32-C3 + **8 条 WS2812B**（建议 30 / 60 / 10 / … 不同灯珠数，用来测 per-strip 上限） |
| 供电 | **每条灯带独立 5V 供电，只与开发板共地**（见 `end-to-end-acceptance.md` §0.2 的教训） |
| 录像 | 固定机位的相机 + `scripts/record-board.py` / `scripts/analyze-board-video.py`（沿用 #20 方法） |

### 0.1 必须记录的已知损失：v2 → v3 断崖升级

**刷 v3 固件后，设备上的全部配置回到默认值。** v2 的 NVS blob（state v3 / script v1）
不被 v3 识别（magic 从 `LMEN`/`LMSC` 变成 `LMEN` v4 / `LMS3` v2，协议 magic 从 `0xA5`
变 `0xA6`、版本 `0x02` 变 `0x03`）。个人测试阶段没有第三方在用，无迁移代价，但：

- ✅ 必须在验收记录里写明「本次升级丢失了旧配置」，**避免以后误判为 bug**；
- ❌ 不要为此写迁移代码——双格式读取会让已经很紧的剧本容量更紧。

基线：v2 的错色率 **0.42%**（8 带 × 64 灯 @20fps，见 `docs/rmt-ble-stability.md`）。

| 2.4 | 分片写压力：连续 400s 下发跨 2 片以上的命令 | **重组失败 0 次** | ____ 次 | ☐ |
| 2.5 | 8 带全开 vs 只开 4 带的**轮周期** | 关闭 4 带后明显下降 | ____ ms → ____ ms | ☐ |
| 2.6 | BLE 写入次数 | v3 分片让写次数增加，记录实际值并与 v2 对比 | ____ | ☐ |

> 2.2 的已知风险：两层让每颗灯从 1 次求值变最多 2 次 + 1 次 blend。
> 8 带 × 64 灯 = 512 颗，最坏 1024 次求值。C3 单核 @160MHz 上若 20fps 撑不住，
> `CONFIG_LUMEN_ANIM_FPS` 可降到 15——**降帧率是允许的结论，不是失败**。
