**真机抓到并修掉的一个 P0**（host 测试无法发现）

`ScriptCommit` 一执行就 panic 重启：尺寸预检在栈上拷了两个 `lumen_script_t`
（各 ~12.3KB），而这条路径跑在 NimBLE host 任务的 **4096 字节**栈上。
PC 栈以 MB 计，所以 10993 项 host 断言全绿也没暴露。已改为
`lumen_script_blob_encode_with_override` 的覆盖视图（只传指针），
并加 `_Static_assert` 把「剧本表必须留在静态区」固定住。
**教训：凡在 BLE 回调链上新增代码，都要问一句「这会在 4KB 栈上放什么」。**

**视觉验收（2026-11-01，摄像头实拍 GPIO 6 那一路）**

接在 GPIO 6 上的是一块 **8×4 LED 矩阵板（30 颗）**。逐项实拍结果：

| 测什么 | 怎么判 | 结果 |
|---|---|---|
| 该路是否就是这块板 | 全关 vs 只开 strip 6 的画面均值 | **1.5 → 104.7** ✅ |
| 单色是否正确 | 设绿色静态段，统计光晕通道 | **R=9 G=93 B=47**，绿色占优 ✅ |
| 呼吸是否有明暗起伏 | 2s 周期、最暗 0，连拍 70 帧测亮度 | **546万 → 2.7亿**，肉眼可见 ✅ |
| **两层叠加**（彩虹 × 呼吸相乘） | 同时看亮度波动与色相变化 | 亮度 **42..103** 波动 + RGB 三通道各自涨落（R 61..116 / G 9..82 / B 20..137）；画面里**灯珠逐颗可辨、色相沿带铺展、暗部不塌陷** ✅ |

最后一张两层实拍是最有说服力的证据：8×5 点阵里每颗灯亮度不同（呼吸包络），
颜色从橙黄渐变到品红（彩虹色相铺展），两者叠加后颜色没有畸变。

> 两个**脚本**（非固件）问题，已修，记在这里免得下次再踩：
> 1. `SetStripPower` 只回 ACK，**不会**主动推 StateReport；要读新掩码得显式 `QueryState`。
> 2. 摄像头过曝的根因是 **GAIN 被自动拉满到 255**，不是曝光时间；`set(CAP_PROP_GAIN, 0)`
>    之后才拍得清（`CAP_PROP_AUTO_EXPOSURE` 在这台机器上读回恒为 -1，不可依赖）。

**仍需真机人眼/手机的部分**：§1 的全部功能项（颜色对不对、两层叠加好不好看）、
§2 的录像与错色率、§3.6 的日志面板、§4 的文档收尾。下面保持原清单不变。

### 0.1 必须记录的已知损失：v2 → v3 断崖升级

**刷 v3 固件后，设备上的全部配置回到默认值。** v2 的 NVS blob（state v3 / script v1）
不被 v3 识别（magic 从 `LMEN`/`LMSC` 变成 `LMEN` v4 / `LMS3` v2，协议 magic 从 `0xA5`
变 `0xA6`、版本 `0x02` 变 `0x03`）。个人测试阶段没有第三方在用，无迁移代价，但：

- ✅ 必须在验收记录里写明「本次升级丢失了旧配置」，**避免以后误判为 bug**；
- ❌ 不要为此写迁移代码——双格式读取会让已经很紧的剧本容量更紧。

## 2. 稳定性（2026-11-01 起改用新方法，旧口径作废）

> ### ⚠ 0.42% 这个基线不再可比
>
> v2 的「0.42%」是用旧工具 `analyze-board-video.py` 得出的，它有两个问题：
>
> 1. **口径只统计「亮灯数 < 8」的帧。** 复算 2026-10-31 的 400s 录像发现，
>    t=210.0s 与 210.3s 两帧是**整板 64 格均匀全亮**（每格亮度 64–88，与正常帧
>    相当），因为不属于「变少」被排除在统计之外。而正常场景只亮 8 颗 ——
>    「整板均匀平涂」正是「没有活动段 → 走 v1 单色回退」的输出形态，
>    最可能的成因是 **TDM 轮询里 GPIO 切换与推像素错位，板子吃到了别的 strip
>    的帧**。这比「部分熄灭」严重得多（内容级错误，不是亮度错误）。
> 2. **时间戳快 20%。** 录像器按请求值 3fps 写容器，而这台相机 1080p 实测
>    只有 2.51fps（1200 帧实际耗时 478.8s），所以全部时间戳偏快，
>    与串口日志按 `t=` 对齐会系统性错位。
>
> 因此：**新的错色率必须用它自己的数字，不能和 0.42% 比。**
> 目标判据仍然是「≤1 次/10 分钟且用户不可感知」，但工具只回答前半句。

### 2.1 新方法：绝对参考，不用滚动基线

旧方法逐格和「它自己过去 90 帧的中位数」比，有三个解不掉的问题：前 3 秒
无法判定；无法区分「错色 / 整条断了 / 显示成别人的颜色」；**持续错色约 1 秒后
会被基线吸收成新常态**，之后再也不报。

新方法直接问「这一帧**应该**是什么样」。场景是已知的（我们自己下发的 8 色），
布局是标定的，所以比绝对值即可，没有基线、不会吸收、类型可分：

| 事件类型 | 含义 | 判据 |
|---|---|---|
| `dark` | 整条熄灭 / WS2812B 锁存残影 | 该带色度强度 < 18 |
| `wrong_hue` | 该带错色 | 与应有色相偏离 > 28° |
| `crosstalk` | **显示成了另一条带的颜色（TDM 串带）** | 更接近别条期望值且近 12° 以上 |
| `dim` / `bright` | 掉压 / 白化 | 亮度相对期望 < 0.45× 或 > 2.2× |

配套三个工具（均已通过自检）：

```bash
# 1) 逐带几何标定（换机位/换分辨率必须重跑）
python scripts/strip-layout.py --selftest
python scripts/strip-layout.py --isolate .layout-shots      # 会改设备状态
python scripts/strip-layout.py --show

# 2) 配置画面 + 录像（新录像器用实测帧率写容器，并记每帧真实时间戳）
python scripts/ble-stress.py --brightness 60 colorize
python scripts/record-board.py base.mp4 --seconds 400 --width 640 --height 480

# 3) 判定
python scripts/analyze-strips-video.py --selftest
python scripts/analyze-strips-video.py stress.mp4 --json out.json
```

### 2.2 分辨率与帧率的取舍（实测，结论有反转）

这台相机的分辨率/帧率实测：

| 分辨率 | 实测 fps | 能否标定 |
|---|---|---|
| 1920×1080 | 2.5~5.0 | **能** |
| 1600×896 | 7.50 | 未试 |
| 1280×720 | 10.0 | 未试 |
| 960×540 | 15.0 | 未试 |
| 640×480 | 30.0 | **不能** |

**曾经判断「帧率比分辨率值钱」，实测推翻了它。** 640×480 虽然能跑到 30fps，
但灯带光晕在低分辨率下糊成一片，逐带自适应亮度的判据（高饱和像素占比）
完全失真——即使把 LED 亮度降到 30，占比仍有 65~92%，标定无法收敛。

所以当前只能在 1080p 标定，而 1080p 只有 2.5~5fps。**这是本套方法最大的
短板**：分辨率够用但帧率不足，帧率够用但标不出来。固件 20fps，
5fps 相当于只抽样 25% 的固件帧。

| # | 项 | 判据 | 实测 | 结果 |
|---|---|---|---|---|
| 2.1 | 8 带 @20fps 连续 **400s** 录像 | 见下方新口径 | **120s 已完成，400s 未跑**（见 §2.4b） | ◐ |
| 2.2 | 两层合成后的**单帧耗时** | 20fps 撑得住（≤50ms/帧） | **8 带单层 11.7ms → 两层 12.6ms/轮**（+0.95ms），远低于 50ms 预算 | ✅ |
| 2.3 | 若撑不住 20fps | 记录实际稳定帧率（降到多少 fps） | 撑得住，**无需降帧**（12.6ms << 50ms） | ✅ |
| 2.4 | 分片写压力：连续 400s 下发跨 2 片以上的命令 | **重组失败 0 次** | **787 条 × 2 片 = 1574 次写，非 0 ACK 0 次**（45s，强制 19B 数据片） | ✅ |
| 2.5 | 8 带全开 vs 只开 4 带的**轮周期** | 关闭 4 带后明显下降 | **11.7ms → 4.5~5.9ms（下降约 52%）** | ✅ |
| 2.6 | BLE 写入次数 | v3 分片让写次数增加，记录实际值并与 v2 对比 | 21B 段载荷在 19B 片容量下 = **2 片/帧**（v2 的 8/12B 段是 1 片）；MTU≥247 时回到 1 片 | ✅ 记录 |

#### 2.4b 首次压力验证（2026-11-02，120s）

| 环节 | 实测 |
|---|---|
| BLE 写入 | 2400 帧 / 120s = **20.0Hz 精确达标**；非 0 ACK **0 次** |
| 录像 | 665 帧 @ **5.0fps**；容器帧率用实测值（旧版按请求值写，时间戳快 20%） |
| 判定 | **0 事件，判据「通过」** |

**但这个「通过」只覆盖 3 条带（s4/s5/s6，基线噪声 0.3~3.0°），不是 8 条。**
其余被排除而非强行判定：

- strip 1 物理上只有 2 颗灯 —— 两个孤立光点在几何上定不出方向，无解；
- 另有 4 条基线色相噪声超过 10°（采样点落在光晕上），硬判会刷出假事件。
  实测某条带基线噪声 14°、压力段抖到 114°，按原逻辑产生 25 个假事件全在它身上。

**相机硬限制（写进验收记录，避免以后误判为固件 bug）**：

- **色域被压缩**：固件色相 0°→315°，相机实测只覆盖 23°→279°（拟合斜率 0.75）。
  s4/s5/s6 三条带实测色相只差 0.3° —— **相机分不开**，因此 `crosstalk`
  （串带检测）在当前硬件上不可用，工具会自动禁用并提示。
- **两组录像之间画面整体亮度会差 31%**，即使曝光参数完全相同。所以基线
  必须在压力段之前紧接着录，不能跨会话复用。

> 2.2 的已知风险：两层让每颗灯从 1 次求值变最多 2 次 + 1 次 blend。
> 8 带 × 64 灯 = 512 颗，最坏 1024 次求值。C3 单核 @160MHz 上若 20fps 撑不住，
> `CONFIG_LUMEN_ANIM_FPS` 可降到 15——**降帧率是允许的结论，不是失败**。

### 2.3 已查明的硬件事实（写进验收记录，避免以后误判为 bug）

| 事实 | 证据 | 定性 |
|---|---|---|
| 8 条灯带**物理长度不同**，从 2 颗到 30 颗 | 逐条 `pmask` 单独点亮 + 录像逐个计数 | 硬件现状 |
| 固件 `State.strip_counts` 报 `[30]×8`，与物理不符 | 向 2 颗那条写 `SetSegment [5,5]`，设备回 `result=0x00 OK` | **已知缺陷**：段可合法指向不存在的灯珠，多余像素被 WS2812B 静默丢弃，协议层看不出 |
| strip_id ↔ 物理位置的映射不是顺序的 | 逐条隔离拍摄（见 `.strip-layout.json`） | 记录备查，非缺陷 |
| 最上面那条（strip 1）**只有 2 颗灯** | 隔离拍摄只能拍到两个孤立光点 | 几何上无法定方向，**该带永远无法纳入自动判定** |
| 相机**色域压缩**：固件 0°→315°，实测只覆盖 23°→279° | 8 色标定后拟合斜率 0.75 | 三条带实测色相只差 0.3°，**串带检测不可用** |
| 640×480 下**无法标定** | 光晕糊成一片，自适应亮度判据失真（占比恒 65~92%） | 只能在 1080p 标定，代价是 2.5~5fps |
| 两组录像之间整体亮度差 31%（曝光参数相同） | 同一 LED 配置、同一 −11/0，全帧均值 0.112 vs 0.147 | **基线必须紧邻压力段录制**，不可跨会话复用 |
