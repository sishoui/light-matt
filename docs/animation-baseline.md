# 动画帧率与 RMT 带宽基线（v2）

**状态**：**部分推导、部分未测**（2026-10-31）。**唯一真相**：本文件的数字分两类，标签写清楚——
`[算]` = 由 WS2812B 时序与 C3 硬件上限推导，可复算；`[测]` = 真机实测；`[未测]` = 没有数据。

[#22 动画引擎](https://github.com/sishoui/light-matt/issues/22)、

## 0. 一句话结论

**8 路 TDM 的线上带宽够用，不是瓶颈。** 64 灯 × 8 条轮询一轮 `[算]` ≈ **17.6 ms**（每条 ≈ 57 Hz），
10fps 动画只用掉约 **17.6%** 的 RMT 带宽。因此 #22 取 **10fps 默认、可配**，
不需要为了帧率牺牲 8 条灯带。

**真正开放的风险是「BLE 抢占 RMT ISR 导致波形损坏（错色）」，不是带宽。**
这条在 8 路条件下**没有实测数据**——手上的硬件只有 1 条灯带（COM6），
8 路需要 8 条灯带 + 8 引脚接线。8 路的真机数字由 [#29](https://github.com/sishoui/light-matt/issues/29) 补。

> 本条**不声称「共存通过」**。v1 的 #7 长跑同样是被跳过而不是通过的
> （见 `rmt-ble-stability.md` §0）。两条票的未验证项合并成同一个开放风险，
> 入口都在 `rmt-ble-stability.md`。

## 2. 带宽上界（可复算）

WS2812B：每 bit **1.25 µs**（800 kHz），每灯 **24 bit**，帧尾 latch ≥ **280 µs**。

```
单条发送 = led_count × 24 × 1.25µs + 280µs
轮询一轮 = 单条发送 × strip_count + GPIO 切换开销（量级 < 10µs/次，忽略）
每条刷新率 = 1 / 轮询一轮
```

| 每条灯珠 | 单条发送 | 8 条一轮 | 每条刷新率 | 10fps 占带宽 |
|---|---|---|---|---|
| 30 | 1.18 ms | 9.44 ms | **105.9 Hz** | 9.4% |
| 64 | 2.20 ms | 17.60 ms | **56.8 Hz** | 17.6% |

结论：

- **轮询一轮远小于 100 ms**，所以「8 条灯带导致动画卡顿」在带宽层面不成立。
- 若真机出现卡顿，瓶颈只可能是 ①BLE 抢占 ISR 造成波形损坏，②单核上渲染任务被
  BLE 主机任务（优先级 21）推迟。渲染任务优先级 4 低于主机任务，这是设计使然
  （不能反过来，否则刷新会阻塞协议栈）。
- **动画帧率上限由观感与 BLE 共存风险决定，不由带宽决定。**

## 3. `mem_block_symbols` 与通道数的取舍

C3 的 RMT 只有 **2 个 TX 通道可用**（`RMT_LL_TX_CANDIDATES_PER_INST = 2`，
v6.1 已确认），整个 group 共 **4 × 48 = 192 word**，无 DMA。

**关键推论（`[算]`，也是 v2 架构的基础）**：8 条灯带走 TDM —— 用
`led_strip_switch_gpio()` 在运行时切换输出引脚，**只占用 1 个 TX 通道**。
因此不存在「8 条要 8 个通道」的问题，也不需要把 192 word 分给多个通道。

由此得到 `mem_block_symbols` 的取舍：

| 取值 | 申请块数 | 可行性 | 说明 |
|---|---|---|---|
| 48 | 1 | ✅ | v1 产品默认值 |
| 96 | 2 | ✅ | |
| **192** | **4** | ✅ | **占满整组，TDM 单通道下可用** |
| 384 | 8 | ❌ | 无 8 个连续块，`led_strip_new_rmt_device` 失败 |

**v2 的推荐值是 192**：一次 ISR 补满整组，中断次数最少，是无 DMA 条件下
「最不容易被 BLE 拖坏」的配置；代价是整组被占满（本项目没有其它 RMT 用户）。

**这一条是推导，不是实测。** 因此：

- **v2 产品固件默认值暂不改动**（仍是 48），避免在无数据的情况下改变现场行为。
- [#29](https://github.com/sishoui/light-matt/issues/29) 的 8 路构建必须把 192 作为
  对照档跑一遍，实测后才改默认值。
- 若 192 的错色率与 48 无差别，改与不改都不影响观感，届时以「中断次数少、CPU 占用低」为准。

## 4. 交给 #22 的四条输入

1. **默认帧率 10 fps，构建期可配**（`Kconfig`，区间 5–30）。
   依据：带宽上界 57 Hz > 10 fps；10 fps 用掉 17.6% 带宽，留出余量吸收 BLE 抢占后的追赶。
   帧率必须可配，以便真机数据出来后调参而不改结构。
2. **TDM 只占 1 个 RMT TX 通道**；8 路轮询由 `led_strip_switch_gpio()` 实现，
   不申请 8 个通道（C3 也给不了）。
3. **静态段不参与帧循环**：只有存在活动动画段或剧本在播放时才进入定时刷帧；
   否则回到 v1 的「状态变了才刷」。这是「静态不空转」的判据，
   也是避免「为了动画把静态场景的 BLE 共存风险无谓放大」的关键。
4. **错色风险保持开放**，不要因为带宽够就认为共存没问题。真机出现
   「偶发闪一下 / 单颗灯变色」时，第一嫌疑是 BLE 抢占 RMT ISR，
   排查入口是 `rmt-ble-stability.md` 的五组实验（8 路版本由 #29 扩展）。

## 6. #29 交付后的状态（2026-10-31）

TDM 多灯带已经实现并能在 host 上测调度逻辑，但**没有任何 8 路真机数字**——
手上只有一条灯带（COM6）。本条记录「已经能测什么」与「还差什么」。

### 已实现（可在 host 上验证）

- `strip_planar.c`：8 条的引脚/灯珠数/降级状态 + 轮询顺序。
  `lumen_planar_next()` 严格轮转，跳过降级条；全部降级时返回 `LUMEN_PLANAR_NONE`
  而不是死等。host 测试覆盖解析、校验、轮转、降级隔离、统计聚合。
- 一条灯带判定失败（`led_strip_switch_gpio` 或 `refresh` 返回错误）后标降级、
  串口只打一次警告，其余条继续——这就是「一条不接不影响其它 7 条」的实现方式。
  **注意 WS2812B 不会回报自己是否在线**，所谓「不接」只能表现为句柄/刷新失败；
  物理上拔掉一条灯带但引脚仍在时，固件**无法感知**（会继续发送，那条灯带只是不亮）。
- `mem_block_symbols` 保持 48 默认值；TDM 只占 1 个通道，所以 192 是可行的
  推荐值（见 §3），但**仍按推导而非实测**，没有改默认值。

### 还需真机才能得到的数字（本文件 §1 的 `[未测]` 行）

拿到 8 条灯带后按下面步骤补，完成后把结果回填 §1/§2：

```
1. 接线：8 条灯带数据脚分别接 CONFIG_LUMEN_STRIP_PINS 列出的引脚，
   全部共地；灯带独立 5V 供电（不要从开发板取电）。
2. menuconfig 设 LUMEN_STRIP_PINS="3,4,5,6,7,10,20,21"（或实测可用引脚），
   LUMEN_RMT_MEM_BLOCK_SYMBOLS 保持 48，先跑一轮。
3. 烧录，串口看 "tdm: strips=8 active=8 round=<N>us avg=<N>us"。
   每 60 轮打一行；round 就是「8 路轮询一轮」的实测周期。
   - 解析预期（64 灯 × 8 条）：≈17.6ms，每条 ≈57Hz。
   - 若实测 round 远大于 17.6ms，说明 GPIO 切换或驱动开销不可忽略，
     把数字回填 §2 并重新评估 10fps 目标。
4. 给 8 条各设不同颜色（小程序分段界面按 strip 分别下发），拍照确认。
5. 拔掉其中一条的数据线，确认其余 7 条继续正常、串口只出现一次降级警告。
6. 断电重启，确认 8 条各自的颜色与灯珠数恢复。
7. 跑 §3 的 BLE 三态（未连 / 空闲 / 20Hz 写入）录像数错色，
   这一项是 #20 遗留的开放风险，8 路条件下从未测过。
```

在 3 与 7 拿到数字之前，**不要**把 §1 的任何 `[未测]` 行改成 `[测]`。
