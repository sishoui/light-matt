## 0. 前提（来自地图 Notes，已定）

- 灯效渲染在**固件**，小程序只下发「类型 + 参数」。
- 灯效建模 = **类型枚举 + 定长参数块**，不做设备端脚本。
- 首批四种：**静态单色、呼吸、彩虹、流光**。
- 一条灯带最多 **8 段**，8 条灯带走 TDM 轮询。
- **逐段下发**，每帧一个段，帧 ≤ 20 字节。
- 亮度上限 `max_brightness = 200`（State 第 7 字节报给小程序）。
- 亮度是**独立字段**，不折进 RGB；gamma 只存在于固件（`lumen_gamma_apply`）。

## 1. 设计决策（每条都标了「未确认」）

| # | 决策 | 取值 | 状态 |
|---|---|---|---|
| D1 | 参数组织方式 | **统一 6 字节**，所有灯效共用同一块 | ⚠️ 未确认 |
| D2 | 色相精度 | **2 字节**（0-65535，一整圈 ≈ 65536 级） | ⚠️ 未确认 |
| D3 | 速度单位 | **频率 ×10，1 字节**（0-255 → 0-25.5 Hz） | ⚠️ 未确认 |
| D4 | 流光跨段相位 | **每段独立相位**（跨段会断裂） | ⚠️ 未确认 |
| D5 | 饱和度体系 | HSV 的 S（0-255），V 恒为满、亮度只走滑块 | 沿用 MVP 既有约定 |
| D6 | 未知灯效类型 | **回 `InvalidParam`，不静默降级**（见 §5 说明） | 已定 |

**为什么统一 6 字节**：逐段下发时帧长固定（6 字节信封 + 1 段号 + 1 类型 + 6 参数 = 14 字节，正好在 20 字节内且留 6 字节余量）。若每灯效参数长度不同，段配置帧的可变长会让校验和长度检查分叉，而 v1 已经证明固定长度最省心。

**D1 的代价**：呼吸的「最小亮度」、流光的「尾部长短」这类专属参数表达不出来。它们被压缩成统一参数的解释方式（见 §3）。如果实测发现表达力不够，升 v2 内再讨论，不动帧结构。

## 2. 参数块布局（6 字节）

所有灯效共用，按小端：

| 偏移 | 字段 | 宽度 | 含义 |
|---|---|---|---|
| 0-1 | `hue` | 2 | 色相 0-65535 = 0-360°，小端。65535 与 0 相邻（环形） |
| 2 | `sat` | 1 | 饱和度 0-255（0 = 白，255 = 纯色） |
| 3 | `rate` | 1 | 速度，**频率 ×10 Hz**，0 = 静止 |
| 4 | `level` | 1 | 灯效强度 0-255，**含义按类型解释**（见 §3） |
| 5 | `flags` | 1 | 位域，见下 |

### flags 位域

| 位 | 名称 | 含义 |
|---|---|---|
| 0 | `reverse` | 方向反转（流光从尾向头、彩虹色相递减） |
| 1-2 | `waveform` | 仅呼吸：0 = 正弦，1 = 三角，2 = 锯齿，3 = 方波（软起软落） |
| 3-7 | 保留 | 必须为 0；非 0 时设备回 `InvalidParam` |

### `rate` 的取值范围与安全上限

`rate` 编码的是**完整周期频率 × 10**：

| rate | 频率 | 周期 | 用途 |
|---|---|---|---|
| 0 | 静止 | — | 静态/固定相位 |
| 1-10 | 0.1-1.0 Hz | 1-10 s | 慢呼吸、慢彩虹 |
| 11-30 | 1.1-3.0 Hz | 0.33-0.9 s | 正常呼吸、中速流光 |
| 31-50 | 3.1-5.0 Hz | 0.2-0.32 s | 快流光（**上限**） |
| 51-255 | > 5 Hz | < 0.2 s | **设备回 `InvalidParam`** |

**3 Hz 是闪烁安全线**（通常建议 ≤ 3 Hz 避免光敏性癫痫），但要区分「亮度闪烁」与「空间流动」：流光 5 Hz 是空间移动，不是亮度闪烁，相对安全。**呼吸（亮度整体起伏）严格限制 ≤ 3 Hz**，即 `rate ≤ 30`。这个区分写进校验：

- 灯效 = 呼吸 → `rate > 30` 回 `InvalidParam`
- 灯效 = 彩虹 / 流光 → `rate > 50` 回 `InvalidParam`

## 3. 四种灯效的精确行为

约定：`t` 是该段的本地时间（秒，从该段**最近一次配置生效**起算）。`phase = (t × rate_freq) mod 1`，`rate_freq = rate / 10`（Hz）。`rate = 0` 时 `phase = 0`。

色相到 RGB 用 `hsvToRgb(hue_deg, sat/255, 1.0)`，**V 恒为 1**，之后再 `lumen_gamma_apply(channel, brightness)`。这与 MVP 小程序侧 `hsv.ts` 的约定一致，固件需要一份等价的整数实现。

### 3.1 静态单色（type = 0x00）

```
每颗灯：hue, sat → RGB（V=1）
rate 忽略；level 忽略
```

这是 MVP 现有能力的等价物，也是「关掉动画、只设颜色」时的目标形态。

### 3.2 呼吸（type = 0x01）

```
包络 e ∈ [0, 1]，由 flags.waveform 决定：
  正弦  e = 0.5 × (1 - cos(2π × phase))          // 从暗到亮再回暗
  三角  e = 1 - |2 × phase - 1|
  锯齿  e = phase
  方波  e = phase < 0.5 ? 1 : 0，但两端各留 10% 做线性斜坡（软起软落）
每颗灯：RGB × e
```

- `level` 在这里 = **最暗时的亮度占比**（0-255 → 0-100%）。`level = 0` 时暗到全黑；`level = 255` 时几乎不呼吸。
- 实际包络 `e' = level/255 + (1 - level/255) × e`。
- **频率上限 3 Hz**（`rate ≤ 30`），超过回 `InvalidParam`。

### 3.3 彩虹（type = 0x02）

两种铺法，由 `flags.reverse` 之外再借 `level` 区分（因为统一参数块没有专属字段）：

```
level = 0        → 整条同色循环（所有灯同色，色相随时间转）
level = 255      → 沿灯带铺满一整圈（第 i 颗的色相 = i/N × 360°），随时间平移
0 < level < 255  → 线性插值：色相空间跨度 = level/255 × 360°
```

灯 i 的色相：

```
hue_i = hue_base + phase × 65536 + (i / N) × (level / 255) × 65536 × (reverse ? -1 : 1)
```

- `sat` 直接作为饱和度。
- 色相计算用 32 位整数 + 取模，**不用浮点**（C3 无 FPU，浮点会拖慢帧循环）。
- 频率上限 5 Hz（`rate ≤ 50`）。

### 3.4 流光（type = 0x03）

```
亮点的位置随 phase 沿灯带移动，尾部按指数衰减。
level = 尾部长度：0 = 无尾（硬边亮点），255 = 整条都是尾
```

单颗灯 i 的亮度系数：

```
p      = (i / N - phase) mod 1          // 亮点在 i 处时为 0
tail   = 1 + (level / 255) × (N - 1)    // 尾部覆盖的灯珠数，1..N
w      = p < tail/N ? exp(-p × N / tail × 3) : 0   // 指数衰减，3 是衰减常数
RGB_i  = hsvToRgb(hue, sat, 1.0) × w
```

- `reverse` 反转移动方向。
- **每段独立相位**（D4）：段的 `t` 从该段配置生效时起算，跨段不连续。
- 频率上限 5 Hz。

## 4. 与分段、gamma、电流预算的交互

### 4.1 分段

- 每个段独立持有：`type + 6 字节参数 + 段生效时间戳 + 灯珠区间`。
- 段之间的**相位互相独立**（D4）。
- **未被任何段覆盖的灯珠**必须熄灭（写 0），不保留上一帧内容。这是避免「残影」的必要条件——WS2812B 会锁存，不主动写 0 就一直亮着。

### 4.2 gamma 与亮度

- 灯效算出的 RGB 是**用户空间**（0-255）。
- **最终输出 = `lumen_gamma_apply(rgb_channel, brightness)`**，与 MVP 完全一致。
- 亮度滑块与灯效亮度**相乘叠加**：动画的包络改的是用户空间值，滑块再统一缩放。这样拖亮度不会破坏灯效的相对亮度关系。

### 4.3 电流预算（重要，尚未解决）

`max_brightness = 200` 是按**静态纯白 64 灯**定的（约 3.0A）。动画风险更高：

- 彩虹/流光可能让**大量灯珠同时处于高亮**，而静态单色时全白是最坏情况。
- **8 条灯带时电流 ×8**，供电方案必须重新设计。

本票只定规格，**不定电流上限**。需要实测（#20）后再决定是否给「动画模式」单独降 `max_brightness`。如果过早固定，会因为不敢给足亮度而牺牲观感。

**在实测结论出来前，固件应保守**：动画模式下把 `max_brightness` 临时乘一个系数（建议 0.75），并把这个行为**报给小程序**（可通过 State 的 `max_brightness` 字段动态反映）。

## 5. 校验规则（设备侧）

按顺序检查，任一失败回对应错误码，整帧不生效：

| 检查 | 条件 | 结果 |
|---|---|---|
| 类型已知 | `type ∈ {0x00, 0x01, 0x02, 0x03}` | 否则 `InvalidParam`（未知类型与未来新增类型都不降级） |
| flags 保留位 | bit 3-7 == 0 | 否则 `InvalidParam` |
| 呼吸频率 | `type=0x01` 且 `rate > 30` | `InvalidParam` |
| 其它频率 | `type ∈ {0x02,0x03}` 且 `rate > 50` | `InvalidParam` |
| 段区间 | `start ≤ end < led_count` 且 `end - start + 1 ≥ 1` | 否则 `InvalidParam` |

**关于「未知类型」的处理**：**回 `InvalidParam`，不做静默降级。**

理由：静默降级会让用户看到「以为设置成功但效果不对」，比明确报错更难排查。这条同时覆盖两种情况——类型不在枚举里，以及未来新增类型旧固件不认识。两者都应让用户知道「这个灯效设备不支持」，小程序据此提示升级固件。

## 6. 固件实现要点（给 #22 的输入）

- **整数运算**：色相/相位/包络全部用 32 位整数与定点数，不用 `float`（C3 无 FPU）。`gamma.c` 现在用 `math.h`，但只在初始化时算一次表，运行时用查表，没问题。
- **每段状态**：`{ uint16_t hue; uint8_t sat, rate, level, flags; uint8_t type; uint16_t start, end; uint32_t t0_ms; }` ≈ 14 字节。8 段 ≈ 112 字节。8 条灯带 × 8 段 ≈ 900 字节，RAM 可接受。
- **相位计算**：`phase = (((now_ms - t0_ms) * rate) / 10000) mod 65536`。单位核对：`rate` 是 0.1 Hz，即 `rate/10` 周期每秒；`(ms × rate) / 10000` = `ms × rate / 10 / 1000` = 经过的**周期数**，正确。注意 32 位溢出：`(now_ms - t0_ms) * rate` 最大约 `(49天ms=4.2e9) × 255` 会溢出 int32，**必须用 `uint64_t` 中间量**。或者先把 `dt_ms` 对 10000/gcd 取模再乘，但用 uint64 更简单可靠。
- **未知类型不写像素**：保持上一帧，避免闪黑。注意这与 §5「回 InvalidParam、整帧不生效」一致——不生效 = 不改该段，自然保持原样。
