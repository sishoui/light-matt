#### 供电（这次踩过的坑，务必记住）

**灯带必须独立 5V 供电，只与开发板共地。** 首次接线时开发板 5V 引脚只量到
**0.3V**，灯带完全不亮；换成独立供电后才正常。64 灯全白约 3.8A，开发板 USB
5V 通常只给 500mA–1A，根本带不动。

如果灯带又不亮，按这个顺序查：
1. **独立电源是否接上、是否通电**（万用表量灯带端子 5V–GND）
2. **共地**（开发板 GND 与灯带电源 GND 必须直连）
3. **DIN 接 GPIO3**（不是 DOUT 端，箭头指向远离开发板）
4. 用 `scripts\build-led-bringup.cmd` + `scripts\flash-led-bringup.cmd COM6`
   单独验证（不依赖 BLE，开机就跑 红→绿→蓝→白）

### 0.3 烧录与启动

```bat
scripts\build-firmware.cmd
scripts\flash-firmware.cmd COM6
```

串口应出现：

```
lumen_ble: GATT 服务已注册（Service 6c756d65-...-0001，RX/TX/State）
lumen_ble: 开始广播（Lumen-XXXX），等连接
lumen_app: 初始化完成：NVS → state_store → led_engine → ble_link
```

> 需要看原始帧字节时，把日志级别调到 DEBUG

> 产品路径每帧只打一行 RX 汇总，这是为了不让串口本身拖慢 20Hz 写入。

## 1. 七条清单（逐条记录）

> **验证分层**：带「固件侧」的结论由 `scripts/acceptance-probe.py` 用 PC 当 central

### ① 小程序扫到设备并连上，MTU 协商成功或优雅降级

**操作**：打开小程序 → 点顶部连接条 → 扫描 → 点 `Lumen-XXXX`。

**应观察到**：
- 列表里出现 `Lumen-XXXX`（XXXX = 设备蓝牙 MAC 后两字节）与 RSSI
- 状态条依次显示「扫描中…」→「连接中…」→「已连接 · Lumen-XXXX」
- Android 串口打印 `mtu updated=256` 左右；iOS 跳过 `setBLEMTU` 且不报错

**固件侧（已验证）**：广播名 `Lumen-5662`，广告含 Service UUID
`6c756d65-...-0001`，RSSI -62。连接后 `mtu=23 → mtu updated=256`，
串口 `TX notify enabled`。GATT 服务下 RX/TX/State 三个特征齐全。

| 结果 | 现象 / 日志 |
|---|---|
| 固件侧 ☑ 通过　小程序侧 ☑ 通过 | 广播/连接/MTU/特征齐全已实测；小程序侧经真机确认 |
| 串口： | `lumen_ble: mtu updated=256` / `TX notify enabled` |
| 小程序日志： | 连接后读 State 正常（见 ⑦ 首行 `State read power=1 brightness=84 rgb=255,255,255 leds=64`） |
| 已知限制 | 断开后点状态条**直接重连缓存设备**，不再展示设备列表（`onStatusTap` 里缓存命中走 `manualReconnect`）。这是最快路径，但用户无法主动选另一台设备。见「已知限制」表 |

### ② 开关按钮能亮灭灯带，回包 ACK 序号正确

**操作**：点大开关按钮，再点一次。

**应观察到**：
- 灯带在可感延迟内亮/灭
- 串口每帧一行：`RX cmd=0x01 seq=0x01 len=1 result=0x00 power=1 ... changed`
- 小程序协议日志里 `ACK` 的 seq 与请求一致

**按 seq 对齐方法**：串口 `seq=0x01`，小程序面板显示 `seq=1 (0x01)`，两者应逐帧对应。

**固件侧（已验证）**：`SetPower(1)` → `ACK cmd=0x01 seq=0x01 result=OK`；
`SetPower(0)` → `seq=0x02 result=OK`。seq 逐帧回显，无跳号。
非法值 `SetPower(2)` → `0x01 InvalidParam`，状态不变。

| 结果 | 现象 / 日志 |
|---|---|
| 固件侧 ☑ 通过　灯带亮灭 ☑ 通过 | ACK seq 正确；灯带亮灭经用户确认 |
| 串口末行： | `RX cmd=0x01 seq=0x02 len=1 result=0x00 power=0 ...` |
| 小程序 ACK 行： | 待填 |

### ③ 拖动亮度滑块灯带实时跟随，无可感延迟

**操作**：缓慢拖动亮度滑块一个来回，再快速来回拖三次。

**应观察到**：
- 灯带随手指连续变化，松手不跳变
- 快速拖动**不排队重放**中间值（latest-wins）
- 串口不出现大批 `ACK notify 失败` 或 `10008`

**固件侧（已验证）**：30ms 间隔连发 20 帧亮度（模拟快速拖动），
20 帧全部回 ACK 且全为 `result=OK`，串口无 `notify 失败`。
结束值落在最后一个下发值（30），说明 latest-wins 没有排队重放中间值。

| 结果 | 现象 |
|---|---|
| 固件侧 ☑ 通过　手感 ☑ 通过 | 20 帧 ACK 全收，最终值正确；用户确认跟手、快速拖动不卡、松手不跳变 |
| 快速拖动时的表现： | 跟手，不卡，松手不跳变（用户确认） |

### ④ 色环选色后灯带颜色正确、无偏色

**操作**：点色环上的红、绿、蓝三处；再点几个预设色块；最后把亮度拖到很低再选深红/深蓝。

**应观察到**：
- 色环选红 → 灯带红；绿 → 绿；蓝 → 蓝（若红绿互换，先回去做 §0.2 第 1 条）
- 预设点击即生效，无中间态跳变
- 低亮度下色相仍正确（暗红不发棕、暗蓝不发灰）

**固件侧（已验证）**：
- 自检渲染日志严格按 `红(255,0,0) → 绿(0,255,0) → 蓝(0,0,255) → 白(255,255,255)`
  各 500ms 输出，结束后恢复存储状态——**通道顺序 GRB 在固件侧成立**
- `SetColor` 三个分量原样落地：红/绿/蓝存储值与下发逐字节一致
- 亮度 16 下选深红 `(128,0,0)`、深蓝 `(0,0,128)`：RGB 未被亮度污染，
  `brightness=16` 独立存放（协议 §7 / #10 的「亮度不折进 RGB」）

**人眼实测（2026-10-30，真机）**：
- 色环红/绿/蓝 → 灯带对应颜色正确；低亮度深红不发棕、深蓝不发灰
- **自检第 4 色实测是「黄」，不是「白」**。固件日志确认下发的是
  `rgb=255,255,255`，`gamma(255)=255`，三通道等值——**不是固件或通道顺序问题**。
  黄 = 红 + 绿，即蓝通道在满功率时塌了：64 颗同时全白约 3.8A，蓝光 LED 的
  Vf 最高（≈3.2V），独立 5V 电源/线损撑不住时它最先掉压。
  这正是 §0.2 里「全白掉压」那条一直没测的已知风险，现在有了实测结论。

**供电改 5V 后复测（2026-10-30）**：白色在**中高亮度已正常**，但仍有色偏——
**低亮度偏紫、高亮度偏黄**。固件侧逐档扫描纯白，确认输出严格等值：

| brightness | 4 | 8 | 16 | 32 | 64 | 128 | 255 |
|---|---|---|---|---|---|---|---|
| R=G=B | 4 | 8 | 16 | 32 | 64 | 128 | 255 |

所以偏色与 gamma / 亮度算法无关（三通道走同一条代码路径，纯白必然等值）。
两个方向相反的偏色指向 LED 本身的通道差异：

- **WS2812B 三个通道的正向压降不同**：红/绿 ≈2.0–2.2V，蓝 ≈3.0–3.4V。
- **低亮度偏紫**：单灯电流小（亮度 16 时 64 灯仅约 0.24A），线路压降可忽略，
  蓝通道按 Vf 反而更容易导通到充分；同时低位量化在低电流下对蓝绿差异更敏感。
- **高亮度偏黄**：电流大（亮度 255 时约 3.8A），线损与电源内阻的压降把
  Vf 最高的蓝通道先吃掉，红+绿占优 → 黄。

**这是器件+布线的电气特性，不是固件 bug。** 要真正消除得从硬件下手（两端供电、
加粗线、更大的首灯电容），或接受它作为 64 灯大功率灯带的固有表现。

| 结果 | 现象 |
|---|---|
| 固件侧 ☑ 通过　颜色/低亮度 ☑ 通过 | 红绿蓝与低亮度色相均正确 |
| 自检第 4 色 / 纯白 | 3.3V 供电时显黄；改 5V 后中高亮度正常，**低亮度偏紫、高亮度偏黄** |
| 红/绿/蓝实际颜色： | 正确（用户确认） |
| 低亮度色相： | 深红不发棕、深蓝不发灰（用户确认） |
| 纯白偏色的根因 | 通道 Vf 差异 + 大电流下线损，非固件；见上表 |

### ⑤ 断线后自动回连并恢复 UI 状态

**操作**：给设备断电，等 10 秒，再上电。

**应观察到**：
- 断电后状态条变「未连接」，**不保留旧的开关/亮度显示**
- 上电后按 1s / 2s / 4s 退避自动回连
- 回连成功后 UI 显示设备真实状态（不是断线前的缓存）
- 回连后点开关仍能收到 ACK（notify 重新订阅生效）
- 三次退避都失败时显示「未连接」并出现手动「重连」/「扫描」入口，**不无限重试**

**固件侧（已验证）**：中心主动断开后 **4.0s 内重新开始广播** `Lumen-5662`，
再次连接成功且 `mtu=256`（notify 需重新订阅，符合协议「断开后重新广播」）。
退避序列在代码里是 `[1000, 2000, 4000]` ms，有 `reconnect.test.ts` 34 个用例覆盖。

**人眼实测（2026-10-30，真机）**：断电后状态条变「未连接」，旧显示被清掉；
上电后自动回连、显示设备真实状态。**但第一次实测时上电后灯带不亮，要开关一次
才亮**——那是 ⑥ 的问题（上电首帧被灯带电源建立窗口吃掉），已修，详见 ⑥。

| 结果 | 现象 |
|---|---|
| 固件侧 ☑ 通过　UI ☑ 通过 | 断开后 4s 内重新广播、可回连；UI 表现经用户确认 |
| 断线到显示未连接的延迟： | 即时变「未连接」（用户确认） |
| 回连成功时间： | 自动回连，无需手动 |

### ⑥ 断电重启后颜色/亮度/开关恢复

**操作**：设置成开灯、亮度约 80、颜色紫色 → 等 2 秒（让 debounce 写入）→ 拔电 → 重新上电。

**应观察到**：
- 重新上电后灯带恢复紫色、亮度约 80、开灯状态
- 若设备是**首次**上电（NVS 无历史），应处于关灯、亮度 128、暖白 RGB(255,180,120)

**另测灯珠数量**：在设备弹层把数量改成 10 → 只有 10 颗亮 → 重启后仍是 10 颗。
填 0、65、字母 → 应被明确拒绝且保留旧值。

**固件侧（已验证）**：
- 写入 `power=1 brightness=80 rgb=128,0,128` → 复位 → 启动日志
  `state restored: power=1 brightness=80 rgb=128,0,128 leds=64 max=255`，逐字段一致
- 数量改 10 → **重启后仍 `leds=10`**（NVS 持久化成立），再改回 64
- 边界：`SetLedCount(0)` 与 `SetLedCount(65)` 均回 `0x01 InvalidParam` 且保留旧值；
  合法区间 1-64 由 `ledCount.test.ts` 覆盖（含字母/小数/空串的前端拒绝）
- 数量减少路径的完整串口序列：`RX cmd=0x06 → 已排队 → rebuild begin: 10 leds
  → render x10 → led count -> 10 → ACK`

**人眼实测（2026-10-30，真机）——发现一个真 bug，已修**：

首次实测：断电再上电后**灯带是灭的**，必须把开关关一次再开才恢复上次颜色。
这是缺陷，不是正常现象：`state restored` 只证明状态从 NVS 读回来了，
不证明像素真的送进了灯带。

**根因**：启动日志里首帧 `render` 在 **325ms** 就发出去了，而灯带是独立 5V 供电，
它的电源建立可能晚于 MCU 就绪，WS2812B 收不到这一帧就整帧丢弃。随后
`s_rendered_valid` 已被置位，只要状态不变就再也不会重发——于是灯一直黑着，
直到用户碰一次开关触发状态变化。

**修复**（`led_engine.c`，`LUMEN_BOOT_REASSERT_COUNT` / `..._INTERVAL_MS`）：
上电后头 4 次渲染跳过「像素未变就跳过」的去重，按 200ms 间隔强制重推，
把窗口覆盖到约 1s。烧录后启动日志变成：

```
I (325) render: (0,15,0) x 64 brightness=15 power=1
I (525) render: (0,15,0) x 64 …
I (725) render: (0,15,0) x 64 …
I (925) render: (0,15,0) x 64 …
```

**教训（与 §3.3 同类）**：状态恢复正确 ≠ 像素送出去了。断电恢复类验收必须
看**灯带有没有亮**，不能用 `state restored` 的日志代替。

| 结果 | 现象 |
|---|---|
| 固件侧 ☑ 通过　人眼 ☑ 通过 | 状态/数量恢复正确；上电不亮已修并复核 |
| 恢复的颜色/亮度/开关： | `power=1 brightness=80 rgb=128,0,128`（与写入一致） |
| 灯珠数量： | 改 10 → 重启仍 10；0/65 被拒并保留旧值；已恢复 64 |
| 修复后复核（2026-10-30） | 断电 → 上电，不动手机，灯带直接亮回上次颜色　**通过** |

`log.test.ts` / `log-panel.test.ts` / `describe.test.ts` 覆盖。

| 结果 | 现象 |
|---|---|
| 代码侧 ☑ 通过　面板实机 ☑ 通过 | 缓冲/暂停/共用 formatter 有单测；真机面板字段完整、三个按钮均可用 |
| 日志样例： | 见下（真机复制出来的原文） |

真机实测的日志片段（`->` 是小程序发出的，`<-` 是设备回报的）：

```
20:43:58.479 <- 01 54 FF FF FF 40 00 FF | - seq=- | State read power=1 brightness=84 rgb=255,255,255 leds=64 max=255
20:44:49.737 -> A5 01 03 01 03 FF FF FF 55 | SetColor seq=1 (0x01) | SetColor rgb=255,255,255
20:44:49.787 -> A5 01 03 02 03 FF FF FF 54 | SetColor seq=2 (0x02) | SetColor rgb=255,255,255
20:44:49.806 <- A5 01 80 01 02 03 00 D3 | ACK seq=1 (0x01) | ACK SetColor cmd=0x03 result=0x00 OK
20:44:49.835 <- A5 01 80 02 02 03 00 D2 | ACK seq=2 (0x02) | ACK SetColor cmd=0x03 result=0x00 OK
20:44:49.838 -> A5 01 03 03 03 FF FF FF 53 | SetColor seq=3 (0x03) | SetColor rgb=255,255,255
20:44:49.895 <- A5 01 80 03 02 03 00 D1 | ACK seq=3 (0x03) | ACK SetColor cmd=0x03 result=0x00 OK
```

一段同时证明了四件事：

1. **时间戳 / 方向 / hex / 解析名 / 参数**五种信息齐全（`seq=` 同时给十进制与 hex）
2. **ACK 的 seq 与请求逐帧对应**：发 `seq=1` 收 `seq=1`，发 `seq=2` 收 `seq=2`
3. **校验和正确**：`A5 01 03 01 03 FF FF FF` → sum=`0xAA` → checksum=`0x55`，
   与协议 §3 的示例完全一致；其余各帧的校验和也逐条核对无误
4. **State read 是裸的 8 字节**（不是协议帧，没有信封和校验和），解析正确：
   `01 54 FF FF FF 40 00 FF` = power=1 brightness=0x54=84 rgb=(255,255,255)
   leds=0x0040=64 max=255。解析器把裸字节与带信封的帧区分开了。

暂停 / 清空 / 复制三个按钮均实测可用。

## 4. #25 多分段静态灯效（待真机执行）

本票是 v2 的第一个端到端纵切：`SetSegment 0x10` / `ClearSegment 0x11` /
`QueryStrip 0x12` → 固件段存储 → 按区间合成 → 断电恢复 → 小程序分段界面。

**已由 host 测试覆盖的部分**（`firmware/test/run-tests.cmd`，无需硬件）：

- 三段不同颜色合成后段内均匀（段 0 纯红、段 1 纯蓝、段 2 纯绿，逐颗断言）；
- **未覆盖区必须为 0**：先往缓冲里填脏数据，再 `compose`，断言 16-19 / 30-39 全 0；
- 改一段颜色后其它段逐字节不变；
- 重叠 / 越界 / start > end / 未知 type / 载荷长度不符 → 拒绝，旧配置不变；
- NVS blob v2 往返（含段表）、坏 magic / 版本 / 段表自相矛盾 → 回默认值；
- `SegmentReport` / `SegmentListEnd` 编码逐字节与向量一致。

**以下只能真机确认**（host 测试无法替代）：

### 4.1 准备


小程序：微信开发者工具导入 `miniprogram/`，真机预览。硬件同 §0.2（64 灯独立 5V 供电、共地）。

### 4.2 三段不同颜色（ticket 第 2 条）

1. 设备弹层把灯珠数量设为 **64**。
2. 分段区依次新建三段（每段选颜色后再点「新建区间」）：

### 4.3 空白区间必须真暗（ticket 第 3 条，本票的核心验收点）

这一段是**专门用来抓「没写 0 就留残影」的**：

1. 先建一个大范围段（例如 `0` – `63`）并设成亮白，让**整条**灯带都亮起来；
2. 把该段删掉（「删除」按钮 → `ClearSegment 0x11`）；
3. 建两段：`0` – `15` 与 `40` – `63`（任意两种颜色）；
4. **近距离肉眼确认 16-39 号灯珠是完全熄灭的**（不是暗光、不是残影、不是旧色）。

5. 串口 `render seg:` 行里 `n=64`；由于 16-39 是 0，整条电流明显低于全亮。

证据：录像（从「全亮」到「删除后只剩两段」的完整过程），或两张照片对比。

保持 4.2 的三段，只把段 1 从蓝改成橙（点预设或色环）。

观察：段 0 与段 2 **不闪、不变色**；串口只出现一次 `SetSegment ... seg=1`，
`render seg:` 行的首/中/末抽样里段 0 与段 2 的颜色不变。

### 4.5 断电恢复（ticket 第 5 条）

1. 保持 4.2 的三段配置；
2. 等 ≥ 1s（500ms debounce + 余量），让 NVS 写完；
3. 直接拔开发板电源，再上电；
4. 观察：三段颜色与区间**全部恢复**；串口首行是 `state restored: ... segs=3`。

证据：录像（断电 → 上电 → 三段恢复）。

### 4.6 重叠被拒（ticket 第 6 条）

在已有 `0` – `15` 的情况下，新建 `10` – `20`：

- 小程序本地预检就会拦下（提示「与段 0（0-15）重叠」）；

## 5. #30 呼吸灯效（待真机执行）

**本票在无硬件环境完成**：只跑了 host 测试（3866 项）、小程序 vitest（239 项）、
`tsc --noEmit` 与固件构建（66% free）。以下步骤**必须在真机上执行**才算通过。

### 5.1 准备

构建并烧录（`CONFIG_LUMEN_ANIM_FPS` 默认 10，可在 `menuconfig` 调到 5-30）：

```cmd
scripts\build-firmware.cmd
scripts\flash-firmware.cmd COM6
scripts\capture-serial.py           :: 或任意串口工具，115200
```

小程序：同一份 `miniprogram/`，设备弹层把灯珠数量设为 **64**。

### 5.2 设置一段呼吸（ticket 第 1、2 条）

1. 分段区划区间 `0` – `29`，点「新建区间」。
2. 在「灯效」区切到**呼吸**；周期保持 1000ms、最暗 0%、波形正弦；点「应用到选中段」。
3. **观察**：该段亮度呈正弦周期变化（约 1 秒一个完整周期），不是静止色。
4. 把周期改成 **334ms** 再应用：明显更快（约 0.33s 一个周期，≈3Hz）。
5. 把周期改成 **3000ms** 再应用：明显更慢。
6. 串口证据：
   - 出现 `SetSegment strip=0 seg=0 [0-29] type=0x01 ...`；
   - 出现 `帧循环模式 -> 动画（fps=10）已绘制=... 跳过=...`；
   - `render seg: ... frame=N ...` 每 10 帧一行持续增长。

证据：录像（334ms 与 3000ms 两个周期各 5 秒）。

### 5.3 min_level 极值（ticket 第 3 条）

1. 最暗 = **0%**，周期 1000ms：谷底必须**完全熄灭**（不是暗灰）。近距离看段内首灯。
2. 最暗 = **80%**（0.8 × 255 ≈ 204）：只剩很浅的呼吸，肉眼几乎恒定。
3. 最暗 = **100%**：恒定满亮，**完全不呼吸**。
4. 串口 `render seg:` 的 `[0]=` 抽样在 5.2 的谷底应为 `0,0,0`。

### 5.4 四种波形可分辨（ticket 第 4 条）

同一段依次切正弦 / 三角 / 锯齿 / 方波，周期都用 1000ms：

| 波形 | 应看到 |
|---|---|
| 正弦 | 平滑起伏，拐点圆润 |
| 三角 | 线性上升/下降，尖端明显 |
| 锯齿 | 线性上升后**瞬间**归零（有跳变） |
| 方波 | 高亮停留约 40% 周期，两端各有约 0.1 周期斜坡，无硬跳变 |

证据：录像。四种波形必须有肉眼可区分的亮度轨迹。

### 5.5 周期下限被拒（ticket 第 5 条，配置不变）

1. 小程序构造层会在本地拦下 < 334ms（`cmdSetSegment` 抛 RangeError），所以正常 UI 走不到设备。
2. 绕过 UI 直接发向量帧 `A50210220C0001000901100EFF4D01600044`（period 333）：
   - 设备回 `ACK SetSegment result=0x01 FAIL`；
   - 串口 `SetSegment 被拒 ... result=0x01`；
   - **该段保持上一次成功的配置**（不是变黑、不是变成 333ms）。
3. 对照：把同一帧的 period 字节改成 334（`A50210220C0001000901100EFF4E01600043`）→ `0x00`。

### 5.6 一段呼吸 + 一段静态共存（ticket 第 6 条）

1. 段 0：`0` – `29` 呼吸（红色基色，周期 1000ms）。
2. 段 1：`40` – `63` 静态绿。
3. **观察**：0-29 脉动，40-63 **绝对不闪、不变色**；16-39（未覆盖）永远熄黑。
4. 串口：`render seg:` 的 `[63]=` 抽样（末灯，属于静态段）在每个 `frame=` 上都相同。

### 5.7 手机断开后呼吸继续（ticket 第 7 条，本票最关键的架构验收点）

1. 让段 0 呼吸起来（周期 1000ms）。
2. 在小程序里主动断开 / 关掉微信 / 走远到断开。
3. **观察**：灯带**继续呼吸**，节奏与断开前一致。
4. 串口：断开后 `render seg: ... frame=` 的编号**继续增长**（说明是固件自己的时间轴，
   不是靠 BLE 帧驱动）。
5. 重新连上：`QueryStrip` 拉回的段配置里 `type=0x01`、period 与断开前一致。
   相位**不因重连重置**——`t0_ms` 只在写入段时设置，重连既不重发段也不改它，
   所以看起来是「接着断开前的节奏继续」而不是从头开始。

### 5.8 静态不空转（ticket 第 8 条，串口可判定）

1. 只有一个静态段（`0` – `63`，纯色）。串口应只有：
   - `帧循环模式 -> 静态（阻塞等待，不空转）...`（启动或从动画切回时一行）；
   - 每次改颜色 / 亮度时的一行 `render seg:`。
   - **不应出现**周期性的 `render seg: ... frame=N`。
2. 把该段切成呼吸，串口立刻出现 `帧循环模式 -> 动画（fps=10）`，随后 `frame=` 持续增长。
3. 切回静态：`帧循环模式 -> 静态（阻塞等待，不空转）已绘制=N 跳过=M`，之后帧号不再增长。
4. 判定：动画阶段的 `已绘制` 每秒约 +10；静态阶段完全不动。

### 5.9 相位天花板（ticket 第 9 条）

本票的**相位溢出**已由 host 测试覆盖（`test_effects_breathing_phase`）：

- `period_ms = 65535`，`r` 从 1 稀疏扫到 65534，再在末尾 40ms 逐毫秒密集扫；
- 断言相位**恒在 [0, 65536)**、单调不减、`r = 65534` 时相位 = 65534；
- 断言 32 位回绕（`t0 = 0xFFFFFFFF`、`now = 0x10`）下相位仍等于真实经过时间 mod period；
  即 `((uint64_t)17 << 16) / 1000`。

真机侧只需一条：周期设 **65535ms**（约 65 秒一个周期），观察亮度变化**极慢但均匀**，
没有跳变、没有突然变快/变慢（32 位写法会在 r ≈ 65534 附近突然失真）。

### 5.10 肉眼错色 / 闪烁（ticket 第 11 条）

在 5.2–5.9 全程盯灯带：

- 有无短暂**错色帧**（红变绿、整条闪白）？
- 有无**闪烁**（不该亮的时刻亮一下）？
- 有无整条变暗 / 掉压 / 重启（`BROWNOUT`）？

本票不调整 `max_brightness`，也不给动画加限流系数。

## 6. #31 彩虹与流光灯效（待真机执行）

对应 [issue #31](https://github.com/sishoui/light-matt/issues/31)，是 [#30 呼吸](#5-30-呼吸灯效待真机执行) 的

### 6.1 准备

### 6.2 彩虹 span 两个边界（ticket 第 1、2 条）

| 操作 | 应观察到 |
|---|---|
| span = 0，周期 1200ms | 整段**同一颜色**，颜色随时间匀滑循环（红→黄→绿→蓝→紫→红） |
| span = 255，周期 1200ms | 整段**铺满一整圈**彩虹，图案随时间平移（不改变形状） |
| 把 span 从 0 缓慢拖到 255 | 颜色沿灯带**连续铺开**，不是二值跳变（ticket 第 3 条） |

判定要点：span=0 时整段任意两颗灯**同时刻必须同色**；span=255 时首尾灯色相应正好差约一整圈。

### 6.3 流光尾部与方向（ticket 第 4、5 条）

| 操作 | 应观察到 |
|---|---|
| tail = 0 | **硬边**亮点：亮珠紧邻的一颗几乎全黑 |
| tail = 255 | **长拖尾**：整段都跟着头部渐暗 |
| 点「反向」 | 亮点从段尾走向段首；正向/反向的图案是镜像 |

### 6.4 周期下限与保留位被拒（ticket 第 6 条，配置不变）

1. 小程序构造器本身拒绝 < 200ms（滑块已钳位），所以这一条主要看**设备侧**：
   用 `scripts\acceptance-probe.py`（或手动改一帧）发 `period_ms = 199` 的彩虹/流光段。
2. 期望 ACK `result=0x01`，**画面保持不变**（旧段仍在跑，不闪黑）。
3. 发一个 flags bit1 置位的彩虹帧，同样 `0x01` 且画面不变。

### 6.5 三种灯效同帧共存（ticket 第 7 条）

划三段互不重叠：`[0-9]` 彩虹、`[10-19]` 流光、`[20-29]` 静态单色。

判定：三段的画面**同时**正确；静态段不随时间变、不被动画段拖慢；
未覆盖的灯珠（如 30-63）始终熄灭。

### 6.6 跨段相位不连续（D4，ticket 第 8 条，本票最关键的「按设计工作」点）

划两段**参数完全相同**的流光 `[0-9]` 与 `[10-19]`，分别下发（不要在同一帧里连发）。

判定：两条亮点**各自独立循环**，段边界处的拖尾会被硬切断——这是**预期行为**（每段相位从自己
的生效时刻 `t0_ms` 起算，D4 已定的取舍）。若看到整条像一条连续的长灯带在跑，说明相位被
共享了，那是 bug。

### 6.7 满周期不错色（ticket 第 9 条）

把彩虹周期设为 **65535ms**（约 65 秒，相位天花板），span=255，盯着看满一整个周期。

判定：颜色始终在正确的色相环上移动，**没有任何一帧突然跳回红色或出现灰白/错色**。
这是 host 测试已覆盖的 32 位溢出点在真机上的对照观察。

### 6.8 肉眼错色 / 闪烁（ticket 第 10 条）

在 6.2-6.7 全程盯灯带：

- 有无短暂错色帧（彩虹段里忽然出现不相邻的色区）？
- 有无闪烁（不该亮的时刻亮一下）？
- 有无整条变暗 / 掉压 / `BROWNOUT` 重启？

彩虹/流光可能让大量灯珠同时高亮，电流高于静态纯白的最坏情况——这是 D6 已接受的风险。
若出现供电问题：**记录不修**，回写地图「电流预算」风险项（本期不加限流系数）。

## 7. #32 剧本 / 阶段序列（待真机执行）


小程序：微信开发者工具导入 `miniprogram/`，真机预览。硬件同 §0.2。
建议灯珠数 **30**（每阶段两段：`0-9`、`10-29`，肉眼容易分辨）。

### 7.4 录制一轮完整 4 阶段循环（ticket 第 1 条的真机证据）

**录制要求**：手机固定机位、能同时拍到**灯带**与**秒表/手机屏幕**；全程不断开。

1. 在「剧本」区确认 **剧本 1** 被选中（4 个阶段行）。
2. 逐阶段编辑（点阶段行 → 用「当前段加入阶段」把当前分段加进去）：
   | 阶段 | 时长 | 段 0 `[0-9]` | 段 1 `[10-29]` |
   |---|---|---|---|
   | 1 | 1000 ms | 静态 · 红 | 静态 · 蓝 |
   | 2 | 1500 ms | 呼吸 · 绿（周期 1000ms） | 静态 · 蓝 |
   | 3 | 2000 ms | 彩虹（周期 2000ms、span 255） | 流光 · 紫（800ms） |
   | 4 | 2500 ms | 静态 · 暖白 | 呼吸 · 绿（1500ms） |
3. 点「下发剧本」。观察进度条：应依次经历 `准备剧本` → 各阶段时长 → 各段 →
   `提交剧本 1` → `激活剧本 1`，最后显示 `100% · 下发完成`。
4. 打开串口（`idf.py -p COM6 monitor`），应看到 `ScriptBegin id=0 stages=4 strips=1`、
   4 行 `ScriptStage`、8 行 `ScriptSegment`、`ScriptCommit ok id=0 stages=4`。
5. 点「播放」。**开始录像**，录 **至少 1.5 个完整循环**（4 阶段一轮 = 7 秒，录 12 秒以上）。
6. 逐阶段核对（用秒表对时间）：
   - 0-7s：阶段 1（红 + 蓝，1 秒）→ 阶段 2（绿呼吸 + 蓝，1.5 秒）→
     阶段 3（彩虹 + 紫流光，2 秒）→ 阶段 4（暖白 + 绿呼吸，2.5 秒）；
   - 7s 后回到阶段 1（**循环生效**，ticket 第 3 条）；
   - 每次切换都能看到**相位重置**：彩虹从色相 0 重新开始、呼吸从最暗重新起。
7. 串口在每次切换时应打出 `剧本 stage N/4 开始（phase 重置）`。

**判定**：整轮 7 秒的顺序、时长、颜色与上表一致；回到阶段 1 时无停顿、无黑帧。

### 7.5 暂停 → 继续（ticket 第 5 条）

1. 播放中，在**阶段 3 进行到一半**时点「暂停」。
2. 画面应**完全冻结**（彩虹不再移动、呼吸不再变化）。等 5 秒。
3. 点「播放」。

判定：从**暂停那一刻的画面**继续，不是从阶段 3 开头、更不是阶段 1。
若从阶段开头重来，说明 `pause_offset_ms` 补偿没生效（bug）。

### 7.6 断开后继续（ticket 第 6 条）

1. 播放中，直接**关掉小程序**（或在系统设置里关蓝牙）。
2. 串口应打 `disconnected`，但灯带**不停**。

判定：剧本继续按阶段切换至少两个完整循环。这是「设备自己跑时间轴」的证明。

### 7.7 多套剧本切换（ticket 第 7/8 条）

1. 剧本 1 已下发（7.4）。切到「剧本 2」，下发一套**明显不同**的（例如 2 个阶段：
   1000ms 全绿、1000ms 全红）。
2. 点「激活剧本 2」→ 播放：看到剧本 2 的内容。
3. 点「激活剧本 1」→ 播放：**看到的仍是剧本 1 原来的内容**（没有被剧本 2 覆盖）。

判定：两套互不影响。串口 `ActivateScript id=1/0` 各一次，`QueryScript` 回的
`ScriptSummary.stages` 分别是 4 与 2。

### 7.8 下发失败保留上一套（ticket 第 10 条）

1. 剧本 1 已提交并可播放。
2. 在编辑器里把**阶段 2 的时长清空**（或填 `0`），点「下发剧本」。
   本端预检会直接拦下（`有 1 个阶段的时长非法`），一帧都不发——这已经证明了本端保护。
3. 再构造一个**本端放得过、设备会拒**的场景：让阶段 2 的段与阶段 1 的段
   在**同一阶段内**重叠是本地拦的；跨阶段不冲突。所以真实设备侧拒绝用
   另一种方式验证：**灯珠数量改小**（例如 30 → 8），再下发原来 `[10-29]` 的段。
   设备 `ScriptCommit` 会回 `InvalidParam (0x01)`。
4. 串口应看到 `ScriptCommit 失败 id=0：整份校验不过，暂存已丢弃，保留上一套`，
   并跟一条 `Event event=0x02 detail=0x00`。
5. 小程序应显示「下发被设备拒绝（InvalidParam），上一套剧本仍可用」。

判定：点「播放」后**仍是原来那套剧本**在跑，没有任何半套行为（不会只有前两个阶段）。

### 7.9 断电重启（ticket 第 11 条）

判定（本票选定的行为）：

这符合 §10.4 的取舍「播放位置不持久化」。若上电自动开跑或从断电位置继续，都是 bug。

## 7. v2 首次烧录发现并修复：渲染任务栈溢出（2026-10-31）

**这是 v2 第一轮真机上的第一个真实缺陷，host 测试完全测不出来。**

### 现象

烧录 v2 固件后设备**上电即反复重启**，串口刷屏：

```
I (327) lumen_engine: state default: power=0 brightness=128 rgb=255,180,120 leds=30 max=200 segs=0
Guru Meditation Error: Core  0 panic'ed (Stack protection fault).
Detected in task "lumen_render" at 0x420109c4
Stack pointer: 0x3fcaa370
Stack bounds:  0x3fcaa8cc - 0x3fcab8c0     ← SP 已越过下界
```

`SP < Stack bounds 下界`，说明渲染任务把栈打穿了，不是空指针也不是看门狗。

### 根因

v2 引入分段后，两个大结构被放在**任务栈上**：

| 结构 | 大小 | 说明 |
|---|---|---|
| `lumen_segment_store_t` | **1024 B** | 8 条 × 8 段 × 16 字节 |
| `lumen_persist_t` | **≈1060 B** | 状态 + 整份段表 + 每条的灯珠数 |

而渲染任务栈只有 **4096 B**，再叠上 `led_strip` / RMT 驱动的调用深度就打穿了。
同一个问题在 NimBLE 主机任务（也是 4096 B）里也存在：`lumen_led_engine_commit`、
`set_segment`、`clear_segment` 各自都放了一份 `lumen_persist_t` 局部变量。

**为什么 host 测试测不出来**：PC 的栈是 MB 级，`firmware/test` 编译的是纯逻辑模块，
根本不跑 FreeRTOS 任务。这类缺陷只有真机能暴露——这正是「像素级/运行时行为必须真机验证」
那句话的具体含义。

### 修复

1. **大结构移出栈**：渲染任务的 `s_render_persist` / `s_render_segments`、
   BLE 回调路径的 `s_commit_persist` 都改为**文件级静态区**。
   渲染任务是单实例任务、这些缓冲只被它使用，所以静态区天然安全；
   两者分开（不共用）是因为 commit 在 NimBLE 任务里跑、渲染任务同时读自己那份。
2. **消除返回值拷贝**：`persist_snapshot_locked()` 从「返回 1060 字节结构」
   改为**指针出参**，否则按值返回仍会在调用者栈上放一份临时对象。
3. **栈留余量**：`LUMEN_RENDER_TASK_STACK_SIZE` 4096 → **6144**，
   `LUMEN_STORE_TASK_STACK_SIZE` 3072 → **4096**，理由写进 Kconfig。

### 修复后验证（真机）

```
I (297) main_task: Calling app_main()
I (327) lumen_engine: state default: power=0 brightness=128 rgb=255,180,120 leds=30 max=200 segs=0
I (327) lumen_engine: render: n=30 brightness=128 power=0
I (397) lumen_ble: GATT 服务已注册（Service 6c756d65-...-0001，RX/TX/State）
I (417) lumen_ble: 开始广播（Lumen-5662），等连接
```
**零 panic**，启动补发按预期打 4 帧。

协议层（PC 当 central，`bleak`）：

| 项 | 结果 |
|---|---|
| State read | **14 字节** `0080FFB4781E00C80100FF000000`（v2 布局正确） |
| `QueryState 0x05` | ACK `A5028001020500D0` + StateReport `A5028201...`，seq 回显 |
| `SetLedCount 0x06` | ACK OK，`led_count=64` |
| `SetPower 0x01` | ACK OK，`power=1` |
| `SetSegment 0x10` ×3 | 三条全 ACK OK，`State.seg_count=3` |
| `QueryStrip 0x12` | 3 条 SegmentReport `0x83` + SegmentListEnd `0x84` (mask `0x07`) |

`State` 最终为 `0180FF00004000C80103FF000000`：
`power=1, brightness=128, rgb=255,0,0`（seg 0 的红色基准色，符合 §7）、

### 仍未确认

串口与协议侧的证据到此为止；请按 §4.3 做一次肉眼确认并拍照。
