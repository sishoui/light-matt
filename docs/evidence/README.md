## 6. §4.5 v2 → v3 升级的配置丢失（记录口径）

**结论：刷 v3 固件后设备配置回到默认值。这是设计取舍，不是缺陷。**
（`acceptance-v3.md` §0.1 的约定：必须在验收记录里写明，避免以后误判为 bug。）

**已确证的机制**（来自代码与文档，非本轮实测）：

| 数据 | v2 | v3 | 后果 |
|---|---|---|---|
| state blob | magic `LMEN` / version **3** | magic `LMEN` / version **4** | 旧 state 读取校验失败 → 全部回默认 |
| script blob | magic `LMSC` / version **1** | magic **`LMS3`** / version **2** | 旧剧本表不被识别 → 4 个槽位为空 |
| 协议信封 | `0xA5` / version `0x02` | `0xA6` / version `0x03` | 旧版小程序连上也不通 |

回默认值的具体形态（`docs/protocol-v3.md` §10.5）：关灯、亮度 128、暖白
`255,180,120`、`strip_power_mask=0xFF`、`strip_counts` 按构建期引脚表、
无段、layer1 空、blend 0、无激活剧本。启动日志首行因此是
`state default: ...` 而不是 `state restored: ...`。

**不写迁移代码是刻意的**：双格式读取会让本已紧张的 16KB 剧本容量再多一份
兼容分支；个人测试阶段没有第三方在用，没有迁移代价。

> ⚠ **本轮没有再次刷固件**，因此没有产生新的 v2→v3 实测快照。
> 上面是机制陈述 + 默认值出处；若要留下实测证据，需按
> `scripts\flash-firmware.cmd COM6` 刷一次并抓 `state default` 首行
> —— **但那会清掉设备当前配置**，属于会改变现场的操作，验收期不建议做。
>
> **以后遇到「刷完灯不亮 / 段没了 / 剧本没了」，先确认是不是又刷了固件**，
> 不要当 bug 查。对照上表的默认值即可判定。
>
> 另注意区分两件事：**刷固件（跨版本）** 会丢配置；**断电重启（同版本）**
> 不会丢 —— 后者由 §1.8 覆盖，`state restored: ...` 才是它的证据。

## 5. 本轮修掉的工具缺陷（不是固件问题，记下来免得下次重踩）

写 `probe-v3-deep.py` 时先出现过 4 个 FAIL，全部是**探针自身的错**：

| 现象 | 根因 | 处置 |
|---|---|---|
| `amask` 恒 0、`seg_count[3]=0` | 前一组测试的剧本非循环播完会 `hold_last`，State 的段数/动画位读的是**剧本最后一阶段**而非静态段 | 测静态段前先 `SetPlayback(0)` |
| 「断连后播放头没推进」 | ① `SetPlayback(action, loop)` 每次调用都写 `loop`，传 0 把 `ActivateScript` 的 `loop=1` 覆盖了；② 剧本总长 4s，短于「断连 + 重连」的开销 | 传 `loop=1`；改用 8×3s=24s 的长剧本 |

这两条现在写进了脚本注释 —— 它们描述的是**协议的真实语义**，不是脚本怪癖。

**顺带确认的固件行为**（都符合契约，不是 bug）：

- 剧本非循环播完停在末阶段（`playback_state=0` + `hold_last`），此时
  State 的段数/基准色仍报**该阶段**的值。
- `ScriptStage duration=0` 被拒（`InvalidParam`），与 §9.6 一致。
- 第二套过大剧本 `Commit` 回 `0x0A` 后，**槽位 1 原先那套 1 阶段剧本原样保留**
  （不是变成空）—— 这正是「失败只丢暂存区」的回滚语义。
