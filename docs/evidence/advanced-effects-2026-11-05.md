# 进阶灯效：循环三档 + 单灯组隔离 测试报告

- **时间**：2026-11-05
- **设备**：`Lumen-5662` @ `CC:8D:A2:C2:56:62`，固件 v4.0，8 条带 × 30 颗
- **方法**：真机裸帧协议直发（`SET_PLAYBACK` / `ACTIVATE_SCRIPT` 三值 loop）+ 相机实拍验证出光
- **结论**：**固件侧循环三档全部正确；单灯组隔离在产品补齐逻辑下成立**
- **同时发现一个真实缺陷**：`applyAdvanced` 把「最后一步循环」静默降级成「全部循环」

---

## 1. 循环三档（固件 + 协议层）

三阶段剧本（红 2s → 绿 2s → 蓝 2s），逐档实测 State 的 `stage_index` / `playback_state` / `flags`：

| 档位 | 实测阶段序列 | 终态 | flags | 判定 |
|---|---|---|---|---|
| **不循环** `loop=0` | `[0, 1, 2]` | stage=2，`playback=0` | `0x02`（无循环位） | ✅ 走完停住 |
| **全部循环** `loop=1` | `[0, 1, 2, 0, 1]` | 持续播放 | `0x03`（bit0=1） | ✅ 回到第 0 步 |
| **最后一步循环** `loop=2` | `[0, 1, 2]`，第 2 步采样 **6 次**，**从不回退**到 0/1 | 持续播放 | `0x07`（bit0+bit2） | ✅ 前两步各一次、最后一步原地重播 |
| 非法 `loop=3` | — | — | — | ✅ 被拒 `InvalidParam` |

设备实际写的 flags 与协议 §7.5 的位表逐位吻合：

```
loop=0 → 0x02   (bit1 script_active)
loop=1 → 0x03   (+bit0 循环中)
loop=2 → 0x07   (+bit0 +bit2 最后一步循环)
```

> 补充：`loop=2` 的「原地重播」用「进入第 2 步后再也没回到 0/1」+「第 2 步被反复采样到」两条共同证明，
> 而不是只看阶段序号——只看序号的话，「停止」和「原地重播」长得一样。

## 2. 单灯组隔离（改一条，其它不动）

### 2.1 为什么必须用相机

剧本内容是**读不回来的**：`QueryStrip` 只返回实时段（`s_segments`），剧本 blob 没有查询接口，
只有 4 字节摘要。所以「其它灯组没被动过」唯一能证明的地方是**它们的实际出光**。

### 2.2 测量方法

相机标定线编号 ≠ 物理灯带编号（实测 `0→4, 2→0, 3→2, 4→5, 5→6, 6→7`），
必须先做逐带隔离测出映射，再把读数还原到物理带号上。

### 2.3 结果

先铺 8 条带各自一色的基准，然后**只改 strip 0**，按产品的 `plan-fill` 逻辑补齐其它灯组后下发：

| 物理带 | 基准色相 | 改后色相 | 变化 |
|---|---|---|---|
| **0** | 359.9° | 317.0° | **Δ43° ← 只有它变了** |
| 2 | 65.5° | 66.3° | Δ1° 不变 |
| 3 | 121.7° | 122.9° | Δ1° 不变 |
| 4 | 173.1° | 174.3° | Δ1° 不变 |
| 5 | 193.2° | 193.5° | Δ0° 不变 |
| 6 | 237.9° | 238.3° | Δ0° 不变 |
| 1 / 7 | — | — | 只有 2 颗灯，相机定不出线段 |

**结论：改一条灯组，其它灯组逐字节保持原状（色相差 ≤1°，在相机噪声内）。**

另外两条独立证据：

- **单独关闭一条带**：`power_mask` 从 `0xFF` → `0xFE`，只掉那一位；剧本仍在播放（`playback=1`），其它 7 带不受影响。
- **补齐确实发生了**：7 条灯组的现有分区全部被读回并补进方案（`{1..7: 现有分区}`），而非留空。

### 2.4 一个必须说清的对照

如果**跳过补齐**、直接下发「只含 strip 0」的方案，其余 7 条会退回基准单色——
相机拍到 8 条全是蓝色系。这正是 `plan-fill` 存在的理由（#101 修的跨灯组串扰）。
**产品走的是补齐路径，所以用户看到的是 §2.3 的结果。**

## 3. 发现的真实缺陷：`loop=2` 在页面路径上会被降级

### 现象

用户在进阶档选「最后一步循环」，实际下发到设备的是「全部循环」。

### 根因

`miniprogram/pages/strip/strip.ts` 有两处（3441 行与 3651 行附近）这样推导循环模式：

```ts
const loop = state !== null && (state.flags & 0x01) === 1;   // 布尔！
```

协议里的 loop 是**三值**（0 不循环 / 1 全部循环 / 2 最后一步循环，§7.5），
但这里只看 bit0，得到的是布尔值。随后 `assertLoopMode` 把 `true` 映射成 `LOOP.ALL`：

```
设备 flags=0x07（loop=2）→ (flags & 0x01) === 1 → true → 实际下发 loop=1  ❌ 降级
```

而用户选的档位明明已经写进草稿（`onLoopTap` → `withDraftLoop`），
但 `draftToScriptConfig` **不携带 loop**，下发时也没人读草稿里的 `draft.loop`。

### 影响范围

- 直接点「应用并播放」→ 降级
- 点循环三档里的「最后一步循环」→ 降级
- 「不循环」和「全部循环」不受影响

### 正确的写法

仓库里已经有现成的正确实现，只是没被用上：

```ts
import { stateLoopMode } from "../../utils/protocol/commands";   // 已 import（第 228 行）
const loop = state === null ? LOOP.NONE : stateLoopMode(state);
```

`stateLoopMode` → `loopModeFromFlags` 正确区分三值（`flags & 0x04` 判 LAST）。
同文件 2735 / 3265 行已经在用这个写法，只有这两处漏了。

### 为什么测试没发现

- `advanced-layers.test.ts` 只测纯函数（`loopFlagsOf` / `loopLabel`），全绿；
- 没有任何测试覆盖 `applyAdvanced` 的 loop 推导；
- 真机 e2e（`complex-plan.test.ts`）自己拼 loop 值，绕过了页面。
