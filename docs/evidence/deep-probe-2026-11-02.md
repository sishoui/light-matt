# 设备侧行为语义探针报告（2026-11-02）

**脚本**：`scripts/probe-v3-deep.py`（本轮新增，已入库）
**设备**：`Lumen-5662`，MAC `cc:8d:a2:c2:56:62`，固件 v3.0，MTU 247，串口 COM6 @115200
**结果**：**69/69 断言通过**
**原始报告**：`.runs/v3/deep.json`（SHA-256 `599412ee64e32bca…`）

---

## 0. 这个脚本补的是什么

`probe-v3.py` 回答「字节对不对、ACK 回没回」。本脚本回答**行为语义对不对**，
覆盖 `docs/acceptance-v3.md` 里原先标成「需小程序真机」、但**设备侧其实可判定**
的那一半。所以下面每一项都要和「UI 侧」分开看：

- ✅ 设备做了什么 —— 本报告
- ☐ 小程序页面怎么显示 —— 仍需真机

## 1. 逐项结果

### §1.1 八条灯带各自独立

| 断言 | 实测 |
|---|---|
| strip 0 设 0-9 红色 后，只有 strip 0 有段 | `seg_counts=[1,0,0,0,…]` |
| strip 1/2/3 未被波及 | `QueryStrip` 均 0 条 |
| 再给 strip 1 设 0-9 绿色 | ACK OK |
| strip 0 的红色段**逐字节不变** | `QueryStrip(0)` 前后相同 |
| strip 1 的段与 strip 0 不同 | 21B 载荷不同 |
| `State.strip_seg_counts` 逐带真实 | `[1,1,0,0,0,0,0,0]` |
| `QueryStrip` 逐带真实（不是复制 strip 0） | `[1,1,0,0,0,0,0,0]` |
| `strip_counts` 逐带 u16 非 0 | `[30]×8` |

> **1.1.4 的口径**：chip 上「序号/灯珠数/GPIO/开关/段数/是否动画」六个字段，
> 设备侧的数据源全部逐带真实。**显示出来对不对**是 UI 的事，仍属未验。
> 另：`strip_counts` 一律报 30 与物理 2~30 颗不符，是**已知缺陷**（见
> `acceptance-v3.md` §2.3），不是本项失败。

### §1.2 每带独立开关

| 断言 | 实测 |
|---|---|
| 8 条都设呼吸段 → `amask=0xFF` | `0xFF` |
| 关第 3 条 → `pmask` bit3 清零 | `0xFF → 0xF7` |
| 其余 7 条仍在跑动画 | `amask` 仍 `0xFF` |
| 串口出现「strip 3 关闭：已推黑帧」 | `I (68797) strip 3 关闭：已推黑帧，后续 TDM 轮询跳过` |
| 重开第 3 条 → `pmask` 恢复 | `0xF7 → 0xFF` |
| 重开后不用重设段 | `seg_count[3]=1` |
| 自检忽略每带开关 | 只留 strip 7 开（`pmask=0x80`）仍走完四色 |
| 自检序列红→绿→蓝→白 | 串口 `1/4 red`…`4/4 white` 四条齐全 |

> **1.2.2 的判据**「无残影」在设备侧只能证明**推了黑帧**（串口那行 + 代码路径
> `BLACK_THEN_SKIP`）。WS2812B 是否真的熄灭要点亮后才看得见 —— 这条**仍算未闭环**。

### §1.4 段区间与重叠

| 断言 | 实测 |
|---|---|
| 0-15 之后设 10-20 → 被拒 | `InvalidParam`，读回只剩 0-15 |
| 0-40 超出 30 颗 → 被拒 | `InvalidParam` |
| 单层带 `blend=1` → 被拒 | `InvalidParam` |
| 被拒后旧段**逐字节不变** | `QueryStrip` 前后 21B 完全一致 |
| 改 strip 2 不影响 strip 0/1 | 两条读回均逐字节不变 |

> 判据里「**提交前**就提示、不发请求」是客户端行为，由
> `miniprogram/tests/segment-editor.test.ts` 的断言锁死；本轮设备侧只证明
> 「万一漏到设备，设备也会拒且不改旧配置」。

### §1.5 多阶段剧本

| 断言 | 实测 |
|---|---|
| 4 套剧本（1/2/3/4 阶段）各自提交 | 全部 `OK` |
| 4 套摘要各自独立 | `stage_count` 分别 1/2/3/4 |
| 激活剧本 2 后只有它 `active=1` | 其余 3 套 `active=0`，`State.script_id=2` |
| 4 阶段（800/1200/800/1200ms）按时长推进 | 切换实测 `0.91s / 2.05s / 2.89s`（期望 0.80/2.00/2.80，±300ms 内） |
| `stage_index` 与画面一致 | 依次 1→2→3 |
| 非循环播完停在末阶段 | `stage=3, playback=0` |
| `ScriptStage duration=0` 被拒 | `InvalidParam` |
| 播放中拔掉手机，剧本继续 | 断连 5.4s 后 `stage 0→1`，`playback=1` |

> **1.5.2 的做法**：用 8×3s = 24s 的循环剧本，断连 2.2s 后重连。用短剧本
> 会因「断连 + 重连」本身耗时 4~6s 而在重连前播完，测不出来。
> 注意 `SetPlayback(action, loop)` **每次都写 loop**，必须传 1，否则覆盖
> `ActivateScript` 设的 `loop=1`。
>
> **1.5.3 的读回口径**：v3 只有 `QueryScript → ScriptSummary`（4 字节），
> 没有读回完整阶段内容的命令。本项只证明**摘要一致**，完整内容需重下发。
> 这是契约的已知限制（`protocol-v3.md` §10.4）。

### §1.6 剧本过大

| 断言 | 实测 |
|---|---|
| 8带×8阶段×8段两层动画（单套 ≈ 9835B）下发 | 768 条 `ScriptSegment` 全 ACK |
| 第一套提交 | `OK` |
| 第二套同尺寸下发 | 全 ACK |
| 第二套 `Commit` | **`0x0A ScriptTooLarge`** |
| 串口 | `ScriptCommit id=1 编码后超过 16384 字节：拒签，配置未改变` |
| 失败后剧本 0 未被改动 | `stages=8` |
| 失败后剧本 1 **保持原样** | `stages=1`（下发前也是 1） |
| 上一套仍可激活并播放 | `Activate OK`，2.4s 后 `stage=2, playback=1` |

> **回滚判据要注意**：`ScriptCommit` 失败是「**只丢暂存区，已提交的不动**」，
> 不是「变空」。所以正确判据是「与下发前相同」，不是「stage_count=0」。

## 2. 这块**没有**证明什么

为防止把 69/69 读成「§1 全过了」，明确列出本报告**不覆盖**的：

1. **颜色好不好看** —— §1.3 的相加/覆盖观感、单层回归，全部需要人眼。
2. **无残影** —— 只证明推了黑帧，没看见灯真的灭。
3. **提交前提示** —— 客户端拦截由单测锁死，真机上「提示文字出现」没验。
4. **chip 显示内容** —— 数据源已验逐带真实，渲染没验。
5. **fade 入口不存在** —— 代码里确认没有，页面上看不到没验。
6. **日志面板** —— 手机 UI。
7. **多设备** —— 只有 1 台。

## 3. 复现

```bash
# 设备空闲、小程序退到后台（协议是单连接，断开才重新广播）
python scripts/probe-v3-deep.py --serial COM6 --json .runs/v3/deep.json
# 想快一点跳过 ~900 帧的过大剧本测试：
python scripts/probe-v3-deep.py --serial COM6 --skip-heavy
```

脚本会改写设备上的段、`pmask` 与 4 个剧本槽位；结束时统一收尾为
「停止播放、清段、8 带全开、亮度 128、关灯」。**不恢复**用户原有的剧本内容
（v3 没有读回完整剧本的命令，见 §1.5.3 的口径）。
