## 1. 测试是怎么分层的

微信小程序 → BLE → ESP32 这条链路，**没有一层能单独证明「能用」**。所以按环境成本分成六层，
各层补对方看不见的盲区：

| 层 | 验什么 | 为什么必须单独一层 |
|---|---|---|
| 固件 host | 协议字节布局、灯效像素数学、状态机 | 纯 C，无硬件，1.4 万断言一两秒跑完 |
| 小程序单测 | 编解码、会话逻辑、页面派生、存储 | `tsc` 干净不证明逻辑对 |
| 后端单测 | 使用日志、设备登记、鉴权 | 与小程序互不依赖 |
| 渲染回归 | 页面真的渲染、`bindtap` 真有方法、点了状态真的变 | **白屏和事件全失效只有渲染层看得见**，`tsc` 与单测都发现不了 |
| 真机 BLE | 真实 MTU / 分片 / CRC / ACK 往返 | 开发者工具的蓝牙是桩实现 |
| 相机视觉 | 灯带**实际**亮不亮、颜色对不对、逐带是否独立 | 协议回 `OK` ≠ 灯珠真的发光 |

## 3. 过程中发现并修掉的问题

这一轮有价值的不是「全绿」，而是**三次把假绿色拆穿**：

1. **渲染回归假绿**：编排器默认连 9501，实际端口是 9502，第一次直接 SKIP。
   补上端口后 49 条才真跑。
2. **视觉层三次假结果**：
   - 第一版视频录像被 `--max-seconds 90` 截断，丢掉最后 36 秒；
   - 第二版拿容器帧率算时间，窗口归属错位（关灯窗口里混进了下一场景的亮帧）；
   - 第三版才发现**标定线编号与物理灯带编号不是一回事**——实测映射是
     `0→4, 2→0, 3→2, 4→5, 5→6, 6→7`。不做隔离测试就下「逐带」结论等于标签张冠李戴。
3. **相机固有局限**（不是缺陷，写进判据）：色域被压缩（固件 0°–315° 实测只覆盖
   约 23°–279°），两条带只有 2 颗灯、几何上定不出线段。所以色相判据用「可区分 + 单调」
   而不是「绝对相等」。

## 4. 结论

- **协议与链路**：v4 字节契约在真机上逐条成立，43/43 + 16/16。
- **小程序**：1834 条单测 + 49 条渲染断言 + 4 条真实交互路径，点击有效、状态真的变。
- **灯带实物**：8 条带可独立开关、颜色正确可区分、逐带亮度生效、八种灯效都出光、
  剧本播放头真的推进。
- **现场已复原**：设备关灯、亮度 128、无残留段、8 带全开。

**已知不覆盖**（如实记录，不算通过）：RMT × BLE 共存长跑（#7，用户决定跳过）、
iOS 后台扫描、多设备切换（只有 1 台设备）、两条 2 颗灯的短带逐带几何标定。
