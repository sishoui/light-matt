## 1. 本轮修掉的两个真机缺陷（都是 P0）

### 1.1 多帧报告在 BLE 主机任务里连发，第 18 帧后全部失败

**症状**：`QueryScene` 只读回 2~28 个部位头、15~221 步，`SceneListEnd` 从不出现。
串口日志：

```
W (733425) lumen_ble: ScenePartReport 发送失败 scene=0 strip=5 part=1
...
W (733575) lumen_ble: SceneListEnd 发送失败 scene=0
I (733585) lumen_ble: QueryScene 0 -> 3 ScenePartReport + 14 SceneStepReport + SceneListEnd
```

**根因**：`send_layout_reports` / `send_scene_reports` 直接跑在 NimBLE 主机任务的
GATT 写回调里。`ble_gatts_notify_custom` 只是把 mbuf 交给主机任务**排队**，真正上天线
要等主机任务回到事件循环——可它此刻正卡在回调里。缓冲耗尽后连发全部失败。
先试过 `vTaskDelay` 让出 CPU：**无效**，因为执行者就是它自己。

**修法**：把「发一串报告」搬到独立任务（`report_task`，队列 4 格）。RX 回调只投递请求
就返回，主机任务得以回到事件循环把 mbuf 发出去。协议不变，只换执行者。

**验证**：同一份最坏场景，修复前读回 28 部位 / 221 步；修复后 **64 部位 / 512 步 + 收尾**。

### 1.2 场景 blob 的 encode / decode / size 对「未编排部位」处理不一致 → 场景永不恢复

**症状**：每次编辑都回 `0x00`，串口也打 `saved key=scene0 (252 bytes)`，但**下一次启动
三个场景全空**：

```
I (339) lumen_engine: 场景 0 未恢复（无 key 或 blob 被拒）：name_len=0 strip0 parts=0/0/0
I (339) lumen_engine: 场景 1 未恢复（无 key 或 blob 被拒）：name_len=0 strip0 parts=0/0/0
I (339) lumen_engine: 场景 2 未恢复（无 key 或 blob 被拒）：name_len=0 strip0 parts=0/0/0
```

**根因**：`lumen_scene_blob_size` / `lumen_scene_blob_encode` / `lumen_scene_blob_decode`
对「一个部位都没编排的槽位」各说各话：

- `size` 只按**实际步数**累加；
- `encode` 写**全部 64 个槽位**的 3 字节头；
- `decode` 要求**全部 64 个槽位**的 3 字节头。

于是 blob 比解码期望的短，`p + 3 > limit` 让**每一次**恢复都失败。host 往返测试之所以
一直绿，是因为测试构造的场景恰好把槽位都填满了——**测试与真机数据的形状不同**。

**修法**：三处统一为「每链只算到最后一个有步的部位」。附带把测试从「期望 64 槽位」
改成「期望不占空间」，并新增一条**只编排一个部位**的 roundtrip 回归（+10 断言）。

**验证**：修复前 `场景 0 未恢复`；修复后 `场景 0 已恢复：name_len=2 strip0 parts=2`，
且断电恢复后三个场景各自 8 部位 / 64 步完整读回。

|---|---|
| 复位后 `layout_valid` | **1** |
| 复位后场景 0 / 1 / 2 | **各 8 部位 / 64 步，全部读回** |

I (339) lumen_engine: 场景 0 已恢复：name_len=2 strip0 parts=2/0
I (359) lumen_engine: state restored: power=1 brightness=128 leds=30 max=200 parts=1 scene=0 layout=1

**NVS 占用**：三场景最坏 3 × 10472 = **31416 字节**，加上布局 2824 与 state，

### 2.1 最坏形态压测（规格风险 #2）

上面那一组每场景只写「1 链 × 8 部位 × 8 步」≈ 1.5 KB，**离最坏形态差 7 倍**，
等于没压。单独写了 `scripts/probe-v5-nvs-stress.py` 来问真问题：

| 项 | 结果 |
|---|---|

| 三场景合计 | **31416 字节** |

**结论：规格风险 #2 没有触发。** 31 KB 进 64 KB NVS，8 次整份重写 + 断电，零失败。

## 4. §3 时间漂移（30 分钟）

**这一节分两半，性质完全不同，别混为一谈：**

| 半 | 验什么 | 判据 |
|---|---|---|
| 4.1 稳定性 | 长时间挂着不崩、不掉线、状态不被改写 | 采样无异常 |
| 4.2 **相位偏差** | 播放头有没有累积漂移 | **闭式解残差** |

> **为什么一开始只有 4.1**：协议没有读「演到第几步」的命令（`QueryScene` 只回编好的
> 步表，不回播放头），所以「相位偏差」这个数拿不到。后来加了一条**只在调试构建里
> 存在**的串口日志（`CONFIG_LUMEN_PLAYHEAD_LOG`，默认 `n`，不进线上契约），
> 4.2 才有真数字。

### 4.1 稳定性（原有，`probe-v5-acceptance.py --drift-minutes`）

**方法**：部位 0 = 8 步 × 100ms 全循环（800ms 一圈，最快）；部位 1 = 1 步 × 3000ms
全循环（最慢）。两者同一场景、同时起跳，跑 30 分钟，每 15 秒读一次 State。

**第一版探针在这里犯了误判**：30 分钟窗口里报了 111 次 `Not connected`，看起来像
「设备跑两分钟就掉线」。同时抓串口，设备侧**完全正常**——`tdm:` 行连续输出、
`pushed` 计数一路涨、零 panic，已经连续跑了 1778 秒。所以掉的是 **Windows 侧的 BLE
链路**，不是设备。

修法：采样失败时先尝试重连，能重连 = 链路问题（记 `reconnects`），重连也失败才记
`failures`。这条经验值得记：**「连不上」要先分清是哪一端的问题**，否则会把 PC 的
BLE 栈问题当成固件不稳定。

**实测结果**（`drift-30min-2026-11-07.log`，探针输出原文）：

```
PASS  · 30.0 分钟连续运行不掉线、不改状态  — 1809s，120 次采样，0 次异常
  采样间隔 15s，共 120 次；其中因 PC 侧链路断开而重连 1 次（设备侧未崩溃）。
=== 6/6 通过 ===
```

- **1809 秒**（30.15 分钟）、**120 次采样**、**0 次异常**；
- 只有**第 0 次采样**遇到 PC 侧链路断开，自动重连后全程稳定；
- 计时期间设备一直在跑两个不同节奏的部位（800ms 一圈 vs 3000ms 一圈）。

### 4.2 相位偏差（新增，`probe-v5-drift.py` + `analyze-playhead-log.py`）

**判据是闭式解残差，不是「步号变了没有」。** 后者只能证明在动，证明不了没漂。

```
elapsed_total = (t - origin) mod total
reconstructed = sum(table[:step]) + elapsed
residual      = reconstructed - elapsed_total
```

- 残差恒 0（±1ms 整数截断）= 播放头完全由绝对时间决定，**不存在累积漂移**；
- 残差随时间单调增大 = 累加式实现，每秒都在丢一点时间，那才是真漂移。

**布置**：同一条链两个部位，周期**互质**——7 步 × 100ms = **700ms** 与
3 步 × 300ms = **900ms**（lcm = 6300ms）。互质很重要：周期能整除采样间隔
（如 1000ms 配 10 秒采样）时每次采样都落在循环的同一相位，既看不出漂移，
也验不到「各走各的」。

**采集期间不碰 BLE**——BLE 链路问题会污染判据，而串口是独立通道。

#### 4.2.1 实测数据

**跑完 30 分钟（1792 秒有效覆盖），180 个采样点，两个部位的闭式解残差全部为 0。**

```
# 相位漂移分析（30.0 分钟窗口）

部位 strip=0 part=0：180 样本 / 1792s / 7 步（100+100+100+100+100+100+100 = 700ms） / loop=1
  闭式解残差：min=0ms max=0ms |max|=0ms

部位 strip=0 part=1：180 样本 / 1792s / 3 步（300+300+300 = 900ms） / loop=1
  闭式解残差：min=0ms max=0ms |max|=0ms

相对相位（(0, 0) vs (0, 1)，周期 6300ms）：180 对样本
  均值 3311.1ms / 极差 3311.1ms / 区间 [0, 6200]

PASS  播放头完全由绝对时间决定，无累积漂移
```

**判定：可接受。** 30 分钟内最大相位偏差 **0 ms**（容差 2 ms，即 uint32 毫秒
整数截断的量级）。

**这个 0 不是「采样对齐」造成的假 0**——必须验：

| 部位 | 周期 | 观察到的步号 | 每步被采到次数 |
|---|---|---|---|
| part 0 | 700ms | **0,1,2,3,4,5,6（全 7 步）** | 19 / 29 / 25 / 24 / 30 / 18 / 35 |
| part 1 | 900ms | **0,1,2（全 3 步）** | 60 / 60 / 60 |

7 步与 3 步都覆盖到了，说明采样确实走遍了整个循环——若每次都落在同一相位
（如周期整除采样间隔），只会看到一两个步号，那时的 0 才是假的。

**相对相位在 [0, 6200] 上均匀分布是预期行为，不是漂移。** 700 与 900 互质，
lcm = 6300ms，两个部位的相对相位本来就会随时间走遍整个周期。**漂移判据看的是
每个部位自己的闭式解残差，不是相对相位的极差。** 这一点容易读错，特意写明。

**工具**：`scripts/probe-v5-drift.py`（布置 + 采集）、`scripts/analyze-playhead-log.py`
（判据）。分析器有 **5 项自检**（无漂移通过 / 0.05ms/s 的漂移被抓出 / 缺步表且反推
不自洽时拒绝 / 采样够密时允许反推并标来源 / `elapsed >= dur` 记为 broken），
另做过注入验证：0ms/s → 0ms、0.5ms/s → 15ms。

**日志**：`playhead-30min-2026-11-07.log`（39715 字节 / 363 行）。

> **布置场景的坑**：`SceneStep` 是 **2 秒防抖落盘**。布置完立刻断开连接会让整个
> 场景留在 RAM 没进 NVS——重启后场景回到出厂那 1 步，而布局（`LayoutCommit` 立即
> 落盘）还在，所以 `parts=2` 但时间轴是错的。第一版踩了这个，白跑两轮。现在脚本
> 等 3 秒 + `QueryScene` 复核步数才算布置成功。

## 5. §4 帧率基线 —— **800 颗 / 64 播放头实测**

票面要求「800 颗灯 / 64 播放头的帧率不低于既有基线」。**本项已实测**：

做法是把 8 条链的 `SetLedCount` 全部设成 **100**（共 800 颗），布局给每条链一个整条
部位（0–99），每部位 1 步彩虹（持续变化，去重不会跳过），然后读串口 `tdm:` 行。

| 指标 | 实测值 |
|---|---|
| TDM 轮周期（8 链 × 100 颗 = **800 颗**） | **round ≈ 5.54 ms** |
| 活跃链 | `lit=8`（8 条全在推） |
| 吞吐 | `pushed` 每 2.4 s +60 → **25 轮/秒** |
| 启动尖峰 | `max=33.6 ms`（首轮建句柄 / 首帧），稳态 `round` 无尖峰 |
| 20 fps 预算 | **50 ms / 帧** |
| 余量 | **约 9 倍** |

**已固化进探针**：`python scripts/probe-v5-acceptance.py --framerate`。它自动做
「8 链 SetLedCount(100) → 每链一个整条部位 → 每部位一步彩虹 → 抓串口 tdm 行」，
并且把三条判据都写成断言：

```
PASS  · 8 条链都报 100 颗  — [100, 100, 100, 100, 100, 100, 100, 100]
PASS  · 8 链整条部位提交  — 0x00
PASS  · lit = 8（8 条链都在推帧）  — lit=8
PASS  · pushed 持续增长（真的每轮都在推）  — 200 → 800
PASS  · 轮周期 < 50ms（20fps 预算）  — 5.53ms / 50ms（800 颗）
```

原始输出：`tdm-800led-2026-11-07.log`。

> **为什么不需要真的接 800 颗灯珠**：`SetLedCount` 让 RMT **按 100 颗的位时间真的把数据
> 打出去**，CPU 与 RMT 的成本是真实的，与另一头有没有接灯珠无关。帧预算消耗的是 MCU
> 的时间，不是灯珠的时间。物理上会变的只有「看不看得见」（色域、压降、RMT 时序），
> 那些不属于本项。
>
> **一个差点漏掉的坑**：第一版测量跑在「没有动画」的场景上（画面不变 → 逐条去重把
> 绝大多数帧跳过），读出 `round=1.918 ms`。240 颗的物理位时间约 7.2 ms，**这个数字
> 在物理上不成立**——它说明大部分链根本没推帧。所以帧率基线**必须在有动画、`lit=8`、
> `pushed` 持续增长**的条件下读，否则测的是「什么都没有」。

**既有基线**（v3 时期，8 带 30 颗/带）：单层 11.7 ms / 两层 12.6 ms 每轮帧。
v5 在 800 颗下 5.54 ms，比 v3 的 240 颗还快——因为 v5 每链只做一次 `memset` + 逐部位
散回，且没有动画的链不进帧循环（`lumen_scene_strip_needs_frames`）。

> **仍不能由本项证明的**：真机色域压缩、长灯带压降、8 条链同 5V 供电的电流阶跃。
> 这三项是物理问题，见 `pending-tasks.md`。
