## 1. 本轮修掉的两个真机缺陷（都是 P0）

### 1.1 多帧报告在 BLE 主机任务里连发，第 18 帧后全部失败

**症状**：`QueryScene` 只读回 2~28 个部位头、15~221 步，`SceneListEnd` 从不出现。
串口日志：

```
W (733425) lumen_ble: ScenePartReport 发送失败 scene=0 strip=5 part=1
...
W (733575) lumen_ble: SceneListEnd 发送失败 scene=0
I (733585) lumen_ble: QueryScene 0 -> 3 ScenePartReport + 14 SceneStepReport + SceneListEnd
```

**根因**：`send_layout_reports` / `send_scene_reports` 直接跑在 NimBLE 主机任务的
GATT 写回调里。`ble_gatts_notify_custom` 只是把 mbuf 交给主机任务**排队**，真正上天线
要等主机任务回到事件循环——可它此刻正卡在回调里。缓冲耗尽后连发全部失败。
先试过 `vTaskDelay` 让出 CPU：**无效**，因为执行者就是它自己。

**修法**：把「发一串报告」搬到独立任务（`report_task`，队列 4 格）。RX 回调只投递请求
就返回，主机任务得以回到事件循环把 mbuf 发出去。协议不变，只换执行者。

**验证**：同一份最坏场景，修复前读回 28 部位 / 221 步；修复后 **64 部位 / 512 步 + 收尾**。

### 1.2 场景 blob 的 encode / decode / size 对「未编排部位」处理不一致 → 场景永不恢复

**症状**：每次编辑都回 `0x00`，串口也打 `saved key=scene0 (252 bytes)`，但**下一次启动
三个场景全空**：

```
I (339) lumen_engine: 场景 0 未恢复（无 key 或 blob 被拒）：name_len=0 strip0 parts=0/0/0
I (339) lumen_engine: 场景 1 未恢复（无 key 或 blob 被拒）：name_len=0 strip0 parts=0/0/0
I (339) lumen_engine: 场景 2 未恢复（无 key 或 blob 被拒）：name_len=0 strip0 parts=0/0/0
```

**根因**：`lumen_scene_blob_size` / `lumen_scene_blob_encode` / `lumen_scene_blob_decode`
对「一个部位都没编排的槽位」各说各话：

- `size` 只按**实际步数**累加；
- `encode` 写**全部 64 个槽位**的 3 字节头；
- `decode` 要求**全部 64 个槽位**的 3 字节头。

于是 blob 比解码期望的短，`p + 3 > limit` 让**每一次**恢复都失败。host 往返测试之所以
一直绿，是因为测试构造的场景恰好把槽位都填满了——**测试与真机数据的形状不同**。

**修法**：三处统一为「每链只算到最后一个有步的部位」。附带把测试从「期望 64 槽位」
改成「期望不占空间」，并新增一条**只编排一个部位**的 roundtrip 回归（+10 断言）。

**验证**：修复前 `场景 0 未恢复`；修复后 `场景 0 已恢复：name_len=2 strip0 parts=2`，
且断电恢复后三个场景各自 8 部位 / 64 步完整读回。

## 2. §1 体积实测

**最坏形态**：8 链 × 8 部位 × 8 步 × 两层（两层都带动画，即最坏变长编码）。

| 项 | 数字 | 性质 |
|---|---|---|
| 下发的 `SceneStep` 条数 | **512**（8×8×8），全部回 `0x00` | 实测 |
| 下发耗时 | **209 秒**（512 条串行、一次一帧等 ACK） | 实测 |
| 读回的 `ScenePartReport` | **64**（8×8） | 实测 |
| 读回的 `SceneStepReport` | **512** | 实测 |
| `SceneListEnd` | **1 条**（收尾正确） | 实测 |
| 每步两层都非空 | **512/512** | 实测 |
| 编码后字节数（最坏） | **10472 B** ≤ 上限 **12288 B** | **算术**（`test_scene_blob_max_size` 586 断言钉住） |

> 编码后的字节数设备不报，所以是宿主侧算术；真机验的是「512 条全写进去且全读得回来」——
> 两者一起才说明「最坏形态装得下」。**布局 blob** 本轮升到 **2824 B**（含相位字节），
> 上限 4096，由 `_Static_assert` 与 `test_layout_sizes` 双重钉住。

## 3. §2 存储压测（三场景轮写 + 真断电恢复）

三个场景各写 8 部位 × 8 步（64 条），逐个切过去验 `active_scene`，然后**用串口 DTR/RTS
真复位**（不是「等一下再读」），重新扫描连接后读回：

| 检查 | 结果 |
|---|---|
| 复位后 `layout_valid` | **1** |
| 复位后场景 0 / 1 / 2 | **各 8 部位 / 64 步，全部读回** |

复位后启动日志（节选）：

```
I (339) lumen_engine: 场景 0 已恢复：name_len=2 strip0 parts=2/0
I (359) lumen_engine: state restored: power=1 brightness=128 leds=30 max=200 parts=1 scene=0 layout=1
```

**NVS 占用**（设计值，非实测）：三场景最坏 3 × 12288 = 36864，加上布局 4096 与 state，
仍在 64KB 分区内；本轮压测未触发页擦除失败（`nvs write failed` 零出现）。

## 4. §3 时间漂移（30 分钟）

**方法**：部位 0 = 8 步 × 100ms 全循环（800ms 一圈，最快）；部位 1 = 1 步 × 3000ms
全循环（最慢）。两者同一场景、同时起跳，跑 30 分钟，每 15 秒读一次 State。

**能验什么、不能验什么**：

- **能验**：长时间挂着不崩、不掉线、状态不被改写（真机）；
- **不能验「相位偏差」**：协议没有读「演到第几步」的命令（`QueryScene` 只回编好的步表，
  不回播放头）。所以「两条部位各走各的、没有累积漂移」这一点由 **host 纯函数单测**
  `test_part_clock_no_drift`（12 断言）钉住——播放头用**绝对时间差**推进
  （`lumen_part_clock_advance` 从 `now - origin` 一次算出），不做累加，所以数学上不存在
  累积漂移。

**第一版探针在这里犯了误判**：30 分钟窗口里报了 111 次 `Not connected`，看起来像
「设备跑两分钟就掉线」。同时抓串口，设备侧**完全正常**——`tdm:` 行连续输出、
`pushed` 计数一路涨、零 panic，已经连续跑了 1778 秒。所以掉的是 **Windows 侧的 BLE
链路**，不是设备。

修法：采样失败时先尝试重连，能重连 = 链路问题（记 `reconnects`），重连也失败才记
`failures`。这条经验值得记：**「连不上」要先分清是哪一端的问题**，否则会把 PC 的
BLE 栈问题当成固件不稳定。

**实测结果**：见 `drift-30min-2026-11-07.log`（探针输出原文）。

## 5. §4 帧率基线 —— **240 颗实测，800 颗未测**

票面要求「800 颗灯 / 64 播放头的帧率不低于既有基线」。本轮实测到的是 **8 链 × 30 颗
= 240 颗 / 64 播放头**，**不是 800 颗**——本机 8 条链里只有 1 条接了 30 颗实物，
其余 7 条用同一份配置驱动但线上没有灯。所以：

| 项 | 数字 | 性质 |
|---|---|---|
| TDM 轮周期（8 链 / 240 颗 / 64 播放头） | **round 1.89–1.92 ms，avg 1.918 ms** | **实测**（串口 `tdm:` 行） |
| 单链间隔 | **≈1.918 ms**（每条链一轮） | 实测（同上） |
| 一次完整推送（8 条链） | **pushed 计数每 2.4 s 增加 60** → 25 轮/秒 | 实测 |
| 8 链 800 颗（每链 100 颗） | 推测每轮约 **6.4 ms**（按颗数线性外推） | **算术，未测** |
| 20 fps 预算 | 50 ms/帧 | 契约 |

**为什么不能算「通过」**：240 → 800 是 3.3 倍，虽然线性外推 6.4 ms 仍远低于 50 ms 预算，
但 WS2812B 的位时间由颗数决定、而每轮还有固定的引脚切换与去重开销，线性外推**不是实测**。
另外 64 个播放头的相位计算成本与部位数（不是颗数）相关，本轮 64 个播放头**已全部在内**。

**既有基线**（v3 时期实测，8 带 30 颗/带）：单层 11.7 ms / 两层 12.6 ms 每轮帧。

> 顺带：这段日志是在 30 分钟漂移测试**之后**抓的，设备已连续跑 **1778 秒**、零 panic、
> `max=10.9ms` 的尖峰出现在启动初期，稳态无尖峰。

**要闭环这一项需要有 8 条满长灯带的设备**。在此之前它标为**未测**，不当成通过。

## 7. 复现步骤

```bash
# 1) 固件（离线构建，见 AGENTS.md 的本机环境）
#    组件注册表连不上时，从 %TEMP% 的旧构建目录拷 managed_components
cmd.exe //c "scripts\build-firmware.cmd"
cmd.exe //c "scripts\flash-firmware.cmd COM6"

# 2) 协议回归
python scripts/probe-v5.py --skip-persist

# 3) 整合验收（体积 + 存储 + 断电恢复）
python scripts/probe-v5-acceptance.py --power-cycle

# 4) 时间漂移（30 分钟，不动持久化）
python -u scripts/probe-v5-acceptance.py --skip-volume --skip-storage --drift-minutes 30
```

> **跑之前先退出手机上的小程序**：协议是单连接，被占着就扫不到设备。
> DTR/RTS 复位会让设备短暂进下载模式，**复位后等 3~5 秒**再扫描。
