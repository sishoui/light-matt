# 研究笔记：个人主体 BLE 小程序上架的硬要求清单

> 调研日期：2026-10-31。问题来源：Wayfinder 研究票「微信上架的硬要求清单」。
> 对象：个人主体（个人开发者，非企业）发布的 BLE 蓝牙控制类微信小程序（lumen：ESP32-C3 + WS2812B 灯带，BLE 直连）。
> **本文只记录证据，不做决策。**

## 一、隐私保护指引与蓝牙权限

### 结论

1. **必须申报**。蓝牙属于《小程序用户隐私保护指引》明列的「处理的信息」之一，对应的是 `wx.authorize({scope:'scope.bluetooth'})`、`wx.openBluetoothAdapter`、`wx.createBLEPeripheralServer`。**官方明确**。
2. **未申报的后果是「接口直接禁用」**，不是「审核被拒」这一种。官方原文：「仅有在指引中声明所处理的用户信息，才可以调用平台提供的对应接口或组件。**若未声明，对应接口或组件将直接禁用**」。**官方明确**。
3. 申报之后还有第二层：**必须让用户同意过隐私政策**才能调用。开发者要「同步微信当前用户已阅读并同意小程序的隐私政策」后才可调用已声明的接口。**官方明确**。
4. `wx.requirePrivacyAuthorize` **不是必须调用的**。官方原文：「不是，`wx.requirePrivacyAuthorize` 只是一个辅助接口，可以根据实际情况选择使用」。**官方明确**。
5. 触发时机：只要「用户触发了一个微信侧未记录过同意的隐私接口调用」就会触发 `wx.onNeedPrivacyAuthorization`；若开发者未响应，微信会**自动弹官方隐私弹窗**。**官方明确**。
6. 与审核的关系：提审时会做**隐私协议与代码的调用一致性比对**。官方原文：「若提交审核的开发版本，其隐私接口调用情况与隐私协议内容有出入，或隐私协议内容为空，则**在提审时会提醒开发者进行更新**」（即拦截提审，不是直接驳回）。**官方明确**。

### 依据

官方文档原文（隐私协议开发指南）：

> 「需要注意的是，仅有在指引中声明所处理的用户信息，才可以调用平台提供的对应接口或组件。若未声明，对应接口或组件将直接禁用。」

> 「配置完成后，对于每个使用小程序的用户，开发者均需要同步微信当前用户已阅读并同意小程序的隐私政策等收集使用规则后，才可以调用已声明的接口或组件。」

隐私接口对照表（原文摘录）：

| 处理的信息 | 接口或组件 |
|---|---|
| **访问你的蓝牙** | `wx.authorize({scope: 'scope.bluetooth'})`、`wx.openBluetoothAdapter`、`wx.createBLEPeripheralServer` |

`wx.requirePrivacyAuthorize` 文档原文：

> 「基于上述特性，开发者可以在调用任何真实隐私接口之前调用 wx.requirePrivacyAuthorize 接口来模拟隐私接口调用，并触发隐私弹窗逻辑。」
> 「一定要调用 wx.requirePrivacyAuthorize 接口吗？ 不是，wx.requirePrivacyAuthorize 只是一个辅助接口，可以根据实际情况选择使用。」

官方隐私弹窗兜底逻辑（原文）：

> 「当开发者调用隐私相关接口时，微信会判断此次调用是否需要触发 wx.onNeedPrivacyAuthorization 事件，若触发后开发者未进行响应，微信将主动弹出官方弹窗。若用户同意，该接口将正常执行后续调用逻辑；若用户拒绝，将进行报错。」
> 「……若距上次用户拒绝不足 10 秒，将不再触发弹窗，直接给到开发者用户拒绝隐私授权弹窗的报错。」

生效时间线（原文）：「2023.09.14 更新：隐私相关功能启用时间延期至 2023年10月17日。……在 2023年10月17日之后，不论 app.json 中是否有配置 `__usePrivacyCheck__`，隐私相关功能都会启用。」

- 官方未说明「声明了蓝牙但代码里从未调用」是否算违规（过度申报）。**查不到**。

## 二、账号注销入口

### 结论

1. **微信没有一条「必须提供账号注销入口」的明文强制要求。** 检索了《微信小程序平台运营规范》《常见拒绝情形》全文，均**无**「账号注销」强制入口条款。这是本次调研里最容易被误传的一条。**官方明确（以「无此要求」的形式）**。
2. 官方**真正强制**的是两条，且都**以「存在账号体系」为前提**：
   - 常见拒绝情形 3.5.5：「如果小程序有账户系统，**必须提供能正常使用且易于发现的「退出」账户选项**。」**官方明确**
   - 运营规范 2.12 技术实现规范 6：「微信小程序内存在账号体系时，**必须提供微信授权登录**」；「应提供功能正常且易于发现的「退出」选项」。**官方明确**
3. 关于「注销」的官方原文只有一处，是**数据处理义务**而非**入口义务**：常见拒绝情形 3.4.1「……并应在**用户注销账号后**应相应删除相关数据。」——它假设了注销会发生，但没要求你必须做注销按钮。**官方明确**
4. 运营规范 2.15 给的是「**向用户提供修改、删除用户数据的方式**」这条更宽的义务：「微信小程序应当向用户提供修改、删除用户数据的方式，确保用户要求删除其用户数据时可通过该方式自行操作完成」。**官方明确**
5. 对**没有账号体系**（只有 openid 静默登录、无注册流程）的工具类小程序：**官方文档没有为这种形态单列规则**。逻辑上本案不构成「账户系统」（无注册、无密码、无用户可见账户），因此 3.5.5 的「退出」义务不成立。**推测（基于条文语义，无直接官方判例）**。
6. 社区一致意见：**没有账号体系时，可以不提供退出/注销**，关键是「不要让用户点任何功能都要求先登录」，让游客身份能体验。**社区实践（仅摘要）**。

### 依据

官方原文（常见拒绝情形 3.5.5）：

> 「3.5.5 如果小程序有账户系统，必须提供能正常使用且易于发现的"退出"账户选项。」

官方原文（运营规范 2.12 第 6 条 授权登录）：

> 「• 微信小程序内存在账号体系时，必须提供微信授权登录。
> • 如果用户选择拒绝授权，你可以在用户表现出向你授予权限的意向后再再次提醒他们。
> • 应提供功能正常且易于发现的"退出"选项。」

官方原文（运营规范 2.15 数据安全）：

> 「微信小程序应当向用户提供修改、删除用户数据的方式，确保用户要求删除其用户数据时可通过该方式自行操作完成，并确保相关数据不可恢复、不可撤销地被完全删除。」

官方原文（常见拒绝情形 3.4.1）：

> 「……并在用户注销账号后应相应删除相关数据。」

社区（微信开放社区，三帖标题一致指向同一问题，摘要可读）：
- 「请问微信小程序如果暂时没有提供账号注销功能审核会不通过吗?」→ 摘要：「问题不大，只要能让未登录的用户（即游客身份）简单体验小程序即可……不要让用户点任何功能都需要先进行登录」
- 「小程序需要提供给用户注销功能吗?」
- 「小程序规范中是否必须要有退出登录或切换账号的功能?」

链接（社区帖需登录，仅作来源记录）：
- https://developers.weixin.qq.com/miniprogram/product/ （运营规范）
- https://developers.weixin.qq.com/miniprogram/product/reject.html （常见拒绝情形）

### 未查到 / 不确定

- **没有找到任何官方判例**说明「无账号体系但不提供注销」会被拒。也**没有**找到相反判例。因此「会不会被拒」= **查不到**，只能按条文语义判为低风险。
- 官方未定义「账户系统」的边界（openid 自动登录算不算）。**查不到**。

## 三、类目风险（个人主体没有「工具-设备管理」）

### 结论

1. **「工具-设备管理」确实不对个人主体开放。** 三重官方证据互相印证：
   - 《微信小程序平台开放的服务类目》**个人主体**分支的「工具」下只有：记账、日历、天气、办公、图片处理、计算器、报价/比价、信息查询、预约/报名、健康管理、备忘录。**没有「设备管理」**。**官方明确**
   - 非个人主体分支的「工具」下才有「设备管理：适用于提供智能设备连接、管理、操控服务」。**官方明确**
   - 《小程序备案服务内容选择指引》里更直白：「19、设备管理：适用于提供智能设备连接、管理、操控服务（**个人主体不可从事**）」。**官方明确**（这条同时说明它卡的是**备案**，不只是代码审核）
2. **BLE 本身不需要「设备管理」类目。** 蓝牙框架文档、`wx.openBluetoothAdapter` 等 API 文档**通篇没有**类目/资质要求，只有 `scope.bluetooth` 授权。真正需要「设备管理」类目 + 微信认证非个人主体的是**「硬件设备接入」**（换取 `model_id`，用于**设备消息**、音视频通话等平台侧硬件能力），官方原文：「接入条件：**经过微信认证的非个人主体小程序**」。**官方明确**
   → 这是一个关键区分：**lumen 走 BLE 直连，不申请 model_id、不用设备消息，就不触发「设备管理」类目门槛**；但反过来说，**类目上也就没有「设备管理」这个名正言顺的选项**。
3. **个人主体挂「工具-信息查询」或「工具-办公」的通过率：查不到可靠数据。** 没有官方口径，也没有找到可信的、可复现的同类案例统计。**查不到**。
4. **类目不符的判定机制是明确的**：运营规范 2.5.7 第 1 条把「主体未开放类目」单列为违规，原文：「微信小程序实际提供的服务，超出其主体类型所支持的类目范围，包括但不限于：**个人主体提供的服务，超出个人主体小程序开放的类目范围**」。处理规则：「一经发现，平台将**提醒开发者限期调整**，如未申请通过相关类目或下架相关服务，将根据违规程度对该小程序**封禁能力直至下架**处理」。**官方明确**
5. **类目不符的典型驳回表现**（社区 + 官方模板一致）：驳回文案形如「你的小程序实际所提供的服务属于尚未开放的服务类目」「存在个人主体小程序未开放的服务类目」，整改建议固定为「2 选 1」：①申请企业主体小程序，补类目后合规提审；②自查代码，移除相关服务内容与分类标签。**社区实践 + 官方指引文档摘要**
6. **「工具-信息查询」的实际匹配度**：官方对「信息查询」的释义是「适用于提供信息查询等服务」。灯带控制既不是「查询」，也很难被解释为「办公」。**推测：类目本身与功能不匹配，属于审核员自由裁量的高风险区，无公开通过率数据。**

### 依据

个人主体「工具」类目原文（《开放的服务类目》个人主体分支）：

> 记账 / 日历 / 天气 / 办公 / 图片处理 / 计算器 / 报价·比价 / **信息查询** / 预约·报名 / 健康管理 / 备忘录
> 「信息查询 …… 适用于提供信息查询等服务。」

## 四、备案链路

### 结论

1. **小程序备案是上架硬阻塞**。未备案无法发布，官方给出的错误码有明文：`"errcode":86369,"errmsg":"小程序上架需先完成备案"`。**官方明确**
2. **个人主体可以完成小程序备案**，**数量上限 5 个**。原文：「个人主体备案小程序数量上限为5个；个体工商户备案小程序数量上限为5个；企业、政府、媒体、其他组织主体小程序备案数量上限50个。」**官方明确**
3. **时长**（原文）：「平台初审将会在 **1-2 个工作日**内完成；备案初审因不合规被驳回，重新修改提交后的审核时效为 **7 个工作日**；各省通信管理局将在 **1-20 个工作日**内（具体以实际审核时间为准）完成审核」。另有工信部短信核验硬约束：「你需要在收到短信的 **24 小时**内完成短信核验，否则会被系统自动退回」。**官方明确**
   → 现实预期：**约 1 周到 1 个月**，取决于省管局。**推测（基于官方区间）**
4. **后端 API 域名必须 ICP 备案**。原文：「域名必须经过 ICP 备案」。这是 `服务器域名` 配置的前提。**官方明确**
5. **HTTPS 端口规则（容易踩坑）**，原文：「对于 https 域名，可以配置端口，如 `https://myserver.com:8080`，但是配置后**只能**向 `https://myserver.com:8080` 发起请求。如果向 `https://myserver.com`、`https://myserver.com:9091` 等 URL 请求则会失败。**如果不配置端口**……那么请求的 URL 中**也不能包含端口，甚至是默认的 443 端口也不可以**。如果向 `https://myserver.com:443` 请求则会失败。」另外：「不支持配置父域名，使用子域名」「域名不能使用 IP 地址（小程序的局域网 IP 除外）或 localhost」。**官方明确**
6. **未备案域名在正式版里能不能调用：不能。** 开发期可用开发者工具「不校验合法域名」绕过；手机上则必须打开调试模式才会跳过校验（原文：「在微信开发者工具中，可以临时开启『开发环境不校验请求域名、TLS 版本及 HTTPS 证书』选项，跳过服务器域名的校验。此时，在微信开发者工具中及手机开启调试模式时，不会进行服务器域名的校验。」）。**官方明确**
   → 这就是社区反复出现的「体验版正常、正式版蓝牙/接口失败」的根因之一。
7. **小程序备案 与 域名 ICP 备案的先后关系：官方没有规定顺序。** 两者是**独立的两条链路**，只是都必须在上线前各自完成：小程序备案属于**微信平台 + 省管局**（针对小程序本体）；域名 ICP 属于**工信部 + 接入服务商**（针对网站/域名）。**查不到任何官方排序要求**。

### 依据

备案失败错误码（原文）：

> 「3、小程序因为没备案导致发布失败，返回的错误码是？
> `"errcode":86369,"errmsg":"小程序上架需先完成备案"`。」

数量上限（原文）：

## 五、审核演示材料

### 结论

1. **官方文档没有任何一节讲「审核演示视频」**。检索了运营规范、常见拒绝情形、发布流程、备案文档，均**未出现**「演示视频」「录屏」作为审核材料的表述。**官方明确（以「无此要求」的形式）**。
2. **官方明文承认的替代材料只有两类**：
   - **测试账号**（原文：运营规范 2.11 第 5 条「若小程序中存在账号关系或付费内容，**需提供测试号，包含账号和密码**，保证审核者可以体验所有功能」；常见拒绝情形 3.3.4 同义）。**官方明确**
   - **功能页面配置**：提审时「填写重要业务页面的类目与标签，重要业务页面组数不多于5组」。**官方明确**
3. **提交入口：就是提审时的「信息填写页面」**（版本管理 → 开发版本 → 提交审核 → 按页面提示填写）。官方原文：「在开发版本的列表中，点击 提交审核 按照页面提示，填写相关的信息」。**官方明确**
   该页面同时是隐私协议的第二个填写入口（官方原文：「入口2：「管理 - 版本管理 - 提交代码审核 - 信息填写页面」」）。**官方明确**
4. **测试账号入口的一个硬细节**：第一次提审如果被判定需要测试账号，会先被打回；**第二次提审才开放填写入口**。官方原文：「当小程序需要开发者提供测试账号才能完成审核体验时，小程序在**首次提交审核时将被打回，再次提交审核时将开放提供测试账号的入口**」。**官方明确** —— 这条意味着「第一次提审几乎必然浪费一次」。
5. **审核员无法验证功能时的实际驳回文案**（社区广泛引用，多条独立来源一致）：
   > 「你的小程序服务核心功能无法完整体验，请完善服务功能后再提交代码审核」
   以及变体：「小程序功能无法完整体验，请在下一次提交审核时提供有效测试帐号及密码或小程序截图、运行视频，在**小程序测试信息填写栏/版本描述/备注**处附上」。
   **社区实践（多篇一致：知乎专栏、博客园、搜狐/CSDN 转载）**
   → 注意：**「运行视频」是被驳回后才出现的补救提示，不是官方文档里的主动要求**。
6. **「模拟模式 / 演示模式」：没有任何官方说法。** 官方文档中不存在「模拟模式」「演示模式」作为过审手段的概念；唯一相关的官方表述是「开发者工具上只能模拟部分蓝牙接口能力，完整功能请使用真机调试」，那是**开发调试**语境，与审核无关。**官方明确（以「无此说法」的形式）**。
7. BLE 专用的一条社区经验：**不要让小程序的核心流程强依赖「必须先连上一台真实设备」**；否则审核员一进来就走不通，直接踩「核心功能无法完整体验」。官方规范侧的依据是常见拒绝情形 3.1.5「小程序的功能应具有使用价值，不能过于简单」与 3.3 可用性和完整性，但**「必须有离线可体验路径」这句话官方没写**。**社区实践 + 规范外推**

### 与本项目最相关的 3 条

- **#1 功能过简**：v3 的设备列表 / 多灯带 / 分段 / 剧本正好压制这条，是已有的结构性优势。

## 对本项目的具体影响

### 上架前必须先解决的硬阻塞

1. **隐私指引申报 + 隐私同意同步**（第一节）。这是唯一一条「不做就连功能都跑不起来」的：未申报 → `wx.openBluetoothAdapter` 直接禁用。工作量小，但漏了就是全盘皆输。
2. **小程序备案**（第四节）。`errcode 86369` 是硬门。个人上限 5 个不是问题（本项目只 1 个），但**1-20 工作日的管局时长必须进排期**，不能等代码写完才想起来。
3. **后端域名 ICP 备案 + 端口配置一致性**（第四节）。文档只登记设备与使用日志，但**只要用到 `wx.request`，域名就必须备案**。端口规则（配了端口就必须带、不配就连 `:443` 都不能写）是最容易在联调末期炸的细节。
4. **提审信息页面填全**（第五节）。测试账号入口第二次提审才开放，意味着**第一次提审可以预期被打回**，要预留一次往返。

### 只是风险（不阻塞开工，但影响能否真上架）

1. **类目**（第三节）。这是本清单**最大的不确定项**：个人主体没有「设备管理」，只能挂「工具-信息查询/办公」，而官方对这两个类目的释义（「信息查询」「办公工具」）与灯带控制都对不上；**没有任何可靠的同类成功案例可参照**，也没有公开通过率。运营规范 2.5.7 把「个人主体超出开放类目」单列为违规，处理是「限期调整 → 封禁能力 → 下架」。**换句话说：技术上完全可行，制度上可能是死路。**
2. **审核员无法验证**（第五节）。审核员手上不会有灯带。官方只认测试账号，不认「模拟模式」；「运行视频」只出现在驳回文案里。**建议在架构上就让"没设备"也能走通完整流程**（设备列表、分段编辑、剧本编辑都可离线操作，只有"下发"需要真机），这是把风险降级为可控的最实际手段。
3. **功能过简**（第六节）。v3 的设备列表 / 多灯带 / 分段 / 剧本已经结构性解决了这条，**不构成风险**。
4. **「账号注销」是被误传的要求**（第二节）。官方没有这条强制条款；强制的是「有账户系统时必须能退出」。本项目**不建账号体系**（openid 静默）就完全不触发。反过来，如果为了"看起来合规"而硬加一个注册/注销流程，**反而会把自己拖进 3.5.5 与 2.12 的账户体系义务里**。

### 一句话总结

**技术上个人主体 100% 能做完这个产品；真正的风险不在代码，在类目。** 隐私与备案是"照着做就能过"的体力活，类目是"做了也未必能过"的制度题，审核演示是"靠产品设计缓解"的概率题。
