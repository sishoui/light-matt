# 灯带效果模拟器

在**不接真机、不开摄像头**的前提下，看到 8 条灯带逐颗灯珠会显示什么颜色。

```bash
python scripts/simulate-strips.py           # 32 项断言 + 出图
python scripts/simulate-strips.py --csv     # 另外打印逐颗 RGB
```

产物落在 `.sim-out/`：每个场景一张 `<name>.png`（8 条并排的横向色块），
多帧场景另有一张 `<name>-frames.png`（时间线），外加 `report.md`。

---

## 1. 为什么它不是「另写一套模拟」

`firmware/sim/sim_main.c` **不重新实现任何灯效逻辑**。它链接的是生产固件的那几个
文件：

| 文件 | 它决定什么 |
|---|---|
| `effects.c` | 八种灯效的像素公式、blend 合成、层亮度 |
| `segment_store.c` | 段的形状校验、`SetSegment` 的合法性与合成入口 |
| `gamma.c` | 用户空间 → 灯珠输出的 gamma 曲线 |
| `led_render.c` | `compose_frame`：未覆盖区清零、逐颗施加 gamma + 全局亮度 |
| `state.c` / `strip_power.c` | 默认值、每带开关门控 |

模拟器只提供两样东西：一个假的 `lumen_led_strip_owner_push_pixels`（把「刷 RMT」
换成「留在内存里」），和一个 JSON 输入输出壳。

**因此像素与真机逐字节同源。** 模拟里看到的绿色就是设备上的绿色，不是近似。

---

## 2. 它能证明什么，不能证明什么

**能证明**（这些都是段语义与数值合成）：

- 哪条灯带有分区、哪条没有，以及「没有分区 = 全黑」；
- `blend` 三种取值的像素结果，包括 `0x03` 按亮度叠加；
- 层 `level`、全局 `brightness`、gamma 的合成顺序；
- 动画在不同时刻的相位（流星走到了第几颗）。

**不能证明**（必须真机）：

- **WS2812B 的色域压缩**——真实灯珠上 `255,180,120` 看着是黄，模拟里是暖白；
- **电源压降**：满亮 8×100 颗时的实际颜色会掉；
- **RMT 时序与 BLE 共存**：帧率、丢帧、闪断。

这三项在报告里会明写，不会被当成「模拟通过 = 真机通过」。

---

## 3. 六个场景

| 场景 | 配置 | 断言要点 |
|---|---|---|
| `zero-zones` | 8 条带都没有分区 | 全部纯黑（曾经的「所有引脚亮黄」） |
| `only-strip0` | 只有 strip 0 有静止彩虹 | 其余 7 条逐颗为 `(0,0,0)` |
| `only-strip0-hue` | 同配置换一个色相 | 与上一条**跨场景比对**：strip 1–7 逐字节不变 |
| `luma-blend` | 彩虹 + 白光流星，`blend=0x03` | 同一帧里既有近白亮处，又留 ≥10 颗彩色；画面随时间变化 |
| `over-blend` | 同配置 `blend=0x00`（旧行为） | **对照组**：黑点数 > 彩色点数，证明背景被吃掉 |
| `luma-on-solid` | 纯蓝背景 + 流星，`blend=0x03` | 亮处近白、暗处仍是背景蓝 |

`over-blend` 是对照组，不是冗余：没有它，「`0x03` 看起来对」可能只是巧合；有了它，
`0x00` 与 `0x03` 的差异才是被测行为本身的证据。

---

## 4. 两个实现陷阱（都实际踩过）

**阈值要按实测峰值定，不能按 255。** `brightness=200` 再过 gamma，满亮通道实测只到
**165**。第一版判据写 `max > 200` 找「近白亮处」，永远匹配不到，把「判据写错」误报成
「固件坏了」。现在一律用 `peak = 本帧最亮通道` 的百分比。

**`cv2.imwrite` 写不了含中文的路径。** 本仓库路径有 `项目`，OpenCV 按 ANSI 打开文件，
静默返回 `False` 且一个字节都不写——表现是「断言全绿但一张图都没有」。改用
`cv2.imencode` 在内存里编码，再用 Python 文件对象落盘。

---

## 5. 编译依赖

模拟器用系统 `gcc` 编译，需要三个桩头文件（`esp_log.h` / `sdkconfig.h` /
`esp_err.h` / `led_strip.h` / `esp_timer.h`）。这些由
`scripts/simulate-strips.py` 的 `build_simulator()` 自动生成到临时目录，不需要手工准备，
也不需要 ESP-IDF 工具链。

唯一预期内的编译告警是 `led_render.c` 的 `TAG` 未使用——桩头把 `ESP_LOGI` 变成了
空操作，真实固件里它被引用。

## 6. 3D 效果图（`scripts/render-3d.py`）

把同一份逐颗色值画成自发光灯珠的 3D 视图。

```bash
python scripts/render-3d.py                                   # 默认对准设备当前配置
python scripts/render-3d.py --rainbow-level 40 --comet-level 100
python scripts/render-3d.py --layout ring --elev 60 --dist 25
```

**色值是真的，几何是假设的。** 亮度与 RGB 来自上面那套固件真实渲染链；8 条带的
空间排布是**名义假设**（平行、等距、沿纵深展开）。真实几何没有 3D 数据可依：
`.strip-layout.json` 只有 2D 像素坐标，而且那台机位拍不到灯带本体。

### 只做两件事

1. **透视投影**——让纵深成立；
2. **加法混合的辉光**——灯珠是自发光光源，加漫反射 / 高光是错的（会把「固件输出
   这个色值」变成「这个色值在某种光照下大概长这样」，引入新的不确定性）。

加法混合必须**在线性空间**做（先反 gamma、累加、再转回 sRGB）。在 sRGB 空间直接
相加会让相邻光斑过早饱和成白块。

### 曝光适应（**不做就会误判**）

第一版按 255 归一化，`level=5` 配置渲染出来整片糊黑，看起来像「固件没输出光」。
真实情况是那档配置峰值只有 `11/255`，而人眼和相机在暗房里会为暗场景放大进光量，
所以 5% 的彩虹依然清晰可辨。

现在按**画面里最亮的灯**自动定曝光（`--exposure-target`，默认 0.92），增益上限
`--max-gain 14`，并把实际倍数写进角标。渲染结果因此在极暗配置下仍能看清结构。

> 这是渲染器的责任，不是灯的规律：**按 255 归一化把「暗」误读成了「没输出」**。

### 层亮度是线性乘算，直觉会骗人

`level=10` 的流星头是 `(11,7,7)`，`level=100` 是 `(165,165,165)`——掉了约 15 倍。
因为 `165 × 10% ≈ 16.5`，过 gamma 后就是 11。这是协议的正确行为（§9.3 在用户空间
乘 `level`），但「10%」这个数字给人的预期是「留一成亮」，两者差得很远。
