## Problem Statement

MVP 能用，但只够控一条灯带、一个颜色。真实使用里有四件事做不了：

1. **一条灯带只能整条一个颜色。** 想把前 10 颗当夜灯、后 40 颗当背景，做不到。调亮度时整条一起变，没有层次。
2. **只能是静态色。** 呼吸、彩虹、流光这些让人愿意长期开着的效果，一个都没有。灯带只能当「一盏能变色的灯」，不能当氛围。
3. **一条线只能接一条灯带。** 手上要接第二条就得再买一块板子、再多连一次蓝牙。想要 8 条一起亮，现在的固件连驱动通道都不够。
4. **换一台设备就得清缓存。** MVP 验收时就暴露了：断开后点状态条只会重连缓存的那一台，没有「换一台」的入口，只能清缓存或重启小程序。

还有一个隐性成本：用户有多台设备、想记录谁什么时候用过，现在没有任何地方存这些信息。

## Solution

四个方向一起推进，但共享同一套底层改动：

- **多分段**：一条灯带按灯珠区间切成最多 8 段，每段独立颜色/灯效。未覆盖的灯珠必须熄灭。
- **多灯效**：固件内置静态单色、呼吸、彩虹、流光四种程序化灯效，小程序只下发「类型 + 参数」，不推像素流。
- **多阶段**：把「阶段序列」做成剧本，每个阶段覆盖全段、有固定时长，固件自己跑时间轴，设备存多套剧本。
- **多引脚**：8 条独立灯带，用 TDM 轮询（C3 只有 2 个 RMT 发射通道），靠 WS2812B 锁存保持画面。
- **多设备**：小程序单连接 + 快速切换，补上「设备列表 / 换一台」的入口；后端只记使用日志，不做归属、不做远程控制。
- **管理后台**：只读看板，看设备使用日志与用户列表。

底层统一到**协议 v2**。v2 不向后兼容——MVP 只是试验，不为旧版本留降级路径。现场那台 64 灯设备重刷固件即可，没有第三方在用。

## User Stories

### 多分段

1. 作为用户，我希望把一条 64 灯的灯带划成最多 8 个灯珠区间，以便不同区域显示不同颜色。
2. 作为用户，我希望每一段可以独立选颜色，以便「前 10 颗暖白当夜灯、后面蓝色当背景」。
3. 作为用户，我希望每一段可以独立选灯效，以便一段呼吸、一段常亮。
4. 作为用户，我希望划段时能直接看到边界对应的灯珠，以便不用靠数数猜位置。
5. 作为用户，我希望段与段之间不重叠，以便不会出现两个段抢同一颗灯珠。
6. 作为用户，我希望没有被任何段覆盖的灯珠保持熄灭，以便不会出现「旧颜色残影」。
7. 作为用户，我希望修改某一段时只有那一段变化，其他段不动，以便调一段不会整条跳变。
8. 作为用户，我希望分段配置在断电重启后恢复，以便不用每次重划。
9. 作为用户，我希望段数上限是 8，以便在表达力和操作复杂度之间取得平衡。

### 多灯效

10. 作为用户，我希望有「静态单色」灯效，以便只想要一个颜色时不去碰动画。
11. 作为用户，我希望有「呼吸」灯效，并且能调呼吸快慢，以便夜里长时间开着不刺眼。
12. 作为用户，我希望呼吸能设置「最暗时有多暗」，以便不会完全黑掉、看起来像坏了。
13. 作为用户，我希望呼吸有正弦 / 三角 / 锯齿 / 方波几种波形，以便不同心情用不同质感。
14. 作为用户，我希望有「彩虹」灯效，并且能选择「整条同色循环」还是「沿灯带铺满一圈」，以便两种观感都能要。
15. 作为用户，我希望彩虹能调色相跨度，以便从「几乎单色微变」到「完整彩虹」连续可调。
16. 作为用户，我希望有「流光」灯效，并且能调尾部长度，以便从硬边亮点到长拖尾。
17. 作为用户，我希望所有动画都能调速度，并且慢到几乎静止、快到有流动感。
18. 作为用户，我希望所有动画都不超过安全闪烁频率（呼吸 ≤3Hz、彩虹/流光 ≤5Hz），以便不会引发光敏不适。
19. 作为用户，我希望动画速度超出安全范围时被明确拒绝，以便我知道这个值设备不接受。
20. 作为用户，我希望反转方向的选项，以便流光可以从另一头开始。
21. 作为用户，我希望动画在手机断开后继续跑，以便锁屏或走出房间也不中断氛围。
22. 作为用户，我希望设置一个设备不认识的灯效时收到明确错误，而不是静默变成别的效果，以便知道需要升级固件。

### 多阶段（剧本）

23. 作为用户，我希望把多个阶段串成一个剧本，每个阶段有固定时长，以便做出一段「灯光小节目」。
24. 作为用户，我希望一个阶段覆盖全部段（每段各自的灯效设定），以便阶段切换是整体切换。
25. 作为用户，我希望一套剧本最多 8 个阶段，以便足够表达一段简单节目。
26. 作为用户，我希望剧本能循环播放，以便常驻氛围。
27. 作为用户，我希望剧本只播一次也能配置，以便做一次性演示。
28. 作为用户，我希望剧本由设备自己跑时间轴，以便手机断开后节目继续演完。
29. 作为用户，我希望剧本能暂停和停止，并且在暂停后能从停止处继续，以便临时打断不丢进度。
30. 作为用户，我希望设备能存多套剧本并能在其中切换，以便不联网也能换节目。
31. 作为用户，我希望剧本下发过程中有明确进度反馈，以便知道还要等多久。
32. 作为用户，我希望剧本下发失败时设备保留上一套可用配置，而不是变成半套坏状态。

### 多引脚（8 条灯带）

33. 作为用户，我希望一块板子能驱动 8 条独立灯带，以便整面墙一次点亮。
34. 作为用户，我希望 8 条灯带能各自独立设颜色和灯效，以便不是简单的复制粘贴。
35. 作为用户，我希望 8 条灯带同时做动画时仍能保持可接受的流畅度，以便不会看到明显卡顿。
36. 作为用户，我希望某一条灯带没接时不影响其他 7 条工作，以便坏一根不瘫一片。
37. 作为用户，我希望知道 8 条灯带同时高亮时的供电要求，以便不会烧电源或掉压。

### 多设备

38. 作为用户，我希望在设备列表里看到「最近连过的设备」和「附近可用设备」，以便主动换一台而不用清缓存。
39. 作为用户，我希望点一下列表里的设备就切换过去，以便换设备不超过两步。
40. 作为用户，我希望切换时先断开当前设备再连新的，以便符合设备「单连接」的约束。
41. 作为用户，我希望切换失败时停在「未连接」并给重试入口，而不是自动来回震荡，以便知道该点哪个按钮。
42. 作为用户，我希望列表按最后使用时间排序，以便最常用的那台在最上面。
43. 作为用户，我希望后端不可达时列表仍能从本地缓存渲染，以便断网也能连上最近那台。
44. 作为用户，我希望切换设备后界面加载的是那台设备的真实分段与剧本配置，以便不会把 A 的配置显示在 B 上。
45. 作为用户，我希望知道「设备列表」不是「我的设备」，任何扫到的人都能连，以便对共享环境的预期正确。

### 后端与后台

46. 作为用户，我希望连接设备时自动记录一条使用日志，以便事后知道谁用过哪台。
47. 作为用户，我希望断网时使用记录能本地缓存、联网后补报，以便记录不丢。
48. 作为运营者，我希望有一个只读看板看到设备最后出现时间与使用次数，以便发现某台设备是否还在用。
49. 作为运营者，我希望看板能列出用户，以便知道有多少人用过系统。
50. 作为运营者，我希望后台只能看不能改，以便不会因为误操作破坏用户数据。
51. 作为用户，我希望后端不存我的实时控制通道，以便控制始终是本地 BLE 直连、低延迟。

### 协议与诊断

52. 作为用户，我希望分段/灯效/剧本的每次下发都有 ACK，以便知道哪条命令被拒绝。
53. 作为用户，我希望错误信息能区分「参数越界」和「长度不对」，以便定位是 UI 传错还是协议不匹配。
54. 作为用户，我希望重连后能快速重建界面（读到当前分段与剧本摘要），以便不会看到空白或旧数据。
55. 作为开发者，我希望隐藏日志面板能显示分段/灯效命令的原始字节，以便和串口日志逐帧对齐。
56. 作为用户，我希望设备不认识 v2 之外的命令时明确报错而不是挂起，以便排查。

## Implementation Decisions

### 协议 v2

- **不向后兼容**：`version` 从 `0x01` 升到 `0x02`。遇到未知 version 回 `UnsupportedVersion`，不尝试兼容解析。
- **信封完全沿用 v1**：magic `0xA5`、`version / command / seq / length / payload / checksum` 布局、校验和算法（求和取反）、`length` 语义都不变。可变长载荷不需要改结构——v1 第 4 字节本来就是长度字段。
- **校验顺序沿用 v1**：magic → version → length → checksum → command → payload 长度 → payload 取值。
- **seq 语义沿用**：每条连接从 `0x01` 起，回显、不去重。
- **命令字分配**：v2 可自由重排（因为不兼容），但保留「`0x80+` 为设备→小程序」的划分。
- **段配置帧**：`seg_id(1) + start(1) + end(1) + type(1) + params(3或7)`，整帧 13 或 17 字节。
- **逐段下发**：每帧独立生效，不做原子事务。中间态是接受的取舍。
- **剧本下发**：多次写入，需要批次概念与进度确认；细则由 #21 定。
- **重连重建**：需要一条「读摘要」路径 + 按段读取配置，具体命令集由 #21 定。

### 灯效引擎（固件）

- **纯函数核心**：灯效计算写成不依赖 ESP-IDF 的纯函数模块，输入「类型 + 参数 + 段内时间 + 段灯珠数」，输出一帧像素。这样能在现有 host 测试里直接测，不引入新接缝。
- **四种灯效的字节布局与公式**已定稿在 `docs/effects-spec.md`，本规格不重复。
- **整数运算**：色相、相位、包络全部定点整数，不用 `float`（C3 无 FPU）。
- **相位计算必须用 64 位中间量**：`period_ms` 最大 65535 时 32 位只剩 131072 余量，这是已踩过的坑。
- **静态与动画共存**：状态不变时不空转刷帧；动画模式下才进入持续帧循环。帧率上限待 #20 实测。
- **段合成**：每帧把各段按区间写入统一像素缓冲，未覆盖区写 0。
- **内存**：每段状态约 15 字节，8 段 120 字节，8 灯带约 960 字节。当前空闲 heap 316KB，可接受。

### 多引脚 TDM

- **C3 硬约束**：`RMT_LL_TX_CANDIDATES_PER_INST = 2`（v6.1 已确认），只有 2 个通道能发，8 条灯带必须轮询。
- **机制**：`led_strip_switch_gpio()` / `rmt_tx_switch_gpio()` 在运行时切换输出引脚，靠 WS2812B 锁存保持画面。
- **前置已满足**：ESP-IDF v6.1，符号可链接。
- **代价已知**：8 路轮询时每条灯带的刷新间隔约为单路的 8 倍，动画流畅度下降。可接受的最低帧率由 #20 实测给出。
- **`mem_block_symbols` 与通道数冲突**：整组只有 192 word，2 通道各占 48 后没有余量加大缓冲。取舍待 #20 定量。

### 持久化

- **分段配置持久化**：断电恢复。
- **剧本存多套**：设备侧存多套，支持激活切换。
- **debounce 写 NVS 沿用 v1 的 500ms 策略**，但动画相位不写 NVS（只存配置，不存相位）。
- **存储失败**仍用 Event 上报，沿用 v1 机制。

### 小程序

- **单连接 + 切换**：不并发。切换状态机需定义失败路径（停在未连接 + 重试，不自动回滚，避免震荡）。
- **设备列表**：分「最近连过」（本地缓存）与「附近可用」（实时扫描）。
- **配置加载**：切到某设备后读该设备的真实配置，不沿用上一台。
- **节流**：动画参数变化不需要 20Hz 拖动节流，但仍需写入串行化。

### 后端与后台

- **自建服务**，**纯记录**：不存实时控制通道。
- **不做归属**：没有 owner 概念，不记权限。
- **数据模型**：最小形态是「用户表 + 使用日志表」+ 两个只读视图。
- **核心难点**：同一台设备在不同手机上 `deviceId` 不同（Android 是 MAC，iOS 是 UUID），日志聚合口径需明确。
- **个人资质**：BLE 直连主线无障碍；后端域名备案在个人测试阶段可绕过。上线前需重审。

## Testing Decisions

### 已有的三个接缝（优先复用，不新造）

1. **`docs/protocol-testvectors.json`（共用向量文件）** —— 这是两端唯一的协议真相接缝。固件 host 测试和小程序 codec 测试**读同一份文件**，任何字节变化都会让两边同时失败。v2 的所有新命令、新错误路径都必须进这个文件。
2. **固件 host 测试（纯 gcc，不含 ESP-IDF）** —— 编译纯函数模块（protocol / command / state / gamma / selftest 等）直接测。**灯效计算必须落进这个接缝**：它不依赖 IDF，所以能在 PC 上验证公式、边界与溢出。
3. **小程序 vitest** —— 纯逻辑层（codec / throttle / session / 颜色 / 错误分诊）用 vitest，不碰 wx / canvas / BLE。

### 测试什么（只测外部行为）

- **协议**：向量文件驱动，逐字节比对编码结果与结果码。不测内部解析步骤。
- **灯效**：给定「类型 + 参数 + 时间」，断言输出的像素值。测边界（0 值、最大值、越界拒绝）与确定性（同输入同输出）。不测内部用什么算法近似 `exp`。
- **分段合成**：给定多段配置，断言整条像素缓冲的内容，特别是**未覆盖区必须为 0**。
- **安全上限**：呼吸 >3Hz、彩虹/流光 >5Hz 必须被拒绝，这是可外部观察的行为。
- **重连重建**：给定一串设备响应，断言最终 UI 状态正确。
- **不做 host 测试的**：TDM 引脚切换、真实 RMT 波形、BLE 时序——这些必须真机验证，不伪装成单测。

### 真机验收

- 8 引脚 TDM 的帧率与错色率：**只能实测**，由 #20 出数字。
- 多分段断电恢复：真机断电重上电看各段是否恢复。
- 不连续的空白区间（如 [0-15] 与 [40-63]）必须真机确认中间确实熄灭。

## Out of Scope

- **WiFi / 云端实时控制 / 远程点灯**。后端只存配置与日志，控制仍走 BLE。
- **设备端脚本 / 字节码解释器**。已否决，走类型枚举 + 参数块。
- **音乐律动 / 音频同步**。
- **每段独立时间轴**。已定为「阶段覆盖全段」。
- **设备间联动分组**（多台同步跑同一剧本）。
- **设备共享与角色体系**。
- **硬件改版**：PCB、外壳、74AHCT125 落板、量产 BOM、8 路供电方案。
- **v1 兼容层**。
- **微信支付 / 电商销售**（个人主体不可用）。
- **OTA 升级**。

## Further Notes

### 必须先知道的三个风险

1. **TDM 的实际表现全部未知。** 工具链通了（v6.1 + `rmt_tx_switch_gpio` 可链接），但 8 路轮询的真实帧率、错色率、与 `mem_block_symbols` 的取舍**一个数字都没有**。这些由 #20 实测，是 #22 动画帧率设计的前置。
2. **电流预算未定。** `max_brightness=200` 是按静态纯白 64 灯定的（约 3.0A）。动画可能让更多灯珠同时高亮，8 条灯带时总电流 ×8。用户明确决定**先不加限流，等实测**。固件禁止偷偷加系数，否则实测数据失去意义。
3. **官方文档明确记载 C3 的 RMT 在开 BLE 时会出现数据帧异常**（无 DMA + ISR 切缓冲，C3 不能用「换核」缓解）。动画持续刷新会放大这条风险。

### 版本策略

**不做任何旧版本兼容。** MVP 只是试验。`idf_component.yml` 已钉 `idf: ">=6.1"`；遇到版本问题就升到最新，不迁就旧版。

### 已定的取舍（不要在实现时「修复」）

- **逐段下发会看到灯带逐段变化**——设计取舍，不是闪烁缺陷。
