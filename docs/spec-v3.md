## 0. 这一版解决什么问题

v2 把多段、多灯效、多阶段、多灯带、多设备都做进了**固件和协议**，但**小程序没跟上**：

| 能力 | 固件 v2 | 小程序 v2 | v3 要补的 |
|---|---|---|---|
| 8 条灯带 | ✅ TDM 轮询 | ❌ `PRIMARY_STRIP_ID = 0` 写死 | App 层全部打通 |
| 分段 | ✅ 每带 8 段 | ⚠️ 只操作 strip 0 | 选带 + 每带独立编辑 |
| 多灯效 | ✅ 4 种，一段一效 | ✅ 单层可用 | **同段两层叠加** |
| 多阶段 | ✅ 4 套 × 8 阶段 | ⚠️ 下发能用，读不回来 | 读回、编辑、可视化 |
| 设备列表 | — | ⚠️ 弹层、本地 8 条 | 独立页 + 后端登记 |
| 每带开关 | ❌ | ❌ | 新增命令 |

核心判断：**这一轮主战场是小程序，固件是"补齐 + 放开"**。固件已有的多带/多段/多阶段能力，
需要在协议层补上三样东西才能真正用起来：每带独立开关、每带配置可查询、设备身份可查询。

## 1. 数据模型的三个新维度

### 1.1 灯带（strip）成为一等公民

v2 里 strip 只是段的一个字段，UI 永远填 0。v3 里灯带是**主界面的切换维度**：

- App 连上后先读 State（37B），得知 `strip_count` 和**每条带各自的灯珠数**；
- 再查 `QueryStripConfig` 得知每条带的 GPIO（只读展示）；
- 用户选一条带 → 编辑该带的段、该带的开关、该带的灯效。

**引脚不可配置。** 引脚表来自固件构建期 Kconfig，协议只读。理由：`led_strip` 句柄按
`max_count` 建一次，运行期改引脚需要重建句柄 + 处理 TDM 中断 + 处理"物理上不存在"的
降级，会放大已实测的 BLE 抢 RMT ISR 问题（`docs/rmt-ble-stability.md`）。收益（少刷一次固件）
远小于风险。

### 1.2 段（segment）变成两层

一个段 = 一个 LED 区间 + 至多两层灯效 + 一个混合模式。

**为什么共享区间而不是子区间**：如果两层各自带区间，那它就不是"一个段叠两层"，
而是"两个段重叠"——这与 v2 已定的"同带内段不重叠"直接冲突，且渲染时每颗灯珠要判定
N 个层的覆盖关系，复杂度从 O(段) 变成 O(段×层)。共享区间让"寻找覆盖段"仍是一次线性扫描。

**为什么只两层**：用户明确要"最多两层"。三层以上在 64 颗灯珠的尺度上视觉收益递减，
但段结构会从 21B 涨到 29B、NVS 记录同样膨胀，直接吃掉本就紧张的剧本容量。

**为什么 blend 只有覆盖/相乘/相加**：取最大值与相加在视觉上高度重合，多一种就多一份 UI
解释成本和测试分支。

### 1.3 阶段（stage）加 fade 字段但行为不变

`fade_ms` 在格式里预留、恒为 0、行为仍是硬切。原因：渐变过渡要在过渡期同时渲染两套阶段帧
再插值，过渡期 RMT 负载翻倍，与已实测的 BLE 抢占 RMT ISR 问题叠加。格式先占位，
避免将来加字段又要升协议。

## 2. 后端：从"纯日志"扩到"设备登记"

### 2.1 变的是什么

v2 后端只存使用日志，设备是 `v_devices` 视图从日志聚合出来的派生概念。v3 要支撑
"设备列表"，就必须有真正的设备实体。

### 2.2 不变的是什么（重要）

**后端仍然不存任何灯光配置。** 设备 NVS 是灯光配置的唯一真相。

理由不是"设计洁癖"，而是：
1. **控制链路不经过服务器**（BLE 直连）。服务器存一份配置，离线时完全用不上。
2. 双真相 = 同步冲突无解。用户在 App 改一段颜色，设备已生效、服务器还没收到，
   此时网络中断再重连，以谁为准？设备为准是唯一可解释的答案，那么服务器那份就永远可能是旧的。
3. 备份诉求可以用"从设备读回"满足——`QueryStrip`/`QueryScript` 本来就是权威路径。

后端只存**登记信息**：谁有这台设备（openid）、用户起的名字、最后在线时间、
以及一份**明确标注非权威**的缓存（灯带数、固件版本），仅用于离线时列表能显示点东西。

### 2.3 身份

| 项 | v2 | v3 |
|---|---|---|
| 设备身份 | 广播名 `Lumen-XXXX`（16 位，会碰撞） | **BT MAC 全地址**（`hw_id`，48 位） |
| 用户身份 | `local-<16hex>`，客户端自称、可伪造 | `wx.login` → openid（配了 AppSecret 时）；否则回落本地身份 |
| 归属 | 无（任何人扫到都能连） | **仍然不做权限控制**，只做"谁登记过"的展示 |

**关键取舍**：设备归属仍然**不做访问控制**。任何人扫到都能连——这是个人测试阶段的前提
（`docs/agents/issue-tracker.md` 明确记录）。`user_devices` 只回答"我见过这台设备"，
不回答"你能不能连"。

**AppSecret 可配置回落**：配了就走 openid，没配就沿用 `local-<hex>`。两种模式下设备登记
都能工作，只是前者跨设备同步、后者只在单机有效。响应里用 `identityKind` 明示当前模式，
App 据此决定要不要显示"仅本机可见"的提示。

## 3. 小程序：信息架构重构

### 3.1 为什么必须拆页

现在整个 App 是**一个 2086 行的 Page**，7 个板块纵向堆叠，全部状态挤在 `index.ts` 的
`data` 里。要新增的维度是：8 条灯带 × 8 段 × 2 层 × 8 阶段。这不是加一个板块能承受的。

### 3.2 页面结构

```
tabBar
├── 设备 devices      —— 列表 / 扫描 / 连接 / 备注名 / 删除
├── 灯光 light        —— 选中灯带的总控：开关、段列表、【每带】切换
└── 剧本 scripts      —— 阶段时间轴，跨带预览

二级页（非 tab）
├── 段编辑 segment-edit   —— 区间 + 两层灯效 + blend（从 light push）
└── 设备详情 device-info  —— GPIO / 灯珠数 / 自检 / 固件版本 / 改名
```

**灯带是"灯光页"内的横向切换器，不是独立页。** 8 条带各占一页会让导航变成 8 个入口，
而用户 90% 时间只关心 1-2 条带。横向切换（顶部 chip 或 swiper）更贴近"这是同一盏灯的不同部分"。

### 3.3 状态分层

v2 的状态全在 Page 里。v3 拆成三层，避免跨页后状态散落：

| 层 | 位置 | 职责 |
|---|---|---|
| 连接层 | `utils/control/session.ts`（单例，App 级） | BLE 连接、seq、ACK、State 镜像、每带配置缓存 |
| 设备层 | `utils/control/device-registry.ts`（新） | 设备列表、备注名、启用掩码、最近连接 |
| 页面层 | 各 page 的 `data` | 只放展示态和编辑中的草稿 |

**会话是 App 级单例**，因为小程序单连接：切页不能断链。页面通过 `getApp().session` 拿，
或在 `onShow` 里订阅。

### 3.4 编辑中的草稿与"设备权威"的冲突

用户改段参数时是本地草稿，点"应用"才下发。v2 的问题是编辑态和设备态混在一起。
v3 规则：

- 段编辑页进入时从设备读该段当前值填草稿；
- "应用"→ 下发 → 等 ACK → 重新 `QueryStrip` 该带 → 用设备返回值覆盖草稿；
- 用户离开页面未应用 → 丢弃草稿，不静默下发。

## 4. 固件要补的东西

除了**协议 v3 全套改造**（见 `protocol-v3.md` §12 迁移清单），还有几个行为性改动：

### 4.1 每带独立开关 + TDM 跳过

`SetStripPower` 关某条带时：先推一帧全黑，再让 TDM 轮询跳过该带。
副作用是**省 RMT 时间**——关掉的带不再占轮询周期，8 带全开时的帧预算因此有了余量。

### 4.2 修正 v2 已知的三处不一致

这三处在 v2 里是真实缺陷，v3 必须一起修（否则多带一打开就会暴露）：

1. `lumen_led_engine_set_segment` 的防御性再校验用 `s_state.led_count`（strip 0 的数），
   与命令层按 per-strip 校验不一致 → 统一用 per-strip。
2. `state_blob` 解码用 strip 0 的 `led_count` 校验**所有**条带的段区间 → 改为按各自带校验。
3. `SegmentReport` 的 `seg_id` 用压缩序号而非真实槽位 → v3 改为报真实槽位。

### 4.3 渲染层的合成位置

两层合成在 **用户空间**完成，之后**统一**过 gamma + 全局亮度。两层都不得自行做 gamma 或亮度。
否则"彩虹 + 呼吸相乘"会在 gamma 后相乘，暗部被压得过狠。

## 5. 测试策略

### 5.1 固件 host 测试（无硬件）

- 协议编解码：用 `docs/protocol-testvectors-v3.json` 全量跑（含 CRC、分片、非法帧；用例数以 JSON 文件为准）。
- 两层合成：纯函数，枚举 blend × 层类型组合，断言输出值。
- 段校验：合法/非法矩阵（空 layer0、单层带 blend、未知 type、区间重叠、周期下限）。
- 剧本容量：断言"能 commit 的一定能 encode 进 16KB"，构造最坏用例验证回 `ScriptTooLarge`。
- blob 往返：state v4 与 script v2 的 encode→decode 幂等。

### 5.2 小程序单元测试（vitest，288 例基线）

- 新信封 + CRC16 + 分片重组（用同一份 v3 向量）。
- 分片边界：正好 179、180、跨越 2 片、重组超时、FIRST 重入丢弃旧缓冲。
- 段两层编码/解码、blend 校验、State 37 字节解析。
- 设备列表与"启用掩码"的本地持久化。

### 5.3 真机验收

| 项 | 判据 |
|---|---|
| 8 条带各自独立设色 | 每条带颜色不同且互不干扰 |
| 每带独立开关 | 关一条带，其余继续跑动画 |
| 两层叠加 | "彩虹 + 呼吸相乘"能看出明暗波动且颜色不畸变 |
| 段不重叠 | 划重叠被拒，且提示明确 |
| 剧本读回 | 断连重连后能从设备读回已提交剧本 |
| 剧本过大 | 构造超限剧本，`ScriptCommit` 回 0x0A 且界面明示 |
| 多设备切换 | 3 台设备来回切，不残留上一台的段数据 |
| 8 带 20fps 稳定性 | 沿用 #20 的录像分析法，错色率不高于 v2 基线 |

## 6. 执行顺序与依赖

这一轮的核心风险是**协议变更必须两端同时改**，中间态不可用。所以先做无协议依赖的部分，
再做协议切换。

| 阶段 | 内容 | 依赖 | 可独立验证 |
|---|---|---|---|
| A | 协议 v3 契约 + 向量生成器 | — | ✅ 本文 + `protocol-v3.md` + JSON |
| B | 固件协议层（信封/CRC/分片/blob）+ host 测试 | A | ✅ host 测试 |
| C | 固件两层引擎 + 每带开关 + TDM 跳过 | B | ✅ host 测试 + bringup 工程 |
| D | 小程序协议层（frame/commands/types）+ 单测 | A | ✅ vitest |
| E | 小程序拆页 + 灯带维度 + 段编辑（两层） | D | ⚠️ 需 D |
| F | 后端设备表 + 会话 API | A | ✅ server 测试 |
| G | 小程序设备页 + 后端同步 | E+F | ⚠️ 需 E,F |
| H | 端到端真机验收 | C+E+G | ✅ 真机 |

**A 是唯一的全局闸门**，B/C 与 D/E 可以并行（两端各自对着同一份向量实现）。
F 与 B/C/D/E 完全独立，可以随时插队。

## 7. 明确不做的事

| 不做 | 原因 |
|---|---|
| 运行期改引脚映射 | 见 §1.1，风险 >> 收益 |
| 每带独立亮度 | 全局调光是最常用操作，下放后变别扭。已定：只有每带开关 |
| 三层及以上叠加 | 见 §1.2 |
| blend 取最大值 | 与相加视觉重合 |
| 阶段间渐变过渡 | `fade_ms` 只预留格式，行为硬切（RMT 负载翻倍） |
| 后端存灯光配置 | 见 §2.2，双真相无解 |
| 设备归属访问控制 | 个人测试阶段前提，只做登记展示 |
| 剧本批量上传 | 逐段一帧，典型场景 12 帧、体感瞬时 |
| 离线编辑后同步 | 设备是唯一权威，离线时只读缓存 |
| 大剧本扩容到 40KB | NVS 跨页写入耗时不划算，宁可明确失败 |

## 8. 已知风险

1. **协议切换是一次性断崖**：v2 数据（NVS blob v3/v1）与 v3 不兼容，刷新固件后旧配置全部丢失，
   回到默认值。个人测试阶段可接受，但**必须在验收记录里写明**。
2. **两层合成让单帧 CPU 开销上升**：每颗灯珠从 1 次求值变最多 2 次 + 1 次 blend。
   8 带 × 64 灯 = 512 颗，最坏 1024 次求值。C3 单核 @160MHz 上需要实测帧耗时，
   若 20fps 撑不住则降到 15fps（`CONFIG_LUMEN_ANIM_FPS` 已可配）。
3. **NVS 容量**：见 `protocol-v3.md` §10.4。最坏情况装不下 4 套满配剧本，属于物理限制，
   用显式失败处理。
4. **BLE 抢 RMT ISR**：v3 帧变长意味着单次写可能分多片，写次数增加。
   需在验收时复核错色率不高于 v2 基线（0.42%）。
