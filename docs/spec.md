## 问题陈述

用户桌上有一条 WS2812B 灯带，现在只能靠开发板串口或临时脚本控制。用户想要的是**像一盏普通灯那样使用它**：

- 打开微信就能用——不装 App、不注册账号、不连 Wi-Fi、不依赖云端。
- 点一下开关就亮灭；拖亮度时灯带立刻跟着变，而不是松手后才响应；选颜色要所见即所得。
- 关灯再开，亮度还是刚才那个；整条灯带断电再上电，颜色、亮度、开关状态都回来。
- 手机离开房间再回来，不用重新扫码配置，自己连上。
- 换了一条不同长度的灯带，能告诉设备现在有多少颗灯珠。
- 出问题时（连不上、颜色不对、偶发闪烁）能在手机上看到每一帧收发的原始字节，而不是靠猜。

现有方案都不合适：通用 BLE 灯控 App 要安装、要账号、常带云依赖；厂商 App 绑死自家硬件；串口调试对最终用户不可用。这个项目要把控制链路缩到最短——**手机 ↔ 设备，一跳 BLE，没有中间层**。

平台与硬件约束塑造了整个方案：iOS 没有设置 MTU 的 API，超长写入会静默失败；ESP32-C3 的 RMT 没有 DMA 且是单核，与 BLE 共用射频；3.3V 逻辑驱动 5V 灯带在规格上不达标。这些不是「可能有问题」，而是设计前提。

## 解决方案

两端：一个原生 TypeScript 微信小程序 + 一个纯 ESP-IDF 固件。

- **发现**：固定 Service UUID 过滤扫描，广播名 `Lumen-XXXX` 供人眼识别；点击即连，不做配对。
- **控制**：单页面完成连接状态 → 开关 → 亮度 → 色环 → 预设色块的全部操作，无页面跳转。
- **协议**：二进制紧凑帧，总长 ≤ 20 字节，每帧回 ACK（回显 seq + 结果码）。
- **状态**：开关与亮度解耦；颜色走用户空间 RGB；固件做 gamma 校正再乘亮度；状态变更 debounce 写 NVS，上电恢复。
- **回连**：缓存 deviceId，进前台静默回连，1s/2s/4s 有限次退避；连上后读 State 特征值同步 UI。
- **诊断**：隐藏协议日志面板 + 固件串口逐帧日志 + 自检命令，靠 seq 对齐两端。
- **可靠性**：渲染永远取最新状态，渲染只在变化时发生；RMT × BLE 共存风险有独立的量化验证与备选路线。

MVP 只有静态单色 + 亮度，没有灯效、没有云端、没有多设备管理。

## 用户故事

### 发现与连接

1. 作为第一次使用的用户，我希望打开小程序就能看到附近名为 `Lumen-XXXX` 的设备，以便不用输入任何地址或配对码就能开始。
2. 作为有多条灯带的用户，我希望扫描结果同时显示广播名和信号强度，以便在列表里认出要连的那一条。
3. 作为用户，我希望点一下设备就完成连接，以便控制流程不超过两步。
4. 作为用户，我希望页面顶部始终显示当前连接状态（未连接 / 扫描中 / 已连接 + 设备名），以便知道现在按按钮有没有用。
5. 作为用户，我希望连接成功后界面自动变成设备里的真实状态，以便不会出现「界面显示开、灯却是关」。
6. 作为用户，我希望手机短暂离开范围后回来能自动重连，以便不用每次重新扫描。
7. 作为用户，我希望自动重连按 1s/2s/4s 的节奏有限次尝试，失败后明确告诉我「未连接」并给手动重连入口，以便它不会无限空转，我也知道该做什么。
8. 作为用户，我希望手机蓝牙没开时看到「请打开蓝牙」而不是报错退出，并在打开蓝牙后自动继续，以便不用重启小程序。
9. 作为 Android 用户，我希望扫描 10 秒仍无结果时被提示检查定位权限和定位开关，以便不会遇到「一直扫不到但没有任何提示」。
10. 作为 iOS 用户，我希望首次使用时看到系统的蓝牙授权提示，并在拒绝后得到可理解的说明，以便知道去哪里改。
11. 作为用户，我希望设备同一时间只接受一台手机连接，以便两台手机不会互相抢控制权导致灯带乱跳。
12. 作为用户，我希望断线时界面立即显示未连接，而不是继续显示旧状态，以便我不会误以为指令生效了。

### 控制

13. 作为用户，我希望有一个独立的大开关按钮，以便一眼找到并可靠地开灯/关灯。
14. 作为用户，我希望关灯后亮度值保留，再次开灯恢复原亮度，以便不用每次重新调光。
15. 作为用户，我希望亮度拖到 0 时等同于关灯，以便两个控件不会互相矛盾。
16. 作为用户，我希望拖动亮度滑块时灯带实时跟随，以便边拖边找到合适的亮度。
17. 作为用户，我希望快速来回拖动时只看到最新位置的效果，而不是把中间值排队重放，以便控制感是「跟手」而不是「追尾」。
18. 作为用户，我希望用色环选任意颜色，以便不被固定色板限制。
19. 作为用户，我希望有 6-8 个常用预设色块（暖白 / 冷白 / 红 / 绿 / 蓝 / 紫 / 橙），以便常用颜色一键到位。
20. 作为用户，我希望低亮度下颜色不偏（暗红不发棕、暗蓝不发灰），以便夜间使用也准确。
21. 作为用户，我希望颜色、亮度、开关可以一次下发，以便切预设或恢复场景时不会看到中间态跳变。
22. 作为用户，我希望开关指令即使丢了一包也能靠一次重传生效，以便按一下就是一下。
23. 作为用户，我希望连续调色/调光不重传旧值，以便不会在松手后又跳回旧颜色。

### 状态与持久化

24. 作为用户，我希望整条灯带断电再上电后恢复断电前的颜色、亮度和开关状态，以便它像普通灯具一样工作。
25. 作为用户，我希望状态变更后很快被记住（短 debounce），而不是每拖动一像素就写一次存储，以便既不丢状态也不磨损 flash。
26. 作为用户，我希望第一次上电（无历史状态）时设备处于安全、可预期的默认状态，以便不会突然全白刺眼或全黑让人以为坏了。
27. 作为用户，我希望能在小程序里告诉设备当前灯带有多少颗灯珠，以便换长度后不用重新烧固件。
28. 作为用户，我希望灯珠数量改完立即生效并在重启后保持，以便只设置一次。
29. 作为用户，我希望灯珠数量填错（0、超上限、非数字）时被明确拒绝并保留旧值，以便不会把设备配置搞坏。
30. 作为用户，我希望设备重连后界面从设备读取一次完整状态再刷新控件，以便两端永远以设备为准。

### 可靠性与边界

31. 作为用户，我希望每条指令都有回执（回显序号 + 结果码），以便丢包或失败能被发现。
32. 作为用户，我希望校验失败的帧被丢弃并回错误码，而不是被执行，以便线路噪声不会变成随机颜色。
33. 作为用户，我希望超长帧被设备明确拒绝，而不是截断后执行，以便不会出现「大部分生效、个别字节错位」的怪状态。
34. 作为用户，我希望未知命令得到明确的「不支持」回执，以便新旧版本混用时能定位问题。
35. 作为用户，我希望亮度/颜色越界时行为是确定的（钳位或拒绝，二选一并写进协议），以便不同版本不会各自解释。
36. 作为用户，我希望固件在 BLE 高频写入时仍然优先保证灯带不闪（渲染取最新状态），以便调节过程稳定。
37. 作为用户，我希望设备只允许一个连接，旧连接异常残留时能被释放，以便重连不会一直失败。
38. 作为用户，我希望「灯闪/错色」能被明确归因到协议、接线或 RMT 中断中的某一类，以便我不用把整条链路重做一遍。

### 诊断

39. 作为开发者，我希望开发版把每一帧的 hex 打到 console，以便在电脑上就能看到收发内容。
40. 作为开发者，我希望页面上有一个隐藏的协议日志面板（连点 5 次开启），包含时间戳、方向、hex、解析后的命令名与参数，以便在真机上定位问题。
41. 作为开发者，我希望日志面板能暂停、清空、复制，以便长日志可以带走去比对。
42. 作为开发者，我希望固件串口日志打印每帧的命令字、序号和结果码，以便两端日志能按 seq 对齐。
43. 作为开发者，我希望有一个自检命令能按固定顺序点亮颜色，以便不依赖小程序就能验证灯带与接线。
44. 作为开发者，我希望两端用同一份 JSON 测试向量跑 codec 单测，以便字节级分歧在真机联调前就暴露。
45. 作为开发者，我希望 codec 在编码结果超过 20 字节时直接抛错，以便不会在 iOS 上变成静默失败的写入。

### 硬件与限制

46. 作为用户，我希望全白高亮度不会让开发板掉电重启；如果会，我希望亮度上限被限制在安全值，以便正常使用中不会把设备弄挂。
47. 作为用户，我希望灯带在 BLE 活动时也不出现肉眼可见的闪烁或错色；如果这是硬件限制，我希望它被明确记录，以便我知道这是已知边界而不是坏了。
48. 作为用户，我希望更换/加长灯带后只需要改灯珠数量，不需要改接线或重烧固件，以便维护简单。
49. 作为后续画板的人，我希望方案里明确记录 3.3V 驱动 5V 灯带必须加 74AHCT125、数据线串阻、首灯电容与共地要求，以便打样时不会漏掉。
50. 作为后续画板的人，我希望数据脚选在 C3FH4 未被占用的 GPIO 上，并且默认值可在编译期改，以便硬件改版不用改业务代码。

## 实现决策

### 1. 系统边界与唯一真相源

- 两端独立构建、独立部署，运行期唯一的耦合是 BLE 上的字节流。
- 协议文档是字节级唯一真相，测试向量是它的可执行副本。任何协议改动必须让**协议文档、测试向量、两端实现进同一个 commit**。
- 本规格不复述协议字节值，只约束协议必须满足什么。协议文档与测试向量已经定稿（见 [protocol.md](./protocol.md)）；改协议时三者必须同步。
- 没有服务器、没有账号、没有云端；设备不联网。

### 2. GATT 结构

- 一个 Service，三个 Characteristic：RX（`write-no-response`）、TX（notify）、State（read）。
- UUID 在协议文档中固定，两端硬编码同一组值；扫描以 Service UUID 过滤，广播名只用于人眼识别。
- State 的 read 布局与「查询状态」命令的应答载荷**完全一致**，避免两端各维护一套解析器。
- 设备只允许 1 个连接（NimBLE 显式配置为 1）。旧连接异常残留必须能被释放，否则重连会一直失败。
- 不做 bonding / 不要求配对；连接即控制，这是已接受的取舍。

### 3. 连接生命周期

- 固定初始化序列：连接 → MTU 协商（**仅 Android 5.1+**；iOS 跳过）→ 订阅 notify → 留间隔或先 read 一次 → 读取 State 同步 UI。
- 订阅成功不等于有数据；设备必须在状态变化时真正 notify。
- 断线监听是唯一的重连触发源；`10006` 不重试写，走重连。
- 回连：缓存 deviceId，进前台静默回连；1s/2s/4s 有限次退避；仍失败则显示未连接并给手动入口。
- `10008` 视为系统兜底异常，先检查是否踩了「notify 后立即写」，加间隔重试一次。
- `10001` 非致命：适配器已初始化，等 `onBluetoothAdapterStateChange`。
- iOS 的 fail `state`（0 未知 / 1 重置中 / 2 不支持 / 3 未授权 / 4 未开启）必须映射为可读文案。

### 4. 帧格式与 20 字节预算

- 帧骨架固定：`magic(0xA5) | version | command | seq | length | payload | checksum`。
- 总长 ≤ 20 字节；骨架开销 6 字节，payload ≤ 14 字节。**MVP 不做分包/重组**。
- 超长帧在设备端必须被拒绝并回错误码，绝不截断执行、绝不缓冲等待后续包。
- 小程序在 encode 后断言总长 ≤ 20，超长抛错，不静默截断（iOS 超长写可能既无 success 也无 fail）。
- 多字段变更用「一次设全部」表达，不依赖多帧的原子性。

### 5. 协议契约（已定稿，见 [protocol.md](./protocol.md)）

- 命令集至少覆盖：设开关、设亮度、设颜色、一次设全部、查询状态、设灯珠数量、自检。
- 每个命令的载荷必须逐字段核算，**全部 ≤ 14 字节**；超预算的命令砍掉或改结构，不引入分包。
- 每个字段的偏移、宽度、字节序、取值范围逐条写明。
- 校验和：算法可执行、覆盖范围明确（含不含 magic/version 必须写明），并给一个能人工验算的例子。
- 结果码至少覆盖：成功、参数越界、未知命令、校验失败、忙/暂不可用。ACK 回显 seq。
- seq 的起点、回绕、设备是否需要去重必须写明。
- 边界语义逐条写死：亮度/颜色越界是钳位还是拒绝；亮度 0 与开关字段冲突时谁优先；未知命令是否回 ACK；坏 magic / 坏 length / 坏校验分别回什么；ACK 在状态生效前还是后发；NVS 写失败回什么。
- version：MVP 填固定值；读端遇到未知版本的行为必须写明（MVP 可拒绝并回结果码）。
- 协议文档的验收线：实现者读完后不需要再问任何问题就能写出 codec。

### 6. 状态模型与持久化

- 共享状态字段：开关、亮度（0-255）、颜色（用户空间 RGB 0-255）、灯珠数量。
- 开关与亮度解耦；关灯保留亮度；亮度 0 等价于关灯。
- 颜色：小程序用 HSV 取色，换算为用户空间 RGB（**不做 gamma**）；固件做 gamma 校正后再乘亮度。gamma 表只在固件，测试向量只覆盖「RGB + 亮度 → 像素值」。
- 持久化：状态变更后 debounce 写 NVS；上电恢复；恢复失败回默认值。
- 灯珠数量：运行时变更需重建 led_strip 句柄；失败回滚并保持旧配置；成功后持久化。
- 首次上电默认：关灯、亮度 128、暖白（具体 RGB 在协议文档固定），避免首次上电全白刺眼。
- 设备是状态权威：小程序每次连上后读 State，不用本地缓存覆盖设备。

### 7. 固件分层与并发

- 三层：`ble_link`（GATT + 帧收发）、`led_engine`（共享状态 + gamma + 渲染）、`state_store`（NVS）；依赖单向。
- BLE 回调只做三件事：解码 → 写共享状态 → 发信号量。**禁止**刷灯、写 NVS、大段日志。
- latest-wins：互斥锁 + dirty 标志 + 二值信号量；渲染任务醒来总是取最新快照，永不排队旧帧。
- 渲染只在状态变化时发生，不做固定帧率空转——这同时减轻下面的 RMT 风险。
- 灯带句柄的唯一所有者是渲染任务；`set_pixel + refresh` 非原子，禁止并发刷新；`refresh` 与 `refresh_async` 二选一并记录理由，若用 async 必须自建双缓冲。
- C3 是单核：NimBLE 主机任务优先级高于渲染任务；栈大小与优先级在骨架票里定并记录理由。
- 初始化顺序照研究笔记的 NimBLE 标准序列；连接数显式设为 1。

### 8. 渲染、RMT 与电气

- 30 灯珠、GRB、默认 GPIO3（Kconfig 可配）。C3FH4 的禁用引脚清单必须写进接线文档；GPIO3 不在禁用名单内。
- **3.3V 驱动 5V 灯带规格不达标**（VIH = 0.7×VDD = 3.5V）：开发阶段接受为已知限制；画板必须加 74AHCT125（不能用 74HC125），首灯并 500-1000µF 电容，数据线串 300-500Ω 电阻，**必须共地**。
- 电流：30 灯全白约 1.8A，开发板 USB 5V 通常限流 500mA-1A。亮度上限的决策规则：若点灯验证出现掉压/重启，固件引入编译期亮度上限，小程序滑块最大值与之对齐；若没有，则在接线文档里明确「全白只短暂测试」。
- **RMT × BLE 是最大技术风险**：C3 无 RMT DMA 且单核，默认怀疑波形损坏。缓解手段只有：`mem_block_symbols` 取 48 的整数倍并实测、编码相关函数放 IRAM、只在变化时刷新、async + 自建双缓冲。判定线沿用验证票：30 分钟高频写入下错色 ≤ 1 次/10 分钟且用户不可感知；不可接受则架构转向 SPI 驱动 WS2812。
- 共存验证必须在端到端验收之前完成；它若失败，验收没有意义。

### 9. 小程序分层

- 传输层：Promise 化 `wx.*`（含超时、错误码归一）；固定初始化流水线；**写入串行化**（同一时刻只有一个写在进行）；断线重连与退避；deviceId 缓存与前台静默回连。
- codec：encode/decode 纯函数；encode 后硬断言 ≤ 20 字节，超长抛错；checksum 与测试向量逐字节一致。
- 节流层：20Hz 上限，latest-wins，不排队；连续量不重传；开关可重传一次；ACK 超时只作为「可能断线」信号触发连接检查，不作为重传连续量的理由。
- 协议日志：环形缓冲保留最近 200 帧，记录时间戳 / 方向 / hex / 解析结果；UI 只消费这个缓冲。
- UI 层不得直接调用 `wx.*`；所有 BLE 细节封在传输层。
- 错误分诊：`10006` → 重连；`10008` → 检查 notify 后立即写；`10001` → 非致命等待。

### 10. 界面

- 单页完成全部操作，无页面跳转：顶部连接状态条 → 开关 → 亮度滑块 → 色环 → 预设色块（6-8）。
- 扫描/连接是弹层，显示广播名 + RSSI；连接中/失败有明确文案。
- 灯珠数量是设备级低频设置，放在连接/设备弹层内，不占主控制流。
- 隐藏协议日志面板：连点版本号 5 次开启，含时间戳/方向/hex/解析结果，支持暂停、清空、复制。
- 平台文案：`10001` 显示「请打开蓝牙」并继续监听；Android 扫描 10 秒无结果提示定位权限/开关；iOS 按 `state` 0-4 给文案。
- 进前台静默回连；回连成功后读 State 同步控件。
- 控件尺寸与手感以真机为准；不做主题、动画、多页面。

### 11. 诊断与可观测性

- 开发版每帧打印 hex 到 console。
- 固件串口按帧打印命令字 / seq / 结果码，能与小程序日志按 seq 对齐。
- 自检命令：不依赖小程序，按固定顺序点亮颜色，用于验证接线与通道顺序。
- 两端时间戳不要求跨端同步；对齐靠 seq。

### 12. 配置、默认值与可调项

- 数据脚、灯珠数、颜色顺序、Service/Characteristic UUID、命令字、结果码、灯珠数量上限、亮度上限、首次上电默认状态——这些值必须在协议文档与 Kconfig 中作为唯一权威记录，两端实现照抄，不得各自演化。
- 协议版本独立于固件版本；MVP 只有一个版本值。

### 13. 变更与协作

- 改协议 = 协议文档 + 测试向量 + 两端实现同一个 commit。
- 一端先实现、另一端后实现时，以测试向量为对齐依据，不以口头描述为准。

## 测试决策

### 什么算好测试

- 只测公开行为：给定字节输入 → 字节输出或状态输出。不测内部函数调用、不测日志文案、不测私有字段。
- 测试必须在协议字节变化时失败。如果改了协议测试还全绿，说明测的是实现细节。
- 不 mock 硬件。BLE、RMT、NVS、供电全部靠真机验收；唯一允许的假件是计时器（节流测试）和假传输通道（串行化测试）。

### 唯一接缝

整条链上只有一个跨端接缝：**协议字节流**。

- 两端的 codec 都实现为纯函数，由同一份 JSON 测试向量驱动。这是最高接缝——再往上就需要真机 BLE，无法稳定跑在 CI 里。
- 固件侧把同一接缝延伸为纯 reducer（旧状态 + 命令 → 新状态）与渲染函数（状态 → 像素字节），在 host target 的 Unity 里测。
- 小程序侧把同一接缝延伸为节流调度（输入流 → 发送流）与写入串行化（用假通道验证同一时刻最多一个在飞）。
- 不为 BLE / RMT / NVS 新建 mock 接缝。这个选择继承自架构基线，本规格不新增接缝。

### 测什么

- **固件 host（Unity）**：帧解码（合法 / 坏 magic / 坏校验 / 坏 length / 超长 / 未知命令）、ACK 编码、状态 reducer 的全部边界（亮度 0、开关与亮度冲突、灯珠数量越界）、gamma + 亮度输出、灯珠数量变更的回滚决策。
- **小程序（vitest）**：codec 跑全部测试向量；encode 超长抛错；节流 100Hz 输入 → 输出 ≤ 20Hz 且发的是最新值；写入串行化；错误码映射与 10006/10008/10001 分诊。
- **两端共用向量**：开灯、关灯、设亮度、设颜色、一次设全部、查询状态、设灯珠数量、自检、合法帧、坏校验帧、坏 magic 帧、超长帧、未知命令、边界值（0 / 255 / 灯珠数上限）。
- **真机门禁**：7 条验收清单 + RMT × BLE 的量化判定线，不作为单测。

### 测试的 prior art

仓库目前没有测试代码，这是第一套。可参照 ESP-IDF 官方 host Unity 测试的组织方式；「两端共用同一份 JSON 测试向量」是架构基线里已经定下的做法。

## 范围之外

- **WiFi / MQTT / 云端控制**：不做第二条通道，不做 Broker 与备案域名。
- **账号体系、云同步、场景云端存储**：原型阶段无服务器。
- **产品化**：PCB 设计、外壳、3C 认证、量产 BOM、小程序审核上架、固件 OTA。
- **灯效库**（呼吸 / 彩虹 / 流光 / 音乐律动）与任何固定帧率驱动。
- **多灯带联动 / 分区控制 / 定时任务**。
- **多设备管理**：设备列表、分组、并发连接策略。
- **BLE 配对与认证**：开放式连接，同房间任何人都能控。
- **协议分包 / 重组**：MVP 帧必须塞进 20 字节。
- **协议版本向后兼容**：两端同时发版的现状下不构成真问题。
- **iOS / Android 机型矩阵穷举**：只记录实测到的差异。

## 补充说明

### 已确认的硬事实（决策前提，不可当假设推翻）

- BLE 默认 ATT MTU 为 23，单次实际可写 20 字节；`wx.setBLEMTU` 仅 Android 5.1+ 有效；iOS 超长写入可能既无 success 也无 fail。来源：研究笔记 A1/A2。
- ESP32-C3 的 RMT 无 DMA（无 `SOC_RMT_SUPPORT_DMA`）且为单核；官方缓解措施「把 RMT 驱动装到另一个核」在 C3 上不可用。来源：研究笔记 B11/B12。
- WS2812B 的 VIH = 0.7 × VDD，5V 供电下为 3.5V，高于 C3 的 3.3V 输出——规格不满足。来源：研究笔记 B13。
- 30 灯全白约 1.8A（单灯 60mA 通用值），开发板 USB 5V 通常限流 500mA-1A。来源：研究笔记 C14。

### 已关闭的开放项

协议字节细节已在 [protocol.md](./protocol.md) 定稿：

- 命令字、载荷布局、字节序、校验和覆盖范围、结果码枚举、seq 语义、State 布局。
- Service / Characteristic 的具体 UUID。
- 首次上电默认颜色 RGB(255,180,120)、灯珠数量上限 64、默认 30。
- ACK 在写入 RAM 后回；NVS 写失败用 Event `0x81`；设备端未知 version 回 `0x07`。

### 仍需在实现前确认

- **亮度上限**：等 #4（led_strip 点灯验证）的供电实测结果。协议已用 State 的 `max_brightness` 字段暴露该上限，初值 255；最终值由固件构建常量决定。
