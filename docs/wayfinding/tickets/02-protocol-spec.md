# 02：协议规格定稿

**类型**：`wayfinder:grilling`（HITL）

## Question

`docs/protocol.md` 要写成什么样，才能让固件和小程序两端各自关起门来实现，最后一次性对上？

这是整条链上最关键的一票。协议没写死就并行开工，两端一定会分叉——字节序、位偏移、gamma 在哪端、亮度乘在哪个阶段、ACK 里 seq 怎么回、命令字冲突——每一个都会在真机联调时伪装成「灯不亮」或「颜色不对」，排查成本极高。

### 已经定了的（见 architecture-brief.md）

- 帧骨架：`magic(0xA5) | version | command | seq | length | payload | checksum`
- GATT：一个 Service + RX / TX / State 三个 Characteristic
- 颜色走用户空间 RGB（0-255，不做 gamma），亮度独立 0-255，gamma 在固件
- 开关与亮度解耦，关灯保留亮度
- 设备对每帧回 ACK

### 硬约束：帧总长必须 ≤ 20 字节

研究已确认（见 [研究笔记](../research/ble-and-firmware-facts.md) A1/A2）：

- BLE 默认 ATT MTU 为 23，减去 3 字节 ATT 头 → **单次实际可写 20 字节**。
- `wx.setBLEMTU` **仅 Android 5.1+ 有效，iOS 没有这个 API**。
- **iOS 上超长写入会静默失败**（既无 success 也无 fail 回调），客户端不能靠错误回调兜底。

所以协议**不能假设 MTU 会被协商到更大**。当前骨架开销 `1+1+1+1+1+1 = 6` 字节，**payload 只剩 14 字节**。

「一次设全部（开关 1 + 亮度 1 + R G B 3）」只要 5 字节，够用。但任何带变长数组或字符串的命令都会爆预算。**这一票必须逐条核算每个命令的载荷是否能塞进 14 字节，并明确写出「超预算时怎么办」**（砍命令 / 拆成多帧 / 引入分包重组）。

### 这一票要钉死的

1. **命令字表**：MVP 需要哪些命令（设开关 / 设亮度 / 设颜色 / 一次设全部 / 查询状态 / 设灯珠数量 / 自检帧…），每个的字面值、载荷结构、字节序、**以及在 14 字节预算下的核算**
2. **ACK 载荷**：结果码枚举（成功 / 参数越界 / 未知命令 / 校验失败 / 忙）、是否回带状态
3. **checksum 算法**：具体怎么算（求和取反？范围含不含 magic？）——这一条两端必须逐字节一致
4. **version 字段**：MVP 填什么值，读端遇到未知版本怎么办
5. **seq 语义**：从几开始、回绕、设备侧是否需要去重
6. **State 特征值的布局**：read 返回什么，和「查询状态」命令的载荷是否同一结构（注意 read 不受 20 字节写入限制，但建议保持一致以免两套布局）
7. **错误与边界**：亮度/颜色越界时是钳位还是拒绝；未知命令是否回 ACK
8. **测试向量**：一批「输入状态 + 期望字节序列」的 JSON fixture，两端共用

## Blocked by

无（可以立刻开始，且**应当在所有实现票之前完成**）

## 交付

- `docs/protocol.md`：完整规格，含命令字表、载荷布局表、ACK 结果码表、校验算法伪代码
- `docs/protocol-testvectors.json`：两端共用的测试向量

## 验收

- [ ] 命令字表覆盖 MVP 全部操作，无未定义命令
- [ ] 每个命令的载荷**实际字节数**都核算过，全部 ≤ 14，超预算的有明确处理方案
- [ ] 每个载荷字段的偏移、宽度、字节序、取值范围都写明
- [ ] checksum 有可执行的伪代码，能人工验算一个例子
- [ ] 测试向量含至少「开灯 / 关灯 / 设亮度 / 设颜色 / 一次设全部 / 合法帧 / 坏校验帧」七类
- [ ] 两端实现者读完后，不需要再问任何问题就能写出 codec
