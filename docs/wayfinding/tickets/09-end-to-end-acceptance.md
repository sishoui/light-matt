# 09：端到端真机联调与验收

**类型**：`wayfinder:task`（HITL — 必须你配合操作）

## Question

七条真机验收清单能不能全部通过；通不过的那几条，根因在哪一侧？

这是整张地图的收口票。它不是「再测一遍」，而是**第一次让两端同时上线**——协议对齐、时序、电气、权限，所有假设在这一刻被真实硬件检验。

### 做法

按 `architecture-brief.md` 的 7 条清单逐条跑，每条记录：现象、串口日志尾部、小程序协议日志相关帧。失败的条目先按下面的顺序二分定位：

| 症状 | 先查 |
|---|---|
| 扫不到 / 连不上 | 小程序端日志与系统蓝牙设置；iOS 下是否需从系统设置删除旧的设备记录 |
| 连上但写入无反应 | 两侧协议日志的 hex 是否逐字节相同（不同 → codec 问题；相同 → 固件分发问题） |
| 灯不亮 / 颜色错乱 | 回到【led_strip 点灯验证】的结论；检查共地与供电 |
| 调光卡顿 / 延迟累积 | 节流层是否真在覆盖而非排队；固件渲染任务是否被阻塞 |
| 重连失败 | MTU 协商、notify 重新订阅、设备侧是否残留旧连接未释放 |
| 断电不恢复 | NVS 写入时机与 debounce 是否生效 |

### 交付

- `docs/acceptance-report.md`：7 条逐条结论 + 证据（日志片段）+ 已知遗留问题
- 修掉验收中暴露的 bug（如果范围小）
- 如果暴露的是设计问题（不是 bug），**不开新票**，记录在验收报告里并回写到 map 的 Not yet specified
