# 09：端到端真机联调与验收

**类型**：`wayfinder:task`（HITL — 必须你配合操作）

## Question

七条真机验收清单能不能全部通过；通不过的那几条，根因在哪一侧？

这是整张地图的收口票。它不是「再测一遍」，而是**第一次让两端同时上线**——协议对齐、时序、电气、权限，所有假设在这一刻被真实硬件检验。

### 做法

按 `architecture-brief.md` 的 7 条清单逐条跑，每条记录：现象、串口日志尾部、小程序协议日志相关帧。失败的条目先按下面的顺序二分定位：

| 症状 | 先查 |
|---|---|
| 扫不到 / 连不上 | 小程序端日志与系统蓝牙设置。**Android 6.0+ 无定位权限会静默扫不到**（8.0.16 前无错误回调）；iOS 缓存设备记录需从系统设置删除 |
| 连上但写入无反应 | 两侧协议日志的 hex 是否逐字节相同（不同 → codec 问题；相同 → 固件分发问题）。**注意 iOS 超长写会静默失败**，先确认帧长 ≤ 20 |
| 写入报 10008 | Android 上 notify 后立刻写会触发；检查初始化序列里是否有间隔 |
| 写入报 10006 | 连接已断，不是写入问题——走重连，不要重试写 |
| 灯不亮 / 颜色错乱 | 回到【led_strip 点灯验证】的结论；检查共地、电容、电平转换。**若错色与 BLE 活动相关**，那是【RMT × BLE 共存】的结论 |
| 偶发闪烁 / 错色，但静止时不出现 | 高度怀疑 RMT 中断被 BLE 抢占；查【RMT × BLE 共存稳定性验证】的 `mem_block_symbols` 结论 |
| 调光卡顿 / 延迟累积 | 节流层是否真在覆盖而非排队；固件渲染任务是否被阻塞；`refresh()` 是否在 BLE 回调里 |
| 重连失败 | MTU 协商、notify 重新订阅、设备侧是否残留旧连接未释放（NimBLE 连接数设成 1 时尤其要确认旧连接已释放） |
| 断电不恢复 | NVS 写入时机与 debounce 是否生效 |
| 全白时板子重启 | 电流超限（30 灯全白约 1.8A，开发板 USB 通常限流 500mA-1A）——不是 bug，是供电 |

### 交付

- `docs/acceptance-report.md`：7 条逐条结论 + 证据（日志片段）+ 已知遗留问题
- 修掉验收中暴露的 bug（如果范围小）
- 如果暴露的是设计问题（不是 bug），**不开新票**，记录在验收报告里并回写到 map 的 Not yet specified

## Blocked by

- 【固件协议实现与状态机】
- 【小程序控制界面】
- 【RMT × BLE 共存稳定性验证】—— 这一票若判定不可接受，本票的验收没有意义
