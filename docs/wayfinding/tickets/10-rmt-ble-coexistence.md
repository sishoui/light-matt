# 10：RMT × BLE 共存稳定性验证

**类型**：`wayfinder:prototype`（HITL — 需要真机长跑观察）

## Question

在 ESP32-C3 上，BLE 连接建立并持续通信时，led_strip 的 RMT 刷新会不会偶发损坏波形、导致灯珠错色或闪烁？如果会，加大 `mem_block_symbols` 能不能压住？

### 为什么单独开一票

研究确认了两个硬事实，它们叠在一起构成这个项目**最大的技术风险**：

1. **ESP32-C3 的 RMT 没有 DMA**（`soc_caps.h` 无 `SOC_RMT_SUPPORT_DMA`，只有 S3 有）。WS2812 波形由 ISR 逐块编码输出。
2. `led_strip` README 原文警告：若 RMT 中断被延迟（例如同核上发生 Wi-Fi 中断），**RMT 事务会损坏，灯珠显示错误颜色**。

而官方给出的头号缓解措施是「把 RMT 驱动装到另一个核」—— **C3 是单核，这条不可用**。C3 又只有一个 2.4GHz 射频，BLE 连接事件周期性抢占中断。

所以这不是「可能有问题」，是「默认应当怀疑」。如果这条不成立，整个方案得换驱动路线（改用 SPI 驱动 WS2812，C3 上可行），那是重大架构变更，必须尽早知道。

### 要验证的

| # | 假设 | 怎么验 |
|---|---|---|
| 1 | BLE 未连接时，灯带稳定 | 基线：`mem_block_symbols=48`，连续刷 30 分钟，肉眼 + 每帧 checksum 比对 |
| 2 | BLE 连接空闲时，灯带仍稳定 | 手机连上不写指令，持续刷新，观察是否偶发错色 |
| 3 | BLE 高频写入时，灯带出现损坏 | 20Hz 连续下发颜色变化，观察错色/闪烁率 |
| 4 | 加大 `mem_block_symbols` 能改善 | 依次试 48 / 96 / 192 / 384，记录错色率变化与内存占用 |
| 5 | `refresh_async` + 自建双缓冲优于 `refresh()` | 对比渲染任务的阻塞时间与丢帧表现 |

### 判定线

- **可接受**：30 分钟高频写入下，错色帧 ≤ 1 次/10 分钟，且用户不会注意到
- **不可接受**：肉眼可见闪烁，或错色频率与 BLE 活动明显相关
- 不可接受 → 记录结论，回写到 map 的 Not yet specified，**架构需要重新评估驱动路线**（SPI 驱动 WS2812 备选）

### 不做

不优化灯效，不处理协议逻辑，只测「刷新 + BLE 共存」这一件事。

## Blocked by

- 【led_strip 点灯验证】—— 先确认灯带本身能稳定点亮
- 【固件 BLE 服务与分层骨架】—— 需要 BLE 真正连上并在跑
